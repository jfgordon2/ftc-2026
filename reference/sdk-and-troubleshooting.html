Words used while diagnosing a problem

Symptom
The exact thing you can observe that is wrong. Example: The Driver Station does not list our OpMode, not The code is broken.
Error message
Text from Android Studio or the Driver Station that identifies a failure. Copy the first message exactly, including its file and line when shown.
Log
A time-ordered record of messages from an app or device. Preserve the relevant Robot Controller, Driver Station, or Logcat lines before restarting.
Configuration
The saved list that connects each Hub port and device type to an exact name. The name in Java must match it, including capitalization.
Hypothesis
One possible cause that the evidence can support or reject. Example: The OpMode is missing because @Disabled is still present.
Evidence
An exact message, value, file and line, log entry, measurement, or inspection result that supports or rejects a hypothesis.

Five-step SDK lookup

  1. Start at the pinned TeamCode readme. Use sample names as a map: Basic for structure, Sensor for one input, Robot for combined capabilities, and Concept for one SDK feature.
  2. Browse the pinned external/samples directory. Read the sample header for required hardware, configuration names, and warnings before using code.
  3. Copy the closest sample into TeamCode, rename the file, class, and OpMode, then adapt names and constants. Remove @Disabled only when testing is safe. Never edit the source sample under FtcRobotController.
  4. In Android Studio, use declaration or quick documentation on the SDK class or method. Then verify its summary, signature, parameters, limits, and return value in the pinned FTC SDK 12.0 RobotCore Javadocs or the SDK artifact index.
  5. Use Oracle Java Language Basics only for the language feature needed by the current robot task.

Troubleshooting questions, in order

Answer each question before moving down. Change one thing at a time so the next result shows whether that change mattered.

  1. Did the code build? Open Android Studio's Build output. If it failed, copy the first error message and open its linked team-code file and line. Make one correction and build again. Success: Build output reports success.
  2. Did the app install? If the build succeeded, check charged 12 V power, the Control Hub USB-C connection, and the named target. Run TeamCode using the official install steps. Success: the Run window reports completion and the Driver Station reconnects to the Robot Controller.
  3. Does the OpMode appear? On the Driver Station, look for its exact display name. If absent, confirm its class is in TeamCode, has @TeleOp or @Autonomous, does not have @Disabled, and was included in the installed app. Success: the expected name can be selected.
  4. What is the first team-code file and line? If INIT or Run reports an exception, copy the exact Driver Station message and the first stack-trace entry shaped like Class.java:line that belongs to the team's file. Start there instead of changing every highlighted line.
  5. What input, decision, and output can telemetry show? If no exception appears but behavior is wrong, display the relevant input value, the choice or current state the code makes, and the output command it sends. Compare those values with the configuration, wiring, and mechanism before changing the algorithm.
  6. What does the log add? If the Driver Station message is not enough, inspect Robot Controller/Driver Station logs or Android Studio Logcat. Save the first relevant error and nearby lines before power cycling when possible.
  7. What did the evidence prove? In the fault log, record the symptom, one hypothesis, the evidence, the confirmed cause, the one change made, and the result of repeating the same test.

Pinned velocity and PIDF lookup

Use this path only for an exact encoder-equipped motor exposed as DcMotorEx. API documentation establishes method behavior; the matching manufacturer source owns exact hardware facts; the team owns its test boundary and acceptance criteria; and only recorded trials establish a result on the installed robot.

  1. Verify identity and scope. Record the exact robot and launcher assembly, motor, motor controller, active configuration, code identity, and SDK version. Confirm the object is a DcMotorEx. A same-brand or similar-looking assembly does not transfer coefficients.
  2. Verify velocity units and sign. Follow pinned RobotCore 12.0.0 getVelocity() and setVelocity(double). Record target and measured velocity in the same documented unit. Wrong-sign, implausible, flat, or full-output behavior is a fault: press Stop, complete shutdown, preserve evidence, and inspect direction, encoder, wiring, configuration, mode, controller, and code instead of tuning around it.
  3. Check the run mode. Record getMode() and the exact velocity-control mode used by the code. Pass that same explicit mode to pinned getPIDFCoefficients(mode) and setPIDFCoefficients(mode, coefficients). A mode mismatch blocks comparison.
  4. Check controller scope. Treat coefficient support, units, scaling, persistence, and effective behavior as controller-, firmware-, SDK-, and run-mode-specific. Recheck after any of those changes. A successful method call does not prove that requested values took effect or are safe.
  5. Read before writing and read back after writing. Preserve the original controller, mode, full P/I/D/F tuple, code/configuration identity, and read time as rollback. After one authorized write, read the tuple back in the same mode and record requested versus returned values. A missing, inconsistent, or unreliable read-back blocks coefficient trials.
  6. Keep an unknown baseline observation-only. If exact original read-back and provenance cannot be established, do not write coefficients, borrow another assembly's tuple, or infer a baseline. Graph target and measured velocity, error, readiness, and physical outcome only, labeled as analysis rather than tuning evidence.

For every powered test, use the game arena and the lesson's Supported or Travel test boundary. Secure the robot, battery, Hub, wires, attached pieces, mechanisms, support, and test artifact as applicable. Name a Driver Station operator and a separate Stop owner with immediate access and authority to press Stop without permission. State the prediction, setup, command, explicit zero or measured safe hold, Stop conditions, and evidence before power. Use robot live, clear, and stopped. Stop immediately for unexpected motion or output, loose hardware, unsafe vibration, implausible telemetry, loss of control, or inability to command zero. After completion or a stop trigger, press Stop, verify safe output and no motion, switch off the Hub, disconnect the battery, and only then touch, inspect, adjust, load, or reset the robot.
