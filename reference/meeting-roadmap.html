Trace, Evaluate, Rebuild meeting roadmap

Coordinate the exact 16-meeting sequence with readiness gates, source and evidence ownership, robot access, and honest fallback work. A fallback preserves learning and records blockers; it never converts missing hardware or an unperformed test into a pass.

Practice now, build as we go

We start with last season’s fully assembled REV and goBILDA StarterBots. Each keeps its own program, configuration, and test records. We will build a BIOBUZZ competition robot with a required launcher while the practice robots support learning.

Meetings 4-13 reserve 35 minutes of each three-hour meeting for physical build work. Keep one powered station under the coach’s supervision. A practice pass does not qualify a different robot; repeat affected checks when moving to the new build.

Robot selection, build milestones, and transfer checklist

Source, decision, and measurement expectations

F (documented fact): name the exact source, revision or access date, and scope. Vendor examples apply only to their matching named assembly; current Competition Manual, Team Update, and Q&A control current game and event claims. D (team decision): record the selected behavior, criteria, or limit and why the evidence supports it. M (team measurement): record robot/configuration identity, procedure, trial ID, units, result, student, checker, and date. Unperformed measurements remain pending delivery evidence.

Readiness gates

  • Meeting 1 identity gate: identify the installed manufacturer and exact revision, active hardware configuration, Control Hub, Driver Station, and matching source path before treating any vendor assumption as applicable.
  • Meeting 2 motor gate: secure the robot on stable support in the game arena, clear every wheel, verify one exact saved name and motor at a time, and prove explicit zero and Stop. No floor travel occurs.
  • Meeting 3 source gate: compare both vendor programs but run only the checked-in program matching the installed robot. A Supported test must pass before any authorized Travel test.
  • Meetings 4-8 TeleOp gate: current game sources and the signed Meeting 3 trace must precede the control map; the drivetrain must pass Supported testing before Travel testing; each mechanism needs exact-part evidence, stable securement, measured limits, safe release, recovery, and Stop before integration. Autonomous work waits until required TeleOp behavior qualifies or is formally reclassified and disabled.
  • Meeting 10 measurement gate: encoder wiring, configured motor type, software direction, wheels, tires, axles, every gearing stage, and track-width references must be consistent and recorded before counts are converted to distance.
  • Meetings 11-12 Autonomous gate: each Meeting 10 action needs completed physical evidence before route composition. A launcher action additionally needs current rules, exact assembly/source match, powered-off geometry inspection, measured artifact and launcher inputs, a guarded method, explicit named zeros, and a passing Supported test before a Travel test.
  • Meeting 13 PIDF gate: record the exact motor, controller, run mode, target unit, code/configuration, load, battery criterion, and original read-back P/I/D/F tuple. If a reliable baseline is unavailable, graph and explain only; do not change coefficients.
  • Meetings 14-16 release gate: preserve exact qualified TeleOp, accepted Autonomous, launcher/PIDF, configuration, rollback, and evidence identities. Meetings 15 and 16 require the event robot, control system, realistic setup, recovery equipment, access credentials, and practiced role backups; missing items remain blocked.
