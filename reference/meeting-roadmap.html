Eight-week meeting roadmap

Use this matrix to coordinate programming with build, drive, test, and documentation work. A fallback is the backup activity used when hardware is unavailable; it preserves the learning goal but does not mean an unavailable or unsafe robot passed a physical test.

Robot readiness gates

A readiness gate is a condition the team must prove before the next kind of test. These gates keep a software lesson from depending on unsafe, loose, or inconsistent hardware.

  • Before Meeting 3: the left and right drive motors, wheels, battery, and wires that make up the drive system (the drivetrain) are secured and clear. Raised-wheel checks must pass before floor driving because the first gamepad commands may use the wrong direction.
  • Before Meetings 4 and 6: any moving mechanism is held in a stable test setup, has measured clear space and conservative limits, and has a named emergency-stop owner. The code cannot provide safe limits until the team has measured the real mechanism.
  • Before Meeting 10: wiring for the sensors that report motor rotation as counts (encoders), motor type, motor direction, wheels, tires, axles, and gearing are consistent and recorded. Otherwise the same code can produce different counts, so a distance calculation would not describe the assembled drivetrain.
  • Before Meeting 13: the exact sensor is installed, protected, listed in the saved hardware list on the Driver Station, and matched to its manufacturer documentation and official sample. This must happen before the team treats a reading as meaningful.
  • Before Meetings 15 and 16: the event robot, control system, tested event code, and recovery equipment are complete enough to rehearse the actual setup, match, and restore steps. Missing equipment must be marked blocked rather than treated as passed.

Integrated meeting matrix

Two three-hour meetings per week. Reliability takes priority over adding features.
Week / meeting What students will make the code do What must be ready on the robot What students will visibly test What the team will record Robot access required If the mechanism is late
Week 1 / M1: Robot Programs Are Instructions Open the project and find the team's Java-code folder (TeamCode). Build and install the app; press INIT to prepare the program, Start to run it, and Stop to end it. Point to the loop, the instructions repeated while active, and telemetry, the messages and values shown on the Driver Station. Inventory electronics, label ports, and establish a clear test area. Each pair changes one Driver Station message, sees the changed text after Start, and rehearses the spoken safety states. Exact build and installation results, notes showing what appeared after INIT, Start, and Stop, and a hardware inventory; use the setup/deploy guide. Mentor-prepared laptops plus configured Control Hub/Driver Station; powered motion is not required. Build locally and record the blocked target or installation step; use cards to trace what should happen at INIT, Start, and Stop without claiming the app was installed.
Week 1 / M2: Variables Make a Motor Move Connect one Java motor name to the same saved Driver Station name, change one power within a mentor-approved limit, and use the first build error's file and line. Blocks may briefly show the same idea before students return to Java. Java stays primary when most pairs can locate, change, build, and explain a similar motor task with light prompting. If that readiness gate fails, record Blocks as the first-event competition-critical fallback while optional Java continues away from event-critical code. Secure one drive motor in a stable test setup; verify its saved name, expected direction, and wire labels. Brief low-power motor test with Stop confirmed. Exact saved motor name, readiness evidence, and the recorded Java or Blocks competition-path decision. One securely held motor and Control Hub. Build prepared code changes; trace expected motor commands against the saved hardware-name table.
Week 2 / M3: Gamepad Input to Drivetrain Output Follow one gamepad value to the left and right motor commands. Inspect the Git diff, the exact added and removed lines, then make a commit, one saved set of tested changes. Gate: drivetrain ready, wired, retained, and safe for raised-wheel tests. Raised-wheel check, then low-speed floor driving in a clear lane. Robot test card and the first Git commit that saves tested robot behavior. Complete drivetrain required for floor tests. Trace joystick values through prepared code, build it, inspect the exact changed lines, and use written input and output values. Do not claim a floor test passed.
Week 2 / M4: Decisions and Driver Controls Write and test one true-or-false decision (a Boolean conditional) that selects slow drive power or a servo command. Gate: mechanism held in a stable test setup with its full travel clear, or use the drive-system slow-mode option. Run both true and false cases; gather driver feedback. Two-case test and control decision notes. Drive system for slow mode, or a servo secured in a stable test setup. Add slow mode to the current drive code, or show the true and false decisions as Driver Station values without moving hardware.
Week 3 / M5: Methods Give Actions Names Move repeated drive instructions into one named Java action without changing behavior. Bring in teammates' saved changes and inspect the history. Harden drivetrain wiring, battery retention, and service access. Run the same short test before and after moving the instructions; the visible robot behavior must stay the same. Reviewed list of exact changed lines and the before-and-after test result. Short drivetrain check after code review. Move instructions in a copy of known-working code, review each use of the named action and each value it receives, and mark the physical before-and-after check blocked.
Week 3 / M6: Mechanisms and Safety Rules Give safe limits clear names, keep commands inside the measured range, and add one check that blocks an unsafe mechanism action. Gate: mechanism held in a stable test setup; builders measure physical stops, areas where parts could collide, and load risks. Test without a game element, then under controlled load at conservative power. Table of measured safe limits, operating notes, and robot test card. Installed mechanism, or one secured separately, that passes the safety gate. Write named limits and test the condition that prevents an unsafe action by using telemetry or prepared example values; do not invent physical limits.
Week 4 / M7: Debugging With Evidence Diagnose prepared build, saved-hardware-name, gamepad-input, and motor-direction problems using exact messages and values. Inspect connectors, fasteners, battery state, and mechanism binding. Reproduce one known safe failure; display the input, the code's decision, and the output command; verify one smallest fix. Completed fault log. Useful for saved-hardware-name or wiring problems; not required for build and code-reading problems. Diagnose build errors, time-ordered app messages, prepared Driver Station values, and code that uses the wrong saved hardware name.
Week 4 / M8: Reliable TeleOp Checkpoint Combine tested features into one reliable driver-controlled program (TeleOp). Name the exact known-working commit used for comparison (the baseline). Complete basic drivetrain and core-mechanism reliability work. Pass the same complete TeleOp cycle three times; separate defects from requests. Known-working checklist, observed-problem list, and a Git tag, a fixed name attached to the exact tested commit. Competition robot with all hardware needed by the known-working TeleOp version. Establish and repeat the known-working result only for available parts of the robot; mark tests for absent mechanisms blocked, not passed.
Week 5 / M9: Autonomous Is a Sequence Build a low-speed sequence that runs without gamepad driving and stops after each written time or safety condition. Prepare a clear field area and a marked guide that places the robot at the same start each time. Measure one simple mobility action from the marked start. Action sequence, measurements, and tested commit. Working drivetrain and controlled floor area. Arrange and narrate action cards; implement and review stop conditions without claiming physical repeatability.
Week 5 / M10: Encoders Turn Motion Into Data Display encoder counts, use measured counts instead of elapsed time for one movement, and add a time limit that stops the attempt if the target is never reached. Gate: consistent encoder wiring, motor type, direction, wheel, axle, tire, and gearing setup. Collect repeated ticks/distance data and compare time-based versus encoder-based motion. Encoder wiring record and a table showing the distance actually measured for recorded encoder counts. Stable drivetrain with verified encoders. Use recorded encoder counts to calculate distance. Review the time limit and the check for whether a motor is still moving toward its target; do not choose final robot values.
Week 6 / M11: Compose and Tune Autonomous Actions Combine named actions for a program that runs without gamepad driving (autonomous), then change one value at a time using repeated results. Keep the starting guide fixed and correct loose or inconsistent hardware before changing code values. Run repeated trials from the same starting mark; keep a simpler tested autonomous program as the backup if the primary sequence becomes unreliable. Trial table, chosen code values, and preserved simpler backup version. Event drivetrain and realistic starting setup. Arrange named code actions and analyze earlier trial data; do not choose values for hypothetical hardware.
Week 6 / M12: State Without Freezing the Robot If needed, make one button press trigger once, or divide a mechanism action into named states, the mechanism's current steps, that let drive code keep running. Move through each named mechanism step by hand; check for collisions and verify the safe Stop response. Confirm controls respond through each transition, the change from one named step to the next. Diagram of each state and the transition arrows showing when it changes, plus the focused test result. Mechanism only if the event robot needs the pattern. Use cards and Driver Station messages to model each named step; defer physical integration or the optional behavior.
Week 7 / M13: Sensors and Small-Team Collaboration Display the sensor's unprocessed readings and have another student inspect the change. After separated useful data, the team may choose a measured decision boundary and bounded command, but telemetry-only, rejecting the sensor for this use, or remounting and recollecting are complete valid outcomes. Gate: sensor installed, protected, listed by its exact saved hardware name, and documented for the exact part. Collect readings at the distances, lighting, and field conditions the robot will encounter. Enable sensor-assisted behavior only if separated useful data justifies it. Unprocessed-reading table, peer-review notes, and one recorded disposition: telemetry-only, reject, remount/recollect, or optional supported boundary/command with its test card. Exact installed sensor for claims about readings, a decision boundary, or behavior. Read an exact matching sample and review captured readings. Keep the outcome telemetry-only or blocked; do not choose a final decision boundary.
Week 7 / M14: Reliability and Failure Recovery Set outputs to safe values when input is missing or invalid, display messages and values that locate failures, and practice restoring the exact tested Git version. Use the event inspection checklist in the work area and correct high-risk wiring or mechanical failures. Practice one known safe failure the team has rehearsed. Run Driver Station Self-Inspect, its built-in control-system check, record any warning, and repeat the original test after the fix. Event troubleshooting guide and fault logs. The event robot setup is preferred; selected build and app-message checks can run without motion. Practice diagnosing build messages, time-ordered app messages, saved hardware names, and code restoration; list physical recovery checks still blocked.
Week 8 / M15: Match Simulation and Event Readiness Sort observed defects into must-fix or defer, repeat every test affected by a fix, then stop adding features and record the exact tested event candidate for Meeting 16 release verification. Gate: event-ready robot with working control system, charged batteries, needed spares, and every inspection item checked. Complete at least three full simulations from the no-gamepad program into the driver-controlled program, rotating student roles. Run log; a fix-now or defer decision with a reason for each problem; the exact tested candidate and rollback identities; and a backup record. Complete event-ready robot and realistic match setup. Rehearse roles, setup, timing, defect sorting, and event-version steps; do not tag robot behavior that has not passed its physical test.
Week 8 / M16: Capstone Demo and Handoff Without mentor keyboard use, each student explains a code path and makes one telemetry-text change in an assigned isolated practice copy. Students then create a separate clean clone, select the exact tested full hash, build it, run the written readiness test when safe, diagnose one rehearsed problem, and complete the ordered tag/release proof. Gate: event-ready robot with laptops, cables, required accounts and passwords, spares, and a backup student for each role. Use the event system for one student-led readiness sequence with separate verify, INIT, run, Stop, shutdown, and evidence checks. Individual telemetry changes stay in disposable copies and are never deployed to the event robot. Individual explanation/change/build-or-incomplete records, practiced backup-role list, clean recovery proof, exact shared tag/release/archive proof or blocker, and keep/change/learn-next answers. Complete event system for the team readiness demonstration; personal telemetry/build evidence uses isolated copies. Create a fresh working copy and build it, explain the code, and diagnose at a table. Mark each blocked personal build/check and final installation item incomplete with an explicit owner/date; do not substitute event-candidate evidence.
