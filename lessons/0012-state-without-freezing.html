State Without Freezing the Robot

Make one button press change a remembered mechanism setting once. Add a timed sequence only if the real mechanism needs one, while keeping driving and Stop responsive.

What you will make the robot do

One press changes a mechanism setting exactly once, even if the button stays held. If the mechanism truly needs ordered steps, the smallest state-and-timer sequence advances without pausing the main control loop. Success means the drivetrain still responds and Stop still works while the mechanism action is in progress. If the robot needs neither behavior, keep TeleOp unchanged and prove the idea with cards.

Words you need today

Held button
A button that remains down across many control-loop updates.
Button edge
The one moment a button changes from not pressed to pressed, or from pressed to released. Today a press edge requests one change.
State
Information the program remembers, such as whether a mechanism is open or closed.
Transition
A change from one state to another after a named event or condition.
Responsive
Able to react promptly to new driver input and Driver Station Stop.
Blocking wait
Code that stays in one wait, sleep, or private loop so other control work cannot update.
Timer
A clock the program can reset and read on later loop updates without waiting beside it.

Before you touch the robot

  • Name the Driver Station operator, Stop owner, mechanism observer, driver, programmer, and recorder.
  • Press Stop, switch off the Hub, disconnect the battery, and release or safely support stored energy before touching or walking a mechanism.
  • Use only documented, team-tested outputs, positions, limits, and safe postures for the exact installed parts. Leave unknown values blank and block powered work.
  • Mark pinch, crush, shear, hard-stop, wire, field-contact, gravity, and changing-load hazards through the complete mechanism path.
  • Preserve the known-good TeleOp and the exact Meeting 11 autonomous fallback. Work in a separately identified candidate.
Press Stop for unexpected direction or output, control delay, repeated transition, collision approach, load shift, field entry, communication loss, loose hardware, battery or wire movement, binding, sound, heat, or odor. Verify drivetrain and mechanism output are safe and motion has stopped, say stopped, switch off, disconnect, and support stored energy before entry or contact.

Follow along: act out one press before coding

  1. Stand in a control loop: one student repeatedly shows the current button card, one holds the remembered-state card, one shows the commanded-output card, and one repeatedly shows a drive-input card. This makes repeated updates visible. Success: drive and output cards are checked on every round.
  2. Hold the button: show one press edge followed by several held-button rounds. Change the remembered state only on the edge. This prevents many changes from one press. Success: the output changes once and stays in its new setting.
  3. Press again: show release, then another press edge. This demonstrates a toggle: each new press changes between two remembered settings. Success: exactly one transition occurs per press.
  4. Present Stop unexpectedly: immediately replace drive and mechanism outputs with their documented stopped behavior. This models Stop priority. Success: no student finishes a planned transition after Stop.
  5. Ask whether more is needed: if two stable settings solve the real operator need, keep the edge toggle. Add named states and a timer only when the powered-off physical map proves ordered intermediate steps are required. Success: every extra state answers a physical need.

Read only the matching vendor example

REV path

In the current REV Starter Bot programming material, read only the named edge-button section containing crossWasPressed() or circleWasPressed(). It demonstrates one event per press. The complete vendor program is not a general state-machine template, and none of its names, outputs, positions, timing, or mechanism assumptions become team values.

goBILDA path

In the reviewed BioBuzzStarterbotTeleop.java, trace the continuously returning loop() and the velocity gate in launch(). They show that drive work can continue while a condition is checked. The complete file is not a general state-machine template, and its target, threshold, directions, outputs, and control settings belong only to that exact StarterBot.

Do not copy the edge sample's sleep. ConceptGamepadEdgeDetection pauses only so demonstration telemetry is easy to see. That pause is a blocking wait, not the nonblocking control pattern for this meeting.

Try it with your partner

Three pairs: one pair per station, rotating every 20 minutes. Two pairs: begin at Physical States and Edge Code, swap after 20 minutes, then complete Responsive Test together. Assign driver, mechanism control, Stop, and recorder; swap duties halfway. No powered motion occurs during rotations.

1. Physical states

  1. With power disconnected and stored energy safe, name the rest state and manually walk only the approved path.
  2. Place one card for each stable state and one arrow for each permitted transition.
  3. Record the button event, physical completion evidence, collision envelope, load change, wire movement, and safe output for each arrow.
  4. Mark an unknown completion condition as a blocker. Do not replace it with a guessed timer.

Success looks like: every code state and transition can point to an observed physical condition.

2. Edge code

  1. Read the pinned edge sample and mark its edge methods separately from its demonstration sleep.
  2. In the candidate, use the exact SDK edge method for the chosen button to toggle one remembered value.
  3. Keep drivetrain input/output, mechanism decision, telemetry, and safe output in the main loop that returns continuously.
  4. Build and inspect the diff for sleeps, private wait loops, and accidental held-button transitions.

Success looks like: one press changes state once, and no added code prevents the loop from returning.

3. Responsive test

  1. Write predictions for tap, hold, release, second tap, startup, blocked transitions, and Stop.
  2. Draw a bounded drive path that requires direction changes while the mechanism action is active.
  3. Name what drive command, mechanism state, and output telemetry will show.
  4. Write a separate trial in which the Stop owner presses Stop before the mechanism action finishes.

Success looks like: the card can prove both drive response and immediate stopped behavior, not only mechanism completion.

Test it safely: drive, mechanism, and Stop

  1. Choose the smallest candidate: use the edge toggle first. If ordered intermediate motion is physically required, add only the named states from the physical map. Reset a timer on state entry only when elapsed time is legitimate team-tested evidence; read it on later loop updates. Success: no sleep or wait-for-mechanism loop appears.
  2. Pass readiness: build, inspect the diff, check startup and Stop outputs, confirm exact configured hardware and tested values, and complete the mechanical/electrical inspection. Success: one edge gives one transition and every path reaches a documented safe output.
  3. Power up safely: with the Hub off connect the accepted battery; switch on; confirm Hub status and Driver Station connection; deploy the reviewed candidate; select its exact name; press INIT; verify identity, telemetry, safe startup state, and zero or documented safe-hold outputs. Success: the robot remains still until the bounded card requests motion.
  4. Run the response trial: call robot live, receive clear, press Start, drive the bounded path, request the mechanism action once, and continue changing drive input while it is active. Success: requested drive changes still appear promptly in telemetry and robot response, with one mechanism transition per edge.
  5. Run the Stop trial: in a separate announced run, press Driver Station Stop before mechanism completion. Success: drivetrain and mechanism outputs reach documented stopped behavior and all motion ceases without finishing the sequence.
  6. Return to safe contact: verify outputs and no motion, say stopped, switch off, disconnect, and support stored energy before inspection or reset. Record the exact state, input, output, drive response, and Stop result before changing anything. Success: every result is tied to one candidate and test row.

If the robot does not need state code

Complete the cards and individual explanation, then leave the known-good TeleOp unchanged. Use remaining powered time for Meeting 11 reliability. Preserve the exact fallback and the Meeting 11 selected baseline. If Meeting 11 left a one-variable changed candidate pending, freeze its marked start and setup, inspect its one-variable diff, pass readiness, and run a complete fresh five-row set; its earlier confirmation trial does not count toward these five rows. For every trial use the full Hub-off battery connection, Hub-on status/identity, INIT safe-output, live/clear, guarded action, Stop, safe-output/no-motion, stopped, Hub-off, and disconnect sequence. Keep every valid result and hand off its exact row IDs. Promote the changed candidate only if this complete set meets the declared threshold; otherwise retain the selected baseline/fallback. If 15 minutes cannot complete all five valid rows, leave the set incomplete and schedule a later session. Do not add unused state code, an artificial mechanism sequence, or an unrelated feature.

If the robot or mechanism is unavailable

This fallback proves edge and state reasoning, but not physical mechanism safety, drivetrain responsiveness, or Stop performance.

  1. Use students and cards to repeat startup, edge, hold, release, second press, every justified transition, drive updates, and an unpredictable Stop.
  2. Read the pinned edge sample. Label its edge API as useful and its demonstration sleep as blocking and not to be copied.
  3. Build a disabled telemetry-only toggle in a disposable copy. Add symbolic states only when the physical record already justifies them; invent no hardware values.
  4. Trace the continuously returning loop and Stop cleanup. Keep all physical outputs absent, safely symbolic, or disabled.
  5. Label the result card/code practice - physical response not tested. Assign an owner and date for mechanism inspection, drive-during-action, and mid-action Stop trials.
