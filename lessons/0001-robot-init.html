Today’s goal

Change a message in the robot program and see it on the Driver Station.

Start here

Telemetry means messages from the program. An OpMode is the program you select on the Driver Station.

  1. Choose one practice robot. Write down its name, season, active configuration, and the source file you will use.
  2. Open the prepared telemetry-only program. Find the message that appears before Start and the message that repeats after Start.
  3. Change PAIR_NAME to your pair’s name. Build, connect to the correct Hub, and deploy.
  4. Follow the safety checklist. Press INIT, check the waiting message, press Start, then press Stop.
  5. Swap roles. Each person explains which line changed and shows the message it produced.

Robot for today: Choose REV practice, goBILDA practice, or the ready BIOBUZZ build. Keep separate records for each. See the practice and build plan.

Build task: Label the two practice robots, photograph their wiring, and save a copy of each program and configuration.

Keep a short result: robot + code version; what we changed; expected result; observed result; next step. Use the detailed worksheet when the test calls for measurements.

Read the safety checklist before power. Open the detailed steps for code, test cases, and worksheets; the mentor helps choose the section needed next.

Before you touch the robot

  • Use a supported test in the game arena: secure the robot frame on stable support and keep every wheel clear of the support, floor, people, wires, and loose objects.
  • Name one routine Driver Station operator and a separate Stop owner. The operator handles ordinary controls. Position the Stop owner with immediate access to Driver Station Stop; the Stop owner may press it without permission.
  • With the Hub off and battery disconnected, secure the robot, battery, Hub, wires, attached pieces, and mechanisms. A second student checks the setup.
  • Inspect the prepared source and successful build evidence to confirm it has telemetry but no hardware lookup or actuator command.
  • Write the prediction: INIT shows the waiting and safe-output messages, Start shows the pair message, nothing moves, and Stop ends updates.
  • Before INIT, position both control roles, confirm Stop access, move everyone outside the marked exclusion area, have the operator say robot live, and have the observer check the arena and answer clear. INIT executes user code.
Stop first. Unexpected movement, looseness, unsafe vibration, implausible telemetry, loss of control or communication, inability to reach the declared safe output, heat, smoke, odor, or unusual sound means press Stop. Verify no motion, say stopped, switch off the Hub, and disconnect the battery before entry or contact.

What you will make the robot do

Your pair will change one telemetry message in the prepared program, deploy it to the identified Control Hub, see initialization and safe-output messages before Start, see your changed message during active execution, and use Stop to end the OpMode.

You will also identify the installed robot's manufacturer and exact revision, select only its matching vendor path, and record the active hardware configuration and every actual drivetrain motor for Meeting 2. Today's prepared program contains no actuator commands, so no mechanism should move.

Words you need today

Manufacturer and revision
The company and exact assembled StarterBot version named by its labels, build record, and matching current documentation. Similar appearance or brand alone does not prove a match.
Vendor path
The REV, goBILDA, or unmatched path selected only after the installed robot and exact revision are identified. An unmatched or unknown robot stays on the team-specific inventory path.
Control Hub
The robot-mounted computer that runs the Robot Controller app and connects software to configured devices.
Driver Station
The operator device used to view the Robot Controller connection, choose the active hardware configuration and OpMode, use INIT and Start, read telemetry, and press Stop.
Active configuration
The exact saved hardware-configuration name currently selected on the Driver Station. It connects saved device names to Hub ports and configured device types.
Device name
The exact case-sensitive name saved for one device in the active configuration. Record capital letters, spaces, and underscores exactly.
TeamCode
The project module for team programs. Today's exact source path is TeamCode/src/main/java/org/firstinspires/ftc/teamcode/BiobuzzTrainingOpMode.java.
OpMode
A robot program selected on the Driver Station. Today's prepared telemetry-only OpMode is BIOBUZZ Training.
Initialization
The setup work that runs after INIT and before Start. The prepared linear OpMode displays its waiting and safe-output telemetry in this stage.
Active execution
The repeated work after Start while opModeIsActive() remains true. Today's active work updates telemetry only.
Telemetry
Messages and values sent by the program for students to read on the Driver Station.
Explicit safe output
A visible declaration or command for the state that should not move hardware. Today the prepared code declares Output = 0 - no actuator commands; this declaration is not proof of a particular motor's zero response.
Stop
The Driver Station control that ends the OpMode. The routine operator handles ordinary controls. A separately named Stop owner stays positioned with immediate access to Driver Station Stop and may press it without permission.
Driver and navigator
The driver uses the keyboard or Driver Station. The navigator reads the step, checks the visible result, and records it. Swap when directed.

Follow along: identify, trace, and deploy

The driver performs each action. The navigator reads the step, states why it matters, and checks the visible evidence. Swap driver and navigator before changing the message.

  1. Identify the robot parts: read the manufacturer label on the motor and other parts. These practice robots are last season's REV and goBILDA StarterBots. Record the season and any modifications as well as the brand. Use each robot's own saved program and configuration. Success: the record names the evidence for the manufacturer or names the blocker, its owner, and the next check.
  2. Record the control-system identity: point to the Control Hub, Driver Station, and gamepad. On the Driver Station, copy the exact active configuration name and list each installed device name, configured type, Hub, and port. This connects the saved setup to physical hardware. Success: another student can trace each recorded device from the screen to its labeled connection or marks the mismatch blocked with an owner and next check.
  3. Open the prepared source: in Android Studio open the repository root, then TeamCode/src/main/java/org/firstinspires/ftc/teamcode/BiobuzzTrainingOpMode.java. This keeps team work out of the official FtcRobotController samples. Success: the project panel shows both modules and the file contains the three prepared telemetry messages.
  4. Trace the lifecycle: mark entry into runOpMode(), initialization telemetry, waitForStart(), the opModeIsActive() loop, active telemetry, and the end reached after Stop. Box the declared Output value and confirm there are no hardware lookups or actuator calls. Success: your arrows predict what appears before Start, after Start, and after Stop.
  5. Make one harmless change: replace PAIR_NAME with a short pair identifier. This gives your pair a recognizable result without adding motion. Success: the diff shows one telemetry string changed.
  6. Build and deploy to the robot: follow the steps outlined here to build the TeamCode run configuration and read the Build output. This catches source errors before deployment. After the supported-test check passes, connect the charged battery while the Hub is off, switch on the Hub, confirm its status and the Driver Station connection, connect the laptop, and choose the identified Hub target.Success: Android Studio reports a successful build, connects to Control Hub, and installation completes.
  7. Select and clear before INIT: choose BIOBUZZ Training. Position the routine operator and separate Stop owner so both have immediate Driver Station Stop access; the Stop owner may press it without permission. Move everyone outside the exclusion area, have the operator say robot live, and have the observer check the arena and answer clear. INIT executes user code, so this must happen first. Success: the arena is clear and Stop access is confirmed before INIT.
  8. INIT, then Start: the routine operator presses INIT and checks Initialized - waiting for Start plus Output: 0 - no actuator commands. If both messages appear and nothing moves, the operator presses Start and watches for 3-5 seconds without anyone entering the exclusion area. Success: telemetry shows the pair identifier, retains the no-actuator declaration, and nothing moves.
  9. Stop and make safe: the routine operator presses Stop at the planned boundary, or the Stop owner presses it immediately for any stop condition without asking permission. Verify telemetry updates end and no motion exists, say stopped, switch off the Hub, and disconnect the battery before contact. Success: the OpMode ends and the team records exactly what was observed, including any mismatch.

Try it with your partner

Three pairs: begin at one station each and rotate within the 65-minute block. Two pairs: begin at Robot identity and Program trace, then complete Deployment together while preserving separate pair predictions and results. Swap driver and navigator before keyboard or Driver Station work.

1. Robot identity

  1. Photograph or sketch the manufacturer label and revision evidence.
  2. Mark REV practice robot, goBILDA practice robot, or team-built BIOBUZZ robot; record season, modifications, and source match. For any mismatch or unknown, name its owner and next check.
  3. Copy the active configuration name exactly.
  4. Trace each saved device name and Hub/port to its physical label; record discrepancies instead of correcting them silently.

Success looks like: every identity came from a visible label, screen, build record, or exact source, and every unknown has a blocker, owner, and next check.

2. Program lifecycle

  1. Arrange cards: enter runOpMode(), initialize, wait, Start, repeat while active, Stop.
  2. Point from each card to the matching source line.
  3. Predict each telemetry message and when updates end.
  4. Confirm the source has no hardware lookup or actuator command and explain what its declared zero does and does not prove.

Success looks like: the cards match source order and the pair distinguishes a declared zero from a measured motor response.

3. Change and deployment

  1. Change only PAIR_NAME and inspect the diff.
  2. Build and save the exact result.
  3. Complete the supported-test and identity gates.
  4. Deploy, position both control roles, call robot live, confirm clear and Stop access, then use INIT, Start, and Stop and record the actual messages and no-motion observation.

Success looks like: one source change produces one recognizable telemetry change, or the record names the exact blocked step without claiming deployment.

Test it safely

Complete one robot test card per pair. Although today's program commands no motion, use the full powered-test ritual because configuration or deployed-code mistakes can make the actual state differ from the prediction.

  1. Prediction: write the exact INIT messages, pair message, declared output, no-motion result, and expected Stop result. Success: every visible result is stated before power.
  2. Setup: in the game arena, secure the robot on stable support with every wheel clear; secure battery, Hub, wires, pieces, and mechanisms; mark the exclusion area; name the routine operator and a separate Stop owner. Position both with immediate Driver Station Stop access; the Stop owner may press it without permission. Success: a second student signs the supported-test and Stop-access checks.
  3. Identity: compare robot revision, Hub target, active configuration, built source path, installed app, and selected OpMode with the record. Success: every identity agrees or deployment remains blocked.
  4. Clear before INIT: move everyone outside the exclusion area, have the operator say robot live, have the observer check the arena and answer clear, and reconfirm the Stop owner's access. INIT executes user code, so do not press it before this check. Success: live, clear, and Stop access are confirmed before INIT.
  5. Run: the routine operator presses INIT and verifies the waiting and no-actuator messages, then presses Start and observes for 3-5 seconds. At the planned boundary the operator presses Stop; for any stop condition the Stop owner may press it immediately without permission. Success: the expected pair message appears only after Start, no hardware moves, and updates end after Stop.
  6. Stop condition: press Stop immediately for any unexpected movement, looseness, vibration, implausible telemetry, communication loss, inability to reach the declared safe output, heat, smoke, odor, or unusual sound. Success: the Stop owner can act without asking permission.
  7. Evidence: record exact messages, times or sequence, deployment result, no-motion observation, Stop response, date, student, and checker. Success: the record states what happened rather than what should have happened.

Prepare the exact telemetry-only starter.
  1. Place it at TeamCode/src/main/java/org/firstinspires/ftc/teamcode/BiobuzzTrainingOpMode.java with @TeleOp(name="BIOBUZZ Training", group="Training").
  2. Retain @Disabled during preparation. We are purposely omitting hardware declarations, hardwareMap calls, actuator commands, gamepad reads, or robot-specific constants.
  3. Build the disabled copy first. Review it to confirm there are no hardware commands; it will not appear in the selectable OpMode list while disabled.
  4. Remove only @Disabled, rebuild, and deploy. In the supported test, prove lifecycle order, exact telemetry, no motion, and Stop before student use.
package org.firstinspires.ftc.teamcode;

import com.qualcomm.robotcore.eventloop.opmode.Disabled;
import com.qualcomm.robotcore.eventloop.opmode.LinearOpMode;
import com.qualcomm.robotcore.eventloop.opmode.TeleOp;

@TeleOp(name="BIOBUZZ Training", group="Training")
@Disabled
public class BiobuzzTrainingOpMode extends LinearOpMode {
    @Override
    public void runOpMode() {
        telemetry.addData("Status", "Initialized - waiting for Start");
        telemetry.addData("Output", "0 - no actuator commands");
        telemetry.update();

        waitForStart();

        while (opModeIsActive()) {
            telemetry.addData("Pair", "PAIR_NAME");
            telemetry.addData("Output", "0 - no actuator commands");
            telemetry.update();
            idle();
        }
    }
}
