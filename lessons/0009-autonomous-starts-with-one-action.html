Today’s goal

Make the robot perform one short drive action without a driver.

Start here

Autonomous runs without driver commands. A timeout ends an action that has taken too long.

  1. Use a robot with qualified drive controls. Choose a clear start and route with the mentor.
  2. Trace the prepared action: start, apply the tested command, check time and Stop, then command zero.
  3. After INIT, compare motor-mode telemetry with the selected robot’s records. Start only when the checks pass.
  4. Test on support first, then run from the marked start. Measure the travel and repeat from the same place.
  5. Keep the simplest working action. Explain why a time limit does not guarantee an exact distance.

Robot for today: Choose REV practice, goBILDA practice, or the ready BIOBUZZ build. Keep separate records for each. See the practice and build plan.

Build task: Make repeatable start marks and check the competition robot’s wheel and cable clearance. Transfer code only after rechecking the new robot.

Keep a short result: robot + code version; what we changed; expected result; observed result. Use the detailed worksheet when the test calls for measurements.

Before you touch the robot

  • Confirm Meeting 8 qualified safe initialization, drivetrain control, and Stop with no unresolved enabled safety-critical defect. If not, Autonomous physical testing is blocked.
  • Name one Driver Station operator and Stop owner. Also name the observer, field reset lead, programmer, and recorder.
  • Press Stop, switch off the Hub, and disconnect the battery before touching the robot, support, wheels, wires, battery, field marks, or test artifact.
  • Secure the frame, battery, Hub, wires, attached pieces, and mechanisms. Establish the arena exclusion area and keep everyone outside it while the robot is live.
  • Before each command, state the predicted direction, setup, command, stopping conditions, and evidence to record.
Press Stop for unexpected direction or movement, loose hardware, unsafe vibration, implausible telemetry, loss of control, field entry, or inability to command zero. Verify no motion, say stopped, switch off the Hub, verify it is off, and disconnect the battery before anyone enters or touches the setup.

What you will make the robot do

From a repeatable marked start, the qualified drivetrain will perform one team-tested, low-speed drive action after Start and then explicitly command zero. It will stop when time expires, the OpMode is no longer active, or the Stop owner ends the attempt.

This is the smallest Autonomous baseline, not a route. Preserve Meeting 8's qualified TeleOp known-good version unchanged while you create a separate Autonomous OpMode.

Words you need today

Autonomous
An OpMode that follows programmed instructions after Start without gamepad driving.
@Autonomous
The annotation that registers this class as an Autonomous OpMode on the Driver Station.
Active check
opModeIsActive(), the check that permits the action to continue only while the OpMode remains active.
Bounded stopping condition
A known limit that prevents an action from continuing forever. Today's normal bound is the team's recorded elapsed-time limit, also called a timeout.
Escape
An early way out. Driver Station Stop makes the active check false; the Stop owner uses it for an observer abort.
Explicit stop
A code statement that commands every drive motor to zero instead of assuming that leaving a loop stops the motors.
Telemetry
Named Driver Station evidence showing the action, elapsed time, commanded output, active state, and exit reason.
Motor run mode
A motor-controller setting that affects how the SDK uses a power command. This lesson reads the current mode; it does not choose or change one.
Expected normal run mode
The exact mode recorded for one drivetrain motor in the Meeting 2 motor map and corroborated by the initialization path in the qualified team code. Each motor needs its own source; a blank or contradiction means unknown.
Observed run mode
The value returned by that motor's getMode() during the reviewed zero-output check. It must match the expected normal run mode before the one action can start. Source M09-F04
Supported test
A powered test in the arena with the robot frame secure on stable support and every wheel clear of the support, floor, people, wires, and loose objects.
Travel test
A powered test in the arena from a marked start along a marked route to a marked stop while everyone stays outside the exclusion area.

Follow along: trace one guarded action

Copy pinned RobotAutoDriveByTime_Linear into TeamCode, give the copy a unique name, and keep it disabled while editing. The sample supplies a starting pattern, not your robot's hardware or motion values.

  1. Register Autonomous: replace the sample registration name with the team's unique name and use @Autonomous. Why: the Driver Station must distinguish this OpMode from TeleOp. Success: the source has one Autonomous registration and no TeleOp registration.
  2. Keep verified hardware facts only: replace every sample name and direction with the exact configuration names and proven directions from the qualified drivetrain. Remove every extra action. Why: a sample's assumptions do not identify the installed robot. Success: a side-by-side audit links each lookup and direction to Meeting 8 evidence.
  3. Retrieve every expected mode: for each mapped drivetrain motor, copy its expected normal run mode and row identity from the Meeting 2 motor map, then point to the qualified code version, file, line, or initialization path that supports the same value. If the map has no mode field or either source is absent or contradictory, write unknown - action blocked. Do not infer a value from the timed sample or another motor. Why: the qualified drivetrain state, not this lesson, owns normal drive behavior. Success: every motor has one agreeing map and qualified-code source, or the action remains blocked.
  4. Read without changing: command explicit zero, display every motor's getMode() value during INIT, and compare each observed value with its expected normal mode. Do not call a mode-changing method in this lesson. Why: telemetry checks the controller state actually present without replacing it. Success: all expected and observed modes match while output remains zero; any unknown or mismatched mode blocks Start and all nonzero output.
  5. Wait without moving: only after the mode gate passes, show ready-at-zero telemetry and call waitForStart(). Why: no action may begin before Start or with an unresolved mode. Success: INIT shows each motor's expected mode, observed mode, source, match result, zero output, and no wheel motion.
  6. Start one action: only if opModeIsActive() is true, reset elapsed time and command the recorded low drive output. Why: the action needs an active OpMode and a known time origin. Success: code review finds one nonzero drive command after Start.
  7. Continue only under both guards: update telemetry while opModeIsActive() is true and elapsed time remains below the team's bounded limit. Why: Stop is the escape and elapsed time is the normal bound. Success: making either guard false leaves the loop.
  8. Command explicit zero: immediately after the loop, command zero to every drive motor and report the exit reason and zero command. Why: a false condition ends a loop but is not itself a motor command. Success: every normal, timeout, or active-false path reaches the visible zero statements.

The one-action Java shape

This is a structural sketch, not buildable code: the team must map its motors and implement setDrivePower. It intentionally omits reusable numbers. Replace each named placeholder only with the team's linked evidence; otherwise keep the OpMode disabled.

@Autonomous(name = "TEAM_UNIQUE_NAME")
public class TeamOneActionAuto extends LinearOpMode {
    private final ElapsedTime runtime = new ElapsedTime();

    @Override
    public void runOpMode() {
        // Map exact qualified drivetrain names and directions.
        setDrivePower(0);
        boolean normalModesVerified = compareGetModeForEveryDriveMotor(
                MEETING_2_MAP_AND_QUALIFIED_CODE);
        telemetry.addData("normal modes verified", normalModesVerified);
        if (!normalModesVerified) {
            telemetry.addData("state", "blocked at zero");
            telemetry.update();
            return;
        }
        telemetry.addData("state", "ready at zero");
        telemetry.update();
        waitForStart();

        if (opModeIsActive()) {
            runtime.reset();
            setDrivePower(TEAM_TESTED_LOW_OUTPUT);
            while (opModeIsActive()
                    && runtime.seconds() < TEAM_BOUNDED_TIME) {
                telemetry.addData("action", "one drive action");
                telemetry.addData("elapsed", runtime.seconds());
                telemetry.addData("command", TEAM_TESTED_LOW_OUTPUT);
                telemetry.update();
            }
        }

        setDrivePower(0);
        telemetry.addData("command", 0);
        telemetry.addData("state", "stopped");
        telemetry.update();
    }
}

Read it aloud: zero first, retrieve each expected mode, read each observed mode, block on unknown or mismatch, wait for Start, check active, reset time, command one action, continue while active and before the bound, then command zero. This sketch's comparison helper stands for a team-owned per-motor check; it does not change any mode. Do not add a turn, mechanism, pause, or second drive action today.

Try it with your partner

Three pairs: one pair begins at each station and rotates every 15 minutes (45 minutes total). Two pairs: spend 15 minutes at Code Trace or Test Design, swap for 15 minutes, then complete Evidence Design together for the final 15 minutes. Swap code driver and navigator at every rotation. No powered motion occurs during stations.

1. Source and code trace

  1. Mark sample structure that is supported by M09-F01, M09-F02, and M09-F03.
  2. Cross out sample hardware names, directions, outputs, and times as team values.
  3. For every drive motor, locate the Meeting 2 motor-map mode entry and the matching qualified code file/line or initialization path. Mark a missing or contradictory source blocked.
  4. Trace registration, zero initialization, expected/observed mode comparison, blocked return, Start, active-and-time guards, telemetry, and explicit zero.

Success looks like: every retained line has a source, team decision, or pending measurement, and the action count is exactly one.

2. Supported-test design

  1. Choose stable support that secures the frame with every wheel clear.
  2. Write each motor's expected normal run mode, Meeting 2 row, qualified code source, planned getMode() label, and match criterion.
  3. Copy the candidate low output and short time only from existing signed evidence; otherwise mark each value blocked.
  4. Write the active-false, time-expired, observer-abort, and unexpected-behavior stop cases.

Success looks like: another pair can inspect the setup and identify command, bounds, Stop owner, expected motion, and evidence before power is connected.

3. Travel and evidence design

  1. Mark one repeatable frame position and heading, one straight route, one expected stop mark, and a larger safety boundary.
  2. Name the robot and floor references used to measure actual travel, including units.
  3. Write the powered-off reset and the criteria that invalidate a trial.
  4. Prepare three rows for setup identity, selected power/time, actual elapsed time and travel, exit reason, zero/Stop evidence, and validity.

Success looks like: the route has room for an early or late stop, and a different recorder could apply the same measurement method.

Test one action safely

A. Freeze the test identity

  1. Record the qualified drivetrain/configuration source, Autonomous source version, OpMode name, code identity, action-card revision, candidate output and time with evidence, battery acceptance, roles, and every stopping condition. For each drive motor, also record the Meeting 2 motor-map row, expected normal run mode, and qualified code file/line or initialization path.
  2. Build while the OpMode remains disabled. Inspect the diff and reject any extra action, borrowed hardware fact, unsupported value, mode-changing call, missing guard, or path that misses explicit zero. An absent Meeting 2 expected mode or qualified-code source blocks the action.
  3. With the Hub off and battery disconnected, inspect and secure the robot and either the supported-test setup or marked travel setup. Any setup change requires inspection again.

B. Prove the shape in a supported test

  1. Secure the robot on stable support in the arena with every wheel clear of support, floor, people, wires, and loose objects. Clear the exclusion area.
  2. Remove @Disabled only for the reviewed zero-output preflight after the code, expected-mode-source, and setup gates pass. With the Hub off, connect the accepted battery; switch on; verify Hub and Driver Station connection; deploy; select the exact OpMode and active configuration; press INIT.
  3. At INIT, confirm explicit zero and no motion. Read and record every motor's getMode() telemetry beside its expected mode, Meeting 2 row, and qualified code source. If any expected mode is unknown, either source conflicts, or any observed value differs, remain at zero, do not press Start, press Stop, shut down, and resolve the record. The lesson does not change a mode to force a match.
  4. Only after every per-motor mode row matches, the operator calls robot live; the observer checks the area and calls clear; the operator presses Start.
  5. Observe one brief command only. Compare every wheel direction with the prediction. Confirm elapsed telemetry updates and that time expiry reaches explicit zero.
  6. Repeat the supported check and press Driver Station Stop before time expires. Confirm the active check becomes false, execution leaves the loop, and explicit zero is reached. If the runtime ends before telemetry can display the final update, use source trace plus observed motion ending as separate evidence and record that telemetry limit honestly.
  7. Press Stop, verify zero command and no motion, say stopped, switch off, verify Hub off, and disconnect the battery before anyone approaches.

Supported-test gate: every expected mode has a Meeting 2 and qualified-code source, every zero-output getMode() readback matches, predicted wheel directions, active-false escape, elapsed-time bound, telemetry, explicit zero, Driver Station Stop, and complete shutdown all pass. Otherwise keep powered action and travel blocked.

C. Measure the travel test

  1. With power off and the battery disconnected, remove the support and place the robot at the marked start and heading. Verify the marked route, expected stop mark, larger safety boundary, exclusion area, reset path, and measurement references.
  2. Complete the same Hub-off, battery-connect, Hub-on, status, connection, select, INIT, identity, zero, per-motor expected/observed mode comparison, live, clear, and Start sequence used by the supported test. Any mode discrepancy blocks that trial before motion.
  3. Observe only the one action. The Stop owner presses Stop for any abort sign or before the robot can cross the safety boundary. Explicit zero must follow a normal time exit or active-false exit.
  4. Verify no motion, say stopped, switch off, verify Hub off, and disconnect the battery. Only then enter, measure actual elapsed time and travel, inspect the robot, and record the exit reason and Stop evidence.
  5. Restore the exact marked start while powered down and repeat until three valid trials use one unchanged code, configuration, robot, battery acceptance, surface, route, criterion, and measurement method. Keep valid failures. Any change invalidates comparison and restarts Trial 1.

One-action baseline gate: three valid trials remain inside the safety boundary, stop through a recorded guard or abort, reach explicit zero, and contain complete evidence. Passing this gate supports only this action and setup; it does not prove a route.
