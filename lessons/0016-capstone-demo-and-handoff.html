What you will make the team able to do

Every student independently explains one subsystem or workflow, personally makes and verifies one harmless small change in a disposable isolated copy, shows the visible proof, and proves one different backup role. The team restores the exact Meeting 15 candidate from a clean location on another prepared laptop without changing or risking the event candidate, builds it, completes controlled deployment or records the blocked equivalent, verifies the exact tested release/tag and archive, packs with two people able to perform each critical role, and leaves a prioritized post-event backlog.

Words you need today

Capstone
A short final demonstration in which each student explains, does, and shows one real part of the team's work.
Clean clone
A new working copy of the repository made in an empty location, separate from every existing team checkout.
Fetch tags
Ask Git to copy the shared repository's fixed tag names and their targets into the local clone without changing the files currently shown. The command form is git fetch origin --tags.
Check out
Make one working directory show the files from an exact tag or commit. For this recovery drill, students use a separate clone and select the approved full hash without editing it.
Tracked changes
Differences Git reports in files it already records. An empty git status --short result means Git sees no tracked or untracked workspace changes.
Full hash
The complete 40-character Git commit identifier, not an abbreviated ID. It identifies the exact saved code being checked.
Annotated event tag
A fixed Git name plus a message attached to one exact commit for the event release. Create it once; never move or reuse it.
Checksum
An optional calculated fingerprint for a saved file or archive. Matching checksums support file-identity checking; they do not prove the robot behavior passed.
Recovery drill
A rehearsal that proves students can restore the exact event version and its records after a laptop or working copy is unavailable.
Archive
An indexed collection of exact code, configuration, test, inspection, recovery, packing, and ownership records that another student can open and verify.
Backup role
A different event responsibility the student has actually practiced, not only a name beside a role.
Handoff owner
The named student responsible for receiving an item or task, checking it, and carrying it forward.
Backlog
A prioritized list of evidence-based work to keep, change, or learn next after the event; it does not modify the frozen release today.
Disposable isolated copy
A separate checkout or copied working folder used only for a harmless practice change, then discarded or returned to its recorded starting version without touching the event candidate.

Before you touch the robot or event version

  • Read the Meeting 15 candidate full hash, configuration, passing run IDs, rollback, current-source record, blockers, and freeze decision. A blocked candidate cannot become a release today.
  • Use a spare prepared laptop or new empty directory outside all existing checkouts for clean recovery. Use a separate disposable location for any rehearsed mystery problem.
  • Do not edit, reset, retag, overwrite, or diagnose inside the event candidate, known-good working copy, sole configuration copy, event Driver Station setup, or release archive.
  • Before robot contact, press Stop, verify zero commanded motion, say stopped, switch off the Hub, disconnect/isolate the battery, and release or support stored energy.
  • Before motion, connect the accepted battery only with the Hub off; switch on; confirm Hub/Driver Station status; verify exact hash/configuration; press INIT; verify safe outputs; then call robot live and clear.
Software recovery never justifies risking event hardware. Press Stop for unexpected motion, field entry, loose hardware, binding, communication loss, cable movement, repeated reset, abnormal sound, heat, swelling, smoke, or odor. Verify zero motion, say stopped, switch off, and disconnect before contact.

Follow along: explain, do, and show

  1. Explain: choose one actual subsystem or workflow and trace its starting input/state, decision, commanded output, physical or screen result, safe Stop/failure behavior, and exact file/configuration. Success: a peer can point to the same path.
  2. Do: in a mentor-approved disposable isolated copy, personally make one harmless small change, such as pair-specific telemetry text. Explain the exact diff, build it, and check the saved build output or telemetry-only result. Do not deploy uncertain disposable code to the event robot. Success: the observer identifies the student's change, explanation, build/check, and proof without taking the keyboard.
  3. Show and discard: locate the diff and saved output/file name, path, time, or checksum when available that proves the result. Then discard the disposable change or return that isolated copy to its recorded starting hash and verify the change is gone. Success: the practice evidence remains while the event candidate and clean recovered copy remain unchanged.
  4. Prove a backup role: perform or lead a tabletop/zero-motion version of a different event responsibility and state when to Stop, use rollback, ask current event authority, or call the mentor. Success: no critical role depends on one person.

Why the clean-clone drill matters: it proves the exact code can be restored on another prepared laptop. Because the drill occurs in a new isolated location, students can diagnose or discard that copy without changing or risking the protected event candidate.

Try every ownership lane with your partner

Three pairs: start one pair in each lane and rotate every 20 minutes. Two pairs: start in two lanes with one lane empty; all pairs and the empty place advance every 20 minutes. Every pair receives 20 minutes in all three lanes. Every student must lead at least one action, record a different student's action, and prove a backup role.

1. Event and backup explanation

  1. Use the current official-source cue card to explain setup, role call, current procedure, Stop, reset, and pit communication.
  2. Each student performs or leads one tightly bounded primary or backup action.
  3. Prepare the bounded final test with setup, expected behavior, Stop condition, and visible pass evidence.
  4. State the escalation boundary, rollback cue, and next handoff owner.

Show: explanation, performed backup action, runnable test, limitation, escalation boundary, and receiver.

2. Build and packing

  1. With power off/disconnected, inspect exact installed parts, fasteners, wiring paths, battery restraint, guards, service points, and containers.
  2. Use exact manufacturer documents to identify actual spares, fasteners, cables, and service instructions.
  3. Use current FIRST sources, not vendor pages, for inspection and legal equipment.
  4. Record the item, condition, source, container, gap, primary, backup, and return owner.

Show: one checkable packing row and one practiced backup action per student.

3. Individual code and evidence

  1. Each student opens the mentor-prepared isolated disposable copy assigned to that student and verifies its recorded starting full hash. This is not the later student-created clean clone.
  2. Each student personally changes only one mentor-approved telemetry text string and explains the exact diff.
  3. Each student starts and checks the cached TeamCode build, then records its result and saved output file/path/time or optional checksum.
  4. Each student discards the change or returns only that disposable copy to the starting hash, then verifies the telemetry change is gone.
  5. If cached dependencies, storage, or tools block the personal build/check, mark that student's proof incomplete and schedule an owner/date follow-up. Never substitute Meeting 15 or event-candidate evidence.

Show: each student's starting hash, telemetry-only diff, personal cached build/check or explicit incomplete status, discard proof, and follow-up when needed.

Test it safely: readiness and isolated recovery

Student-led final readiness demonstration

  1. Inspect: complete the current inspection and Self-Inspect. Success: no unresolved must-fix item remains.
  2. Verify identity: compare the installed full hash and configuration with Meeting 15. Success: every identity matches the tested candidate.
  3. Predict: state the bounded behavior and the expected Stop result. Success: the test card names visible pass and abort evidence.
  4. Prepare power: with the Hub off, connect the accepted battery, switch on, and confirm Hub and Driver Station status. Success: the expected control system reconnects.
  5. Select and INIT: select the exact OpMode/configuration, press INIT, and verify identity and safe outputs. Success: no motion starts before Start.
  6. Run: call robot live, receive clear, and perform only the bounded action. Success: observed behavior matches the written criterion or is recorded as a failure.
  7. Stop: press Stop and verify zero commanded motion and no physical motion. Say stopped. Success: Stop proof is visible and recorded.
  8. Shut down: switch off the Hub and disconnect the battery before contact. Success: the robot is safe to approach.
  9. Preserve evidence: record inspection, installed identity, behavior, Stop, student roles, shutdown, and result. Success: another student reconciles the row with the Meeting 15 candidate.

Clean-clone recovery on another prepared laptop

  1. Isolate: use a spare laptop or new empty directory outside every existing checkout. Record machine, path, operator, repository URL, and the full candidate hash recorded and approved in Meeting 15. Do not delete or repurpose the known-good copy.
  2. Create the clean clone: a student runs git clone <TEAM_REPOSITORY_URL> <NEW_EMPTY_DIRECTORY>. Text inside angle brackets is a placeholder that students replace with the team's recorded actual value; it is not a literal command value. Success: the new folder was created by the student during this drill, not prepared in advance.
  3. Fetch fixed tag names: inside the new clone, run git fetch origin --tags. Success: the command finishes without changing the checked-out files; a network/authentication failure is recorded as blocked.
  4. Check out the tested commit: run git switch --detach <TESTED_FULL_HASH> using the actual Meeting 15 full hash. Success: git rev-parse HEAD prints that exact 40-character hash before Android Studio opens.
  5. Verify clean files: run git status --short. Success: it prints nothing. Any output means the clone is not clean and blocks release proof until explained.
  6. Build without edits: record SDK/project/tool identity and build TeamCode. Do not edit to make recovery pass. Success: build output, time, machine, full hash, and saved output file name/path are recorded; an optional checksum may be added.
  7. Deploy without candidate risk: prefer spare hardware. If only the event robot exists, first prove exact hash, preserve installed/configuration identity and restore method, inspect, then deploy only the unchanged hash using the full safe power sequence. If any gate fails, stop at clean build and record controlled deployment as blocked.
  8. Verify the recovered OpModes: compare the displayed names with the Meeting 15 record before INIT. Success: names and configuration agree.
  9. Run the recovered bounded test: complete only the established low-risk behavior. Success: behavior matches the written criterion or is recorded as failed.
  10. Stop and shut down: press Stop, verify zero commanded motion and no motion, say stopped, switch off the Hub, and disconnect the battery before contact. Success: clone hash, clean state, build, configuration, deploy or explicit blocked equivalent, test, Stop, and shutdown records agree.

Each student's harmless disposable change evidence

  1. Use the assigned practice state: each student uses the mentor-prepared isolated disposable copy assigned before the meeting at the recorded starting full hash. These copies keep ownership work parallel; they do not replace the student-created clean clone above. Record the student, path, and starting hash. The clean recovered copy and event candidate remain untouched.
  2. Make and explain one small change: the student personally changes a mentor-approved harmless item, such as pair-specific telemetry text, and explains the diff. The mentor supervises scope and safety but does not type. Success: the diff contains only that student's intended harmless change.
  3. Build and check: the student starts and checks the cached build in the disposable copy and records the exact output or telemetry-only check. Do not deploy uncertain disposable code to the event robot. Success: the student's row names the build/check result and saved output/file identity. If infrastructure blocks the personal check, mark it incomplete and schedule an explicit follow-up; do not substitute event-candidate evidence.
  4. Discard and verify: discard the disposable folder or return only that isolated copy to its recorded starting hash; then verify the student's change is absent. Success: the row records discard/reset proof, while the clean recovered copy and event candidate still show the approved full hash and no changes.

Separate rehearsed recovery problem

Use only a harmless Meeting 14 problem in a disposable checkout, mock setup, spare device, or zero-motion rehearsal configuration. Record symptom/time/hash/configuration, test one explanation, change only disposable state, repeat the bounded check, discard that state safely, and re-verify the clean candidate hash. Never merge, tag, release, or deploy the practice fix to the event candidate. If the mentor reveals the cause or takes the keyboard, record Supported and rerun later.

Record the exact release, archive, and packing answers

A label does not make code tested. Create or verify the event tag/release only when it resolves to the exact Meeting 15 deployed-and-tested commit and today's required recovery/readiness proof passes.

Create or verify the release in this order

In the command examples below, text inside angle brackets is a placeholder. Replace it with the mentor-approved actual team value; never type the brackets or example format as though it were the team's value.

Twenty-minute boundary: this block completes only operations prepared before the meeting. If any step or archive input cannot finish inside the block, record release/archive incomplete, the exact blocked step or missing input, owner, and continuation date; then continue in that scheduled post-meeting session. Never claim completion or rush, omit, or weaken verification to fit the clock.

  1. Verify the exact tested identity: compare Meeting 15's approved full hash with git rev-parse HEAD, then reconcile its configuration, passing run IDs, rollback, inspection, today's readiness result, clean recovery build, and every release blocker. Success: all release-gate records identify the same full hash and no blocker remains.
  2. Fetch existing tags: run git fetch origin --tags. Success: the local clone has the current shared tag records. Record authentication or network failure as blocked.
  3. Check whether the approved actual tag exists: use the mentor-approved actual tag name and check for refs/tags/<ACTUAL_TAG_NAME>. If it exists, do not recreate, move, force, or reuse it. If it is absent, continue to the creation step.
  4. Verify an existing tag object: for an existing ref, run git cat-file -t "refs/tags/<ACTUAL_TAG_NAME>". Success: the only accepted output is tag; commit identifies a lightweight tag and blocks release.
  5. Resolve the existing tag's commit: separately run git rev-parse "refs/tags/<ACTUAL_TAG_NAME>^{}". Success: the complete output exactly equals the tested 40-character full hash.
  6. Create the annotated tag only if absent: after a mentor approves the actual tag name and message, run git tag -a <ACTUAL_TAG_NAME> <TESTED_FULL_HASH> -m "<ACTUAL_APPROVED_MESSAGE>". Never move, force, or reuse an existing event tag.
  7. Verify the newly created tag object: run git cat-file -t "refs/tags/<ACTUAL_TAG_NAME>". Success: the only accepted output is tag.
  8. Resolve the newly created tag's commit: separately run git rev-parse "refs/tags/<ACTUAL_TAG_NAME>^{}". Success: the complete output exactly equals the tested 40-character full hash.
  9. Push only that tag: run git push origin "refs/tags/<ACTUAL_TAG_NAME>". Do not push a branch or all tags as part of this step. Success: the shared repository accepts that one tag; otherwise record release sharing as blocked.
  10. Create the independent clone: a second student uses the mentor-prepared second empty parent/location and runs git clone --no-tags --no-checkout <TEAM_REPOSITORY_URL> <SECOND_NEW_EMPTY_DIRECTORY>. Success: the student creates this second clone during the block; it was not pre-created.
  11. Fetch only the actual tag: inside the second clone, run git fetch --no-tags origin "refs/tags/<ACTUAL_TAG_NAME>:refs/tags/<ACTUAL_TAG_NAME>". Success: the fetch names only the approved actual tag ref.
  12. Independently verify the tag object: in the second clone, run git cat-file -t "refs/tags/<ACTUAL_TAG_NAME>". Success: the only accepted output is tag.
  13. Independently resolve the tag's commit: separately run git rev-parse "refs/tags/<ACTUAL_TAG_NAME>^{}". Success: the complete output exactly equals the tested 40-character full hash.
  14. Follow the prepared named host checklist: use the mentor-written Repository-host release checklist: ______, which contains the team's exact approved UI path or authenticated CLI command. Create or locate the release attached to the actual tag without exposing secrets or relabeling a different build. Success: the checklist result, release tag, and displayed commit agree with the independently checked hash.
  15. Complete the staged archive index: fill the prepared template with the actual exact source/configuration identity, test and inspection record IDs, pit guide, role matrix, packing list, rollback, release location, and each approved primary/backup storage destination. Do not substitute example or intended locations. Success: every entry contains the saved item's exact identity and actual location.
  16. Save to the approved destinations: save the indexed items only to the prepared primary and backup destinations. Success: the student records the actual resulting locations; a planned destination is not proof of a saved item.
  17. Open or restore proof: a different student uses the index to download/open the release archive and restore or open one backup item. Record exact item identity, actual location, time, optional checksum, and what opened successfully. Success: proof demonstrates independent access to saved material, not merely that a link exists.
  18. Record the final state: if authentication, network, tag type/hash, creation/push, second clone/fetch, prepared host checklist, archive input/save, or restore proof fails or exceeds the block, mark release/archive incomplete with the exact blocked step or input, owner, and scheduled continuation date. Do not claim release completion. Success: the record says released only when every required step passes without skipped verification.

If the robot, network, account, or candidate is unavailable

  1. Robot unavailable: complete individual explanations, clean source/build, configuration comparison, captured-log diagnosis, tabletop setup, archive, packing, and backups. Mark inspection, deploy, motion, Stop, and physical test blocked with owners/dates.
  2. Network/account unavailable: use a previously verified local repository and immutable hash for practice. Do not claim a clean network clone, remote backup, pushed tag/release, or backup-owner access.
  3. Release/archive block expires or an input is missing: stop at the last fully verified step. Record release/archive incomplete, the exact blocked step or missing archive input, owner, and scheduled post-meeting continuation date. Never rush, skip a type/hash/access check, or report completion to fit 20 minutes.
  4. Candidate mismatch or Meeting 15 blocked: stop release work, preserve both identities, and schedule missing inspection/full simulations. Never tag the newest file merely because it builds.
  5. No safe deployment target: finish isolated clean build, compare exact hash/configuration with installed proof, record fresh deploy not rerun, and assign controlled deployment.
  6. Personal build/check infrastructure blocked: preserve the student's telemetry-only diff and starting hash, mark the personal check incomplete, and schedule the named student, machine/dependency fix, owner, and date. Meeting 15, clean-recovery, or event-candidate evidence cannot replace that student's proof.
  7. Student absent: record missing explain/do/show and backup proof; do not infer independence or leave a role with one owner.

Mentor preparation

  • Audit Meeting 15's exact candidate, three passing runs or blocked status, rollback, current authority, role proof, packing gaps, and deferred work. Do not release a blocked candidate.
  • Prepare the spare laptop and an empty parent location outside all existing checkouts for the student-created recovery clone. Separately prepare a second empty parent/location for the second student's independent release-verification clone. Do not pre-create either clone.
  • Prepare one isolated disposable copy per student at the recorded starting full hash. Cache and verify the required build dependencies in each copy so each student can start/check a bounded build within the 20-minute lane; do not pre-make the student's telemetry change.
  • Prepare a separate disposable recovery-problem location and the one harmless problem previously rehearsed in Meeting 14. Never alter the candidate, sole copies, event hardware/configuration, or tag.
  • Prefer spare hardware for deployment. If only the event robot exists, require exact-hash equality, preserved installed/configuration identity, restore plan, inspection, and the smallest established test.
  • Before the meeting, select and write the team's exact repository-host release procedure as a named checklist, including the exact approved UI path or authenticated CLI command for that host. Verify each assigned student's access without displaying, copying, or recording secrets; do not assume GitHub CLI or any other host/tool.
  • Pre-stage an empty archive index/template naming every required input field and prepare the approved primary and backup storage destinations. Do not prefill identities, locations, results, checksums, access proof, or restore proof that students must observe.
  • Verify non-secret access to the prepared archive destinations and schedule a post-meeting continuation owner/date in case the bounded release/archive operations cannot finish. Recheck current FIRST event/inspection sources and exact installed-hardware service documentation.
