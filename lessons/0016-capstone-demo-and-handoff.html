Words you need today

Input
A gamepad value, sensor value, saved state, or other value that begins a code path.
Autonomous request
A planned robot action started by the Autonomous program rather than a driver's live control.
Method
A named group of instructions that receives a request and performs one understandable job.
Guard
A condition that permits, limits, redirects, or stops an action before an output is commanded.
Output
The final command sent to a motor, servo, telemetry display, or other device.
Telemetry
Values and messages the program sends to the Driver Station so students can compare requests, decisions, and commands.
Stop
The Driver Station action that ends the running OpMode. Today's proof includes the expected zero-output or measured safe-hold result.
Full hash
The complete Git commit identifier recorded for the exact tested files.
Event tag
The protected Git name recorded for the event version. It must resolve to the approved full hash.
Clean location
A new empty directory or prepared spare laptop location outside every existing working copy.
Clean clone
A new repository copy created in a clean location from the team's recorded repository address.
Harmless change
One isolated telemetry-text edit that cannot command or alter robot motion.
Supported test
A powered test in the game arena with the robot frame secure on stable support and every wheel clear of the support, floor, people, wires, and loose objects.
Readiness test
The team's previously passed, bounded Supported test used to confirm the restored event version without adding behavior.
Mystery fault
One harmless problem taught and safely rehearsed earlier, presented without revealing its cause.
Evidence
A saved command result, build result, test row, fault row, log, telemetry record, or direct observation tied to a student and exact identity.
Archive
The indexed set of exact source, configuration, test, recovery, role, and equipment records another student can open.
Credential owner
The named person responsible for account access and recovery. Records name the owner and access check, never a password, token, recovery code, or secret.
Pending physical check
A robot or equipment result that has not been performed and must remain marked incomplete with an owner and date.
Backup role
A second responsibility a student has actually practiced, not only one assigned on paper.

What you will prove today

Every student traces one gamepad input or Autonomous request through method, guard, output, telemetry, and Stop; makes one isolated harmless change; then independently prepares, builds, deploys, completes one assigned readiness-test OR previously taught mystery-fault diagnosis track, and preserves its evidence. The team assigns at least one student to each track so both appear in the final handoff. The mentor never uses the keyboard or controls to complete student work. The team also restores the protected event version in a clean location, verifies its exact full hash and event tag, and hands every critical item and responsibility to a primary and practiced backup.

Before any powered work

Team choice M16-D01 Measure it M16-M01
  • Use only the game arena and the Supported test setup. Secure the robot frame, battery, Hub, wires, attached pieces, mechanisms, support, and test artifact. Mark an exclusion area and keep everyone outside it while the robot is live.
  • Name one student as Driver Station operator and a different student as Stop owner. The Stop owner has immediate access to Stop and may press it without permission. Swap these roles before the other student demonstrates.
  • Before power, write the exact full hash/tag, active configuration, OpMode, prediction, command, explicit zero-output or measured safe-hold result, Stop condition, and evidence to save.
  • Before contact, press Stop, verify no motion, say stopped, switch the Hub off, disconnect and isolate the battery, and release or support stored energy.
  • For power-up, connect an accepted battery only while the Hub is off; switch on; confirm Hub and Driver Station status; select the exact configuration and OpMode; press INIT; verify identity, telemetry, and safe output; call robot live; receive clear; then Start.
  • After the bounded action, press Stop, verify the expected output and no motion, say stopped, switch the Hub off, and disconnect the battery before contact or reset.
Stop immediately for unexpected movement, support movement, loose hardware, unsafe vibration, binding, wire movement, implausible telemetry, loss of control, inability to command zero or the safe hold, repeated reset, abnormal sound, heat, swelling, smoke, or odor. Preserve the evidence. Do not touch, adjust, or retry until Stop is confirmed, the Hub is off, and the battery is disconnected. Change only one diagnostic variable before an identical retest.

Prepare every student in parallel

All pairs work at the same time for 30 minutes without robot power. In each pair, Student A owns the keyboard for minutes 0-14 while Student B prepares the exact identity, test, fault, equipment, and handoff evidence; use minutes 14-16 to verify the reset and swap; Student B owns the keyboard for minutes 16-30 while Student A completes the remaining preparation. The mentor may ask neutral evidence questions but does not type, dictate the next action, or finish a record.

Keyboard doer: trace, change, reset, build

  1. Each student independently restores or opens the assigned known-good clean location and records its path. Verify its event tag, full hash, and clean status against the team identity before editing. Record Pass / Blocked; a shared prior restore does not substitute for this student's proof.
  2. Choose one actual gamepad input or Autonomous request.
  3. Point to its method, each guard, final output, telemetry, and Stop/cleanup path. Explain what happens when the request is absent, rejected, or interrupted.
  4. In the assigned disposable isolated copy, verify the starting full hash and change one telemetry text string only.
  5. Inspect and explain the diff; build it; save the result; discard the change; verify the starting hash and clean state; then start and record the unchanged build needed for the later deployment. Never deploy the changed copy.

Each student gets one 14-minute keyboard turn and records restore/open location, exact identity match, clean status, evidence/result, every trace point, isolated path, exact diff, changed build, clean reset, and unchanged build. Mentor or partner keyboard work does not count.

Partner preparation: equipment and ownership

  1. Inspect the actual robot, Driver Station, controllers, accepted batteries, chargers, laptops, cables, tools, exact spares, containers, and printed records.
  2. For each installed part, use only its exact identified assembly or product document for service and spare information. Record a missing identity as a pending physical check.
  3. Name the actual location, condition, primary owner, practiced backup, return owner, and evidence.
  4. Verify repository, release, archive, and event-information access. Record only owner, recovery owner, access result, and check time; never record secrets.

Partner preparation: assigned track and evidence

  1. Copy the repository address, event tag, tested full hash, SDK/tool identity, configuration, OpModes, readiness-test ID, rollback, and archive location from the approved records.
  2. Prepare one new empty location per active pair and confirm it is outside every existing working copy.
  3. Each student chooses one assigned track: the known readiness Supported test or one mystery fault taught and rehearsed earlier. Record the choice before the robot appointment. Across the team, assign at least one student to each track.
  4. For readiness, prepare that student's test card. For diagnosis, prepare that student's fault-log row and disposable fault instance without revealing the cause. Assign Driver Station operator, independent Stop owner, observer, and recorder for any powered action.

Another pair can follow the records without hidden values, remembered steps, or access to a secret.

Every student's complete workflow

Team choice M16-D02 Measure it M16-M01

The 90-minute block gives each pair one robot workflow appointment and two parallel evidence/archive appointments. In the robot appointment, Student A completes the assigned track during minutes 0-14, minutes 14-16 are a safe reset and written handoff, and Student B completes the assigned track during minutes 16-30. Each student chooses and completes one track, not both. Students remain active during all three appointments. The mentor may stop unsafe work and ask neutral evidence questions, but may not type, touch controls to finish a step, dictate the next action, reveal a mystery-fault cause, or complete an explanation. A takeover records Supported, not Independent, and requires a later rerun.

If the robot, network, account, or student is unavailable

  • No robot or safe deployment target: complete trace, isolated harmless change, clean restoration, exact identity, build, captured-log diagnosis, equipment, archive, and handoff work. Mark deploy, readiness test, Stop response, and every physical result pending with the named student and date.
  • No network: use the documented clean-location recovery from a previously verified source archive. Record that a fresh network clone and remote tag check remain pending.
  • No account access: record the credential owner, recovery owner, failed access check, and follow-up. Never share or write a secret.
  • Identity mismatch or build failure: stop before deployment. Preserve both identities and the first error; diagnose from evidence without editing the protected candidate.
  • Student absent or mentor takeover: mark that student's complete workflow and backup proof incomplete. Do not infer independence from pair or team success.

Mentor preparation

  • Audit Meeting 15's approved tag/full hash, configuration, OpModes, passing evidence, rollback, current-source checks, blockers, and role matrix. A blocked candidate remains blocked.
  • Prepare one empty recovery location per active pair and one disposable isolated copy per student at a recorded starting hash. Cache required build dependencies, but do not make the student's change or pre-create a claimed clean clone.
  • Prepare the game-arena Supported test: stable support, clear wheels and mechanisms, exclusion area, accepted battery, secured hardware, written readiness criterion, immediate Stop access, and evidence forms.
  • Prepare one harmless mystery fault previously taught and rehearsed. Use separate disposable software/configuration state, a mock setup, or captured logs. Do not disturb the protected candidate or create electrical, mechanical, thermal, motion, account, or equipment risk.
  • Verify current FTC build, install, run, troubleshooting, inspection, and event resources; the SDK v12.0 project; exact installed-part documents; and the team's reviewed Git restore checklist.
  • Prepare the equipment/archive index and verify assigned access without viewing, copying, displaying, or recording secrets. Leave student evidence, results, identities, and locations blank.
