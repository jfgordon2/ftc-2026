Today’s goal

Run one drive motor at a time and learn which code controls each wheel.

Start here

A variable stores a value. setPower sends a motor command; setPower(0.0) commands zero.

  1. Open the mentor-prepared Meeting2OneMotor OpMode.
  2. Choose one motor row from the Meeting 1 artifact. Copy its exact Driver Station hardware name.
  3. Replace only REPLACE_WITH_DRIVER_STATION_NAME inside the quotation marks. Keep the quotation marks.
  4. Build the OpMode. Assign the controller as Driver/User 1. With the robot safely supported, press INIT and check the displayed motor mode before Start.
  5. Press Start. Hold gamepad 1's X button to run the motor at 0.25 power; release X to stop it. Record which wheel moves, its direction, and whether release stops it. Power down, then repeat with another motor name.

Before any motor can move

  • Work only in the game arena. Secure the robot frame on stable support and prove that every wheel clears the support, floor, people, wires, and loose objects through a full hand rotation.
  • Secure the battery, Control Hub, wires, attached pieces, and mechanisms. Keep all wires away from wheels, shafts, gears, sharp edges, and pinch points.
  • Switch off the Hub and disconnect the battery before touching wiring, wheels, motors, support, or the robot. Say stopped before anyone enters the exclusion area.
  • Name a routine Driver Station operator and a separate Stop owner. Both keep immediate access to Stop; the Stop owner may press it without permission.
  • Before INIT, identify the one motor selected for the trial, predict the moved side or wheel and observed direction, confirm the OpMode maps only that motor, and record the signed test card.
  • Stop immediately for unexpected movement, a second motor moving, loose hardware, unsafe vibration, rubbing, wire movement, implausible telemetry, loss of communication or control, inability to command zero, heat, smoke, odor, or unusual sound.
One motor, one trial. Never use floor travel here. After each trial, press Stop, switch off the Hub, disconnect the battery, and record the result before selecting another motor.

Detailed steps, code, and worksheets

What you will make the robot do

Every actual drivetrain motor will turn by itself in a Supported test, return to explicit zero, respond to Driver Station Stop, and gain its own checked row in the team's motor map.

You will copy one exact hardware name into a complete Java OpMode, trace how that name reaches one motor, repair the first compiler error, and complete a fresh task that helps choose the team's programming path.

Words you need today

Variable
A name used by the program to refer to a value or object. Here, testMotor refers to the configured motor.
Assignment
Putting a value or object into a variable with =.
Method call
An instruction asking an object to do an action. testMotor.setPower(0.25) calls the motor's setPower method.
Active configuration
The saved robot configuration currently selected on the Driver Station. Its Hub, port, motor type, and device name must describe the physical motor before Java uses that name.
Hardware map
The FTC connection between a configured device name and a Java object. The text in hardwareMap.get must exactly match the saved name.
Configured motor type
The motor type selected for that device in the active Robot Controller configuration. Record what the screen shows; do not infer it from appearance.
Placeholder
Temporary text that must be replaced. In this OpMode, replace REPLACE_WITH_DRIVER_STATION_NAME with one exact hardware name.
gamepad1
The FTC SDK object for the controller assigned as Driver/User 1. This OpMode can use it because Meeting2OneMotor extends LinearOpMode, which inherits gamepad1 from the SDK's OpMode class.
Hold control
An action that continues only while a button is held. Here, holding gamepad 1's X button runs the selected motor; releasing X commands zero.
Motor run mode
The setting that controls how the motor controller interprets commands. The read-only call motor.getMode() reports the current setting. Today you display and record the current mode; you do not switch modes.
Compiler error
A build message that identifies Java the compiler cannot accept. Begin with the first message, file, and line instead of guessing from later messages.
Explicit zero
A motor command that sends 0.0. The team must still observe whether output stops and whether Driver Station Stop ends the OpMode.
Supported test
A powered test in the game arena with the robot frame secure on stable support and every wheel clear of the support, floor, people, wires, and loose objects.
Light prompting
The mentor may repeat the fresh task or ask what evidence the pair will check, but does not point to the line, dictate the edit, or repair the code.
Blocks fallback
The mentor-prepared competition project for this exact installed robot, used if the observable Java readiness threshold is not met. It does not create a second set of hardware facts or acceptance tests.

Find the exact hardware name

  1. Start with Meeting 1: choose one completed motor row. Confirm the physical wheel, Hub, port, and saved hardware name describe the same motor.
  2. If the Meeting 1 name is missing or unclear: ask the mentor to open the active configuration on the Driver Station. Find the Control Hub, open Motors, and locate the correct numbered port. Read the device name shown on that row. Do not rename the device during this activity.
  3. Copy exactly: capitalization, spaces, numbers, and underscores all count. For example, left_drive and Left Drive are different names.
  4. Check with a partner: one student points to the Meeting 1 or Driver Station name while the other points to the text inside the Java quotation marks. Compare one character at a time before building.
  5. At INIT: read the current mode displayed in telemetry and record it in the selected motor's row. After each motor has been tested, compare the completed rows and resolve any unexplained mode difference before later drive tests.

In Java: make one student edit

  1. Open the prepared file: the mentor has already placed and checked Meeting2OneMotor.java in TeamCode.
  2. Find the only student-edit line: locate REPLACE_WITH_DRIVER_STATION_NAME in the hardwareMap.get call. Replace that text with the exact name from the chosen motor row. Keep the quotation marks.
  3. Find the lookup: point to hardwareMap.get. Explain that the text inside its quotation marks must match the Driver Station configuration.
  4. Trace the control: point to gamepad1.x, setPower(0.25), and the else branch containing setPower(0.0). Explain that the motor runs only while X is held.
  5. Build before power: build the clean copy and read the result. A successful build proves the Java syntax is accepted; it does not prove the name matches a configured motor or that the motor will move.
  6. Repair the first compiler error: build the prepared copy containing one missing semicolon. Record the first message, file, and line; add only the semicolon; rebuild. Why: the first diagnostic gives a bounded place to start. Success: the record preserves the original diagnostic and the repaired copy builds.

This is the complete mentor-prepared OpMode. Its structure follows the FTC SDK's basic LinearOpMode pattern, reduced to one motor so it works with either practice robot after the exact configured name is supplied. Students replace only the hardware-name placeholder.

package org.firstinspires.ftc.teamcode;

import com.qualcomm.robotcore.eventloop.opmode.LinearOpMode;
import com.qualcomm.robotcore.eventloop.opmode.TeleOp;
import com.qualcomm.robotcore.hardware.DcMotor;

@TeleOp(name = "M2 One Motor Test", group = "BIOBUZZ")
public class Meeting2OneMotor extends LinearOpMode {
    @Override
    public void runOpMode() throws InterruptedException {
        // STUDENT: Replace only the text inside these quotation marks.
        DcMotor testMotor = hardwareMap.get(
                DcMotor.class, "REPLACE_WITH_DRIVER_STATION_NAME");
        testMotor.setPower(0.0);

        telemetry.addData("Current mode", testMotor.getMode());
        telemetry.addLine("Ready. Check the supported robot before Start.");
        telemetry.update();

        waitForStart();

        while (opModeIsActive()) {
            // gamepad1 is inherited from the FTC SDK's OpMode class.
            if (gamepad1.x) {
                testMotor.setPower(0.25);
            } else {
                testMotor.setPower(0.0);
            }

            telemetry.addData("X held", gamepad1.x);
            telemetry.update();
        }

        testMotor.setPower(0.0);
    }
}

The file maps one motor and shows its current mode before Start. While the OpMode is active, holding gamepad 1's X button commands 0.25 power and releasing X commands 0.0. It does not set a direction or change a run mode. Record the observed direction instead of assuming one from a vendor example.

Build the evidence in three workstreams

Three pairs: begin at different workstreams and rotate. Two pairs: begin at Identity and Code, swap, then serve together as the test crew. Swap driver and navigator at each move. No pair may approve its own trial alone.

1. Identity and product source

  1. Count the actual drivetrain motors and compare the count with Meeting 1.
  2. For each motor, use the Meeting 1 artifact. If a name is missing or unclear, ask the mentor to open the active configuration and trace the physical motor to the actual Hub, numbered port, and saved name.
  3. Copy the exact case-sensitive name already shown in the active configuration. Do not rename a device during the one-motor test.
  4. Beside each motor's name, type, and Hub/port, record the current mode returned when the one-motor OpMode is initialized for that motor.
  5. Match the installed manufacturer/model/revision to its exact product page, or mark model-specific work blocked with an owner and next check.
  6. Prepare one blank motor-map row per actual motor and record each motor's trial.

Success looks like: motor count equals prepared rows, every identity is observed rather than inferred, and every source is exact or explicitly blocked.

2. Java and build evidence

  1. Open the mentor-installed Meeting2OneMotor OpMode. Replace only the quoted placeholder in hardwareMap.get with one exact name from Meeting 1 or the active Driver Station configuration.
  2. Compare the quoted Java name with the source one character at a time, then build. At INIT, record the selected motor's current mode.
  3. Confirm the OpMode maps only the selected motor, begins at explicit zero, commands 0.25 only while gamepad 1's X button is held, and commands zero when X is released.
  4. Build the clean copy, then record and repair the first compiler error in the seeded-error copy.
  5. Record the exact Java lookup. Predict and observe direction; this introductory OpMode does not set direction in code.

Success looks like: clean code builds, the first diagnostic is preserved, and no second drivetrain motor can receive nonzero output in the selected trial.

3. Supported test and observation

  1. Inspect the support, all-wheel clearance, secured hardware, wire route, exclusion area, operator, Stop owner, and signed test card.
  2. Write the predicted moved side or wheel and direction before INIT.
  3. Observe the selected motor's movement, explicit-zero result, and Stop response without entering the exclusion area.
  4. Press Stop, power down, disconnect, and obtain the student's and independent checker's names before the next motor.

Success looks like: one and only one selected motor moves, it returns to zero, Stop ends the OpMode, and the complete trial is signed before selection changes.

Run one Supported test for every motor

  1. Select one motor: mark one untested motor row and trial. The one-motor OpMode must map only that motor. Why: one-at-a-time selection isolates the code-to-hardware connection. Success: two students agree on the location, Hub/port, saved name, Java lookup, configured type, and student-edit line.
  2. Inspect while unpowered: with the Hub off and battery disconnected, secure the frame, support, battery, Hub, wires, attached pieces, and mechanisms; hand-rotate every wheel to prove clearance. Why: no wheel may contact the support or surroundings. Success: the independent checker signs the setup.
  3. Approve the trial: the mentor checks the robot, supported setup, Driver/User 1 controller assignment, and the sample's hold-X-to-run control, then signs the test card. Why: the test must match the robot and setup being used. Success: the controller assignment, button, power, release behavior, and Stop owner are clear before power is connected.
  4. Verify the name before INIT: compare the chosen Meeting 1 or Driver Station name with the quoted text in hardwareMap.get, one character at a time. After INIT, compare the current-mode telemetry with the chosen motor row. Why: the Java lookup can find only an exact configured name. Success: the configuration, Hub/port, configured type, and quoted name agree.
  5. Predict and build: write the expected moved side or wheel and direction from a named viewing side. Confirm the OpMode maps only that motor, sets it to zero before waitForStart(), commands 0.25 while X is held, and commands zero when X is released; then build successfully. Why: a written prediction and explicit release behavior make mismatches visible. Success: the prediction, code check, and successful build are recorded before power is connected.
  6. Clear before INIT: position the routine operator and separate Stop owner with immediate Stop access. Move everyone outside the exclusion area; the operator calls robot live, and the observer checks the arena and answers clear. Why: the complete powered setup must be safe before the program begins. Success: live, clear, and Stop access are confirmed before INIT.
  7. INIT, inspect, then Start: the operator presses INIT and confirms no motion. Read the selected motor's current mode in telemetry. If the OpMode is missing from the list or INIT reports that the device cannot be found, press Stop and recheck the active configuration and quoted name; do not guess a new name. After the checks pass, press Start, hold X briefly, then release it. Observe only from outside the exclusion area. Why: the trial must show both the held command and its release state. Success: only the selected side or wheel moves while X is held and it stops when X is released.
  8. Stop and make safe: the operator presses Stop at the planned boundary, or the Stop owner presses it immediately for any stop condition without permission. Say stopped, switch off the Hub, and disconnect the battery. Why: contact is allowed only after power is removed. Success: Stop ends the OpMode and the team records its observed response.
  9. Record before repeating: complete and sign every field in that motor's row. If any result is blocked or unexpected, name the owner and next check; do not retest or select another motor until the setup is safe. Why: each row must describe its own evidence. Success: completed rows equal the actual motor count, with one trial per motor.

The team passes this activity only when every actual drivetrain motor has its own completed one-at-a-time Supported test row. A result from one motor never proves another motor's lookup, direction, zero, or Stop response.

If powered robot work is unavailable

Do not claim a motor lookup, movement, direction, explicit-zero result, or Stop response passed. Hardware unavailability alone does not activate the Blocks fallback.

  1. Reconcile Meeting 1's motor count, physical labels, saved names, configured types, and product sources wherever those records are directly available. Mark every unchecked fact blocked with an owner and next check.
  2. Trace and build the disabled Java task. Repair the seeded semicolon error and preserve its first message, file, and line. A local build proves syntax only, not deployment or motion.
  3. On paper, predict the selected motor, direction, X-held response, X-release response, and Stop evidence. Keep physical results marked blocked until the robot is available.
  4. Assign a date, owner, unique trial, student, and checker for every missing Supported test before Meeting 3 uses the motor map.

Success looks like: available source and build evidence is complete, every physical result remains visibly blocked, and no unavailable test is represented as passing.
