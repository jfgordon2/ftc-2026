Today’s goal

Run one drive motor at a time and learn which code controls each wheel.

Start here

A variable stores a value. setPower sends a motor command; setPower(0.0) commands zero.

  1. Use the selected practice robot’s motor map. Match a wheel to its motor, Hub port, and exact configured name.
  2. In the mentor-prepared test, find the motor lookup, the approved power, the time limit, and the zero-power command.
  3. Build the test. With the robot safely supported, press INIT. Read the motor modes now; resolve mismatches before Start.
  4. Press Start for the approved short test. Check which wheel moves, its direction, and that it stops. Power down before changing the setup.
  5. Repeat for the other drive motors. Swap roles and repair the prepared missing-semicolon example.

Robot for today: Choose REV practice, goBILDA practice, or the ready BIOBUZZ build. Keep separate records for each. See the practice and build plan.

Build task: Inspect drive wheels, fasteners, battery retention, and cable clearance. Update the map for each practice robot separately.

Keep a short result: robot + code version; what we changed; expected result; observed result; next step. Use the detailed worksheet when the test calls for measurements.

Read the safety checklist before power. Open the detailed steps for code, test cases, and worksheets; the mentor helps choose the section needed next.

Before any motor can move

  • Work only in the game arena. Secure the robot frame on stable support and prove that every wheel clears the support, floor, people, wires, and loose objects through a full hand rotation.
  • Secure the battery, Control Hub, wires, attached pieces, and mechanisms. Keep all wires away from wheels, shafts, gears, sharp edges, and pinch points.
  • Switch off the Hub and disconnect the battery before touching wiring, wheels, motors, support, or the robot. Say stopped before anyone enters the exclusion area.
  • Name a routine Driver Station operator and a separate Stop owner. Both keep immediate access to Stop; the Stop owner may press it without permission.
  • Before INIT, identify the one motor selected for the trial, predict the moved side or wheel and observed direction, confirm every other motor is commanded to explicit zero, and record the signed test-card ID.
  • Stop immediately for unexpected movement, a second motor moving, loose hardware, unsafe vibration, rubbing, wire movement, implausible telemetry, loss of communication or control, inability to command zero, heat, smoke, odor, or unusual sound.
One motor, one trial. Never use floor travel here. After each trial, press Stop, switch off the Hub, disconnect the battery, and record the result before selecting another motor.

What you will make the robot do

Every actual drivetrain motor will turn by itself in a Supported test, return to explicit zero, respond to Driver Station Stop, and gain its own checked row in the team's motor map.

You will trace a Java double, assignment, method call, and hardwareMap lookup; repair the first compiler error; then complete a fresh task that decides whether Java or the prepared Blocks project is the competition path.

Words you need today

Variable
A named place that holds a value. In double testPower = approvedTestPower;, testPower is the variable and double is its Java type.
Assignment
Putting a value into a variable with =.
Method call
An instruction asking an object to do an action. testMotor.setPower(testPower) calls the motor's setPower method.
Active configuration
The saved robot configuration currently selected on the Driver Station. Its Hub, port, motor type, and device name must describe the physical motor before Java uses that name.
Hardware map
The FTC connection between a configured device name and a Java object. The text in hardwareMap.get must exactly match the saved name.
Configured motor type
The motor type selected for that device in the active Robot Controller configuration. Record what the screen shows; do not infer it from appearance.
Direction setting
The software choice FORWARD or REVERSE used for that motor. It is separate from the direction students observe at a named wheel or side.
Motor run mode
The setting that controls how the motor controller interprets commands. The read-only call motor.getMode() reports the current setting. Today you display and record that expected normal mode; you do not switch modes.
Compiler error
A build message that identifies Java the compiler cannot accept. Begin with the first message, file, and line instead of guessing from later messages.
Explicit zero
A motor command that sends 0.0. The team must still observe whether output stops and whether Driver Station Stop ends the OpMode.
Finally cleanup
A Java finally block that runs when control leaves its paired try block. The prepared test uses it to command every mapped drivetrain motor to zero after normal completion, Stop, return, or interruption.
Supported test
A powered test in the game arena with the robot frame secure on stable support and every wheel clear of the support, floor, people, wires, and loose objects.
Light prompting
The mentor may repeat the fresh task or ask what evidence the pair will check, but does not point to the line, dictate the edit, or repair the code.
Blocks fallback
The mentor-prepared competition project for this exact installed robot, used if the observable Java readiness threshold is not met. It does not create a second set of hardware facts or acceptance tests.

In Java: trace and build the prepared test

  1. Match identity: choose one row from the Meeting 1 handoff. Point to its physical location, labeled Hub/port, exact saved name, configured motor type, and exact-product source or blocker. Why: a correct Java statement can still select the wrong device. Success: the physical labels, active configuration, and handoff agree without guessing.
  2. Find the lookup: compare the saved name character by character with hardwareMap.get(DcMotor.class, "EXACT_SAVED_NAME"). Why: the Java lookup uses that exact configured name. Success: another student independently confirms the same match.
  3. Trace the value: point from approvedTestPower through the testPower assignment to setPower(testPower). Then point to setPower(0.0). Why: this separates the trial's command from its explicit zero. Success: you explain each line without substituting a reusable number.
  4. Trace direction: compare approvedDirection with the selected motor row's direction setting, then predict the side or wheel and direction that observers should see. Why: software direction and observed movement are different facts. Success: the prediction names a viewing side and remains written even if the result differs.
  5. Build before power: build the disabled clean copy and read the result. Why: a successful build is required before deployment but does not prove hardware behavior. Success: the clean copy builds with the selected motor name unchanged.
  6. Repair the first compiler error: build the prepared copy containing one missing semicolon. Record the first message, file, and line; add only the semicolon; rebuild. Why: the first diagnostic gives a bounded place to start. Success: the record preserves the original diagnostic and the repaired copy builds.

The mentor prepares one exact name and direction entry for every actual drivetrain motor, the selected row index, and the trial-specific values only after verifying the exact installed motors, robot revision, source guidance, and stable setup. Values belong on the signed test card and trial record; this lesson supplies no reusable power or duration. The method below is placed inside the prepared LinearOpMode and called with those mentor-reviewed arrays and values.

private void runOneMotorTest(
        String[] exactDriveMotorNames,
        DcMotor.Direction[] approvedDirections,
        int approvedSelectedMotorIndex,
        double approvedTestPower,
        long approvedTestDurationMs) throws InterruptedException {
    if (exactDriveMotorNames.length != approvedDirections.length
            || approvedSelectedMotorIndex < 0
            || approvedSelectedMotorIndex >= exactDriveMotorNames.length) {
        throw new IllegalArgumentException("Incomplete drivetrain test setup");
    }

    DcMotor[] driveMotors = new DcMotor[exactDriveMotorNames.length];
    for (int i = 0; i < driveMotors.length; i++) {
        driveMotors[i] = hardwareMap.get(
                DcMotor.class, exactDriveMotorNames[i]);
        driveMotors[i].setDirection(approvedDirections[i]);
        driveMotors[i].setPower(0.0);
        telemetry.addData(
                exactDriveMotorNames[i] + " expected normal mode",
                driveMotors[i].getMode());
    }
    telemetry.update();

    DcMotor selectedMotor = driveMotors[approvedSelectedMotorIndex];
    try {
        waitForStart();
        if (opModeIsActive()) {
            selectedMotor.setPower(approvedTestPower);
            sleep(approvedTestDurationMs);
            selectedMotor.setPower(0.0);
        }
    } finally {
        for (DcMotor motor : driveMotors) {
            motor.setPower(0.0);
        }
    }
}

Before enabling the prepared file, count the name and direction entries against the motor map. The setup loop must map every actual drivetrain motor, command every one to zero, and display every getMode() result before waitForStart(). Compare the returned modes across all motor rows; an unexplained mismatch blocks Start. During the bounded test only selectedMotor receives the approved test power. Normal completion and every exit through finally command all mapped motors to zero. Do not call setMode() or teach mode switching in Meeting 2.

Build the evidence in three workstreams

Three pairs: begin at different workstreams and rotate. Two pairs: begin at Identity and Code, swap, then serve together as the test crew. Swap driver and navigator at each move. No pair may approve its own trial alone.

1. Identity and product source

  1. Count the actual drivetrain motors and compare the count with Meeting 1.
  2. For each motor, open the active configuration and trace physical location to the actual Hub, numbered port, and exact saved name.
  3. Create or edit that port's device only as needed; choose the exact configured motor type, assign the exact case-sensitive descriptive name, save, activate, and record the Driver Station evidence.
  4. Beside each motor's name, type, Hub/port, and direction, record the expected normal mode returned by the prepared file's read-only getMode() display.
  5. Match the installed manufacturer/model/revision to its exact product page, or mark model-specific work blocked with an owner and next check.
  6. Prepare one blank motor-map row per actual motor and assign each a unique trial ID.

Success looks like: motor count equals prepared rows, every identity is observed rather than inferred, and every source is exact or explicitly blocked.

2. Java and build evidence

  1. Prepare one disabled test selection at a time; compare its lookup string side by side with the active Driver Station motor row and record the Java evidence.
  2. Display getMode() for every mapped drivetrain motor before waitForStart(). Compare all returned modes and block Start on any unexplained mismatch.
  3. Confirm all drivetrain motors begin at explicit zero and only the selected motor can receive the signed card's trial-specific command.
  4. Build the clean copy, then record and repair the first compiler error in the seeded-error copy.
  5. Record the exact Java lookup and direction setting in the selected motor row.

Success looks like: clean code builds, the first diagnostic is preserved, and no second drivetrain motor can receive nonzero output in the selected trial.

3. Supported test and observation

  1. Inspect the support, all-wheel clearance, secured hardware, wire route, exclusion area, operator, Stop owner, and signed test card.
  2. Write the predicted moved side or wheel and direction before INIT.
  3. Observe the selected motor's movement, explicit-zero result, and Stop response without entering the exclusion area.
  4. Press Stop, power down, disconnect, and obtain the student's and independent checker's names before the next motor.

Success looks like: one and only one selected motor moves, it returns to zero, Stop ends the OpMode, and the complete trial is signed before selection changes.

Run one Supported test for every motor

  1. Select one motor: mark one untested motor row and trial ID. Keep all other drivetrain outputs at explicit zero. Why: one-at-a-time selection isolates the code-to-hardware connection. Why: no wheel may contact the support or surroundings. Success: the independent checker signs the setup.
  3. Approve the trial: the mentor checks the exact product source and setup, chooses trial-specific power and duration, and signs the test card. Record its ID, values with units, source, and approver in the trial evidence; do not reuse them for another motor or setup without approval. Why: the lesson cannot supply universal motor values.   4. Verify configuration and Java before INIT: compare the active Driver Station configuration and selected motor row with the Java lookup. After the clear-area check and INIT below, compare the live pre-start telemetry. Compare configuration name, actual Hub/port, configured motor type, exact case-sensitive name, Java direction setting, and the expected normal mode returned by getMode(); record Driver Station and Java evidence with student and checker. Compare the mode with every other motor row. Why: saved configuration, source, and controller state must describe the intended drivetrain. Success: every identity field agrees and no unexplained run-mode mismatch remains before Start.
  5. Predict and build: write the expected moved side or wheel and direction from a named viewing side. Confirm the prepared method maps every drivetrain motor, zeros each one before waitForStart(), commands only the selected motor, and zeros all motors in finally; then build successfully. Why: a written prediction and executable cleanup make mismatches and exit behavior visible. Success: the prediction, all-motor count, cleanup review, and successful build are recorded before power is connected.
  6. Clear before INIT: position the routine operator and separate Stop owner with immediate Stop access. Move everyone outside the exclusion area; the operator calls robot live, and the observer checks the arena and answers clear. Why: the complete powered setup must be safe before the program begins. Success: live, clear, and Stop access are confirmed before INIT.
  7. INIT, inspect, then Start: the operator presses INIT and confirms no motion. Read every motor's getMode() telemetry now. Record and resolve any unexplained mismatch; press Stop if a check fails. Only after these checks pass, press Start. Observe only from outside the exclusion area. The selected motor receives the trial-specific command and then explicit zero. Why: the trial must show both output and its planned safe state. Success: only the selected side or wheel moves and it stops at the explicit-zero command.
  8. Stop and make safe: the operator presses Stop at the planned boundary, or the Stop owner presses it immediately for any stop condition without permission. Say stopped, switch off the Hub, and disconnect the battery. Why: contact is allowed only after power is removed. Success: Stop ends the OpMode and the team records its observed response.
  9. Record before repeating: complete and sign every field in that motor's row. If any result is blocked or unexpected, name the owner and next check; do not retest or select another motor until the setup is safe. Why: each row must describe its own evidence. Success: completed rows equal the actual motor count, with one unique trial per motor.

The team passes this activity only when every actual drivetrain motor has its own completed one-at-a-time Supported test row. A result from one motor never proves another motor's lookup, direction, zero, or Stop response.

If powered robot work is unavailable

Do not claim a motor lookup, movement, direction, explicit-zero result, or Stop response passed. Hardware unavailability alone does not activate the Blocks fallback.

  1. Reconcile Meeting 1's motor count, physical labels, saved names, configured types, and product sources wherever those records are directly available. Mark every unchecked fact blocked with an owner and next check.
  2. Trace and build the disabled Java task. Repair the seeded semicolon error and preserve its first message, file, and line. A local build proves syntax only, not deployment or motion.
  3. On paper, predict the selected motor, direction, explicit zero, and Stop evidence for each planned trial. Do not enter power or duration until the mentor approves the exact setup and source.
  4. Assign a date, owner, unique trial ID, student, and checker for every missing Supported test before Meeting 3 uses the motor map.

Success looks like: available source and build evidence is complete, every physical result remains visibly blocked, and no unavailable test is represented as passing.
