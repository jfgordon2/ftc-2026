Integrate and Debug TeleOp

Integrated means the separately tested drivetrain and mechanism code paths are combined in one reviewed version. Coexist means those paths work alone and together without stealing inputs, retaining stale commands, or defeating safe release and Stop. A candidate is the exact reviewed code version ready for the next recorded test; it is not yet qualified or known-good.

Combine the tested drivetrain and enabled mechanism controls, prove that they coexist, and use evidence to isolate one cause before changing one thing.

What you will make the robot do

The integrated TeleOp candidate will preserve the tested drivetrain and every enabled Meeting 6 mechanism action while controls are used alone and together. The team will test neutral, drivetrain, mechanism, simultaneous input, release, reverse or recovery, and Stop, then close any fault only from an evidence trail and the repeated original test.

Integration does not authorize a new action, value, hardware name, vendor assumption, or wider physical range. Begin with the recoverable drivetrain candidate and the separate mechanism candidate. Keep every pending, failed, unmatched, optional, or unavailable feature disabled.

Words you need today

Integration
Combining separately tested code paths into one candidate and checking whether they still behave correctly together.
Coexistence
Drivetrain and mechanism controls operate alone and simultaneously without stealing inputs, hiding decisions, retaining stale commands, or defeating safe release and Stop.
Symptom
The exact observed mismatch between the written expectation and the actual message, telemetry, command, sound, or movement.
Layer
One place where a cause may live: Build, Configuration, Wiring, Input, Code, or Mechanical.
Hypothesis
One possible cause that predicts what evidence should appear and what result would reject it.
Instrumentation
Bounded evidence added to reveal what happened without changing the intended control decision, such as input, decision or state, and commanded-output telemetry.
Cause
The explanation supported by the collected evidence and the result of repeating the original test after one change.
Integrated candidate
The exact reviewed code version that contains both accepted paths and is ready for the next recorded test. It is not yet a qualified baseline.

Before you integrate or test

  • Work only in the game arena. Start with a Supported test: secure the robot on stable support with every wheel clear of the support, floor, people, wires, and loose objects.
  • Name the Driver Station operator, mechanism operator when separate, observer, recorder, and independent Stop owner. The Stop owner has immediate access and does not wait for permission.
  • Press Stop, verify no motion, switch off the Hub, and disconnect the battery before inspection, code deployment, configuration work, physical contact, or reset.
  • Preserve the Meeting 5 drivetrain limit and the Meeting 6 enabled-feature scope, safe releases, measured holds, conflict rules, and tested load stage. Do not invent or widen a value during integration.
  • Write the exact case, expected telemetry and behavior, abort signs, and safe outputs before power. Run one bounded case at a time.
  • Use only a mentor-prepared, known-safe simulated fault in a disposable copy. Never unplug live wiring, partly seat a connector, loosen a structure, bypass an interlock, reverse polarity, create a bind or stall, or manufacture unsafe motion.
Stop first. Unexpected movement, lost control, missing zero or safe hold, collision, binding, stall, looseness, heat, odor, unusual sound, implausible telemetry, communication loss, or field entry means press Stop. Verify no motion, say stopped, switch off the Hub, and disconnect the battery before contact. Preserve the symptom; do not try another input.

Integrate without erasing what already passed

  1. Lock both inputs: record the exact drivetrain and mechanism versions, active configuration, matching vendor path and lifecycle, tested actions, safe outputs, test IDs, and open blockers. Success: each executable behavior points to upstream evidence; incomplete behavior is disabled.
  2. Map shared resources: compare gamepad fields, hardware fields, helper names, constants, lifecycle methods, telemetry captions, and output writes. Mark collisions before copying code. Success: the map says which path owns each input, decision, state, and output.
  3. Preserve one matching lifecycle: add the team-owned drive and mechanism calls to the installed robot's existing REV linear or goBILDA iterative path. Do not combine lifecycles or copy the unmatched vendor branch. Success: initialization, active loop, no-request behavior, and explicit shutdown remain traceable.
  4. Merge one path at a time: start from a recoverable copy, add the reviewed mechanism call path to the tested drivetrain candidate, build, and inspect the complete diff before adding anything else. Success: the diff contains only the intended integration and diagnostic telemetry.
  5. Command every output once per loop: calculate drivetrain and mechanism commands from fresh inputs and decisions, then make final writes. No inactive branch inherits a prior moving output. Success: neutral, release, blocked conflict, and recovery select explicit zero or a verified safe hold.
  6. Trace the interaction: add concise input, decision or state, and commanded-output telemetry for both paths. Use distinct captions and include any interlock or conflict result. Success: a reader can distinguish operator request, code choice, and command without guessing from motion.

Non-compilable pseudocode: this shape-only snippet intentionally uses undefined placeholders, including turnInput, recoveryInput, interlockClear, DriveDecision, MechanismState, decideDrive, and decideMechanism. Do not paste or deploy it; substitute only the team's approved names and already-tested values.

// NON-COMPILABLE PSEUDOCODE: undefined placeholders show structure only.
double driveInput = gamepad1.left_stick_y;
boolean mechanismInput = gamepad2.right_bumper;

DriveDecision driveDecision = decideDrive(driveInput, turnInput);
MechanismState mechanismState = decideMechanism(
        mechanismInput, recoveryInput, interlockClear);

double leftCommand = driveDecision.leftCommand;
double rightCommand = driveDecision.rightCommand;
double mechanismCommand = mechanismState.command; // zero or verified safe hold by default

telemetry.addData("Drive input", driveInput);
telemetry.addData("Drive decision", driveDecision.name);
telemetry.addData("Drive commands", "%.2f / %.2f", leftCommand, rightCommand);
telemetry.addData("Mechanism input", mechanismInput);
telemetry.addData("Mechanism state", mechanismState.name);
telemetry.addData("Mechanism command", mechanismCommand);
telemetry.update();

// Write each final command through the exact mapped output once.

Why this matters: separate code can pass alone but fail after sharing inputs, names, state, loop time, or defaults. A visible ownership map and fresh final commands expose those interactions without weakening the earlier safety contract.

Debug from evidence before edits

Start with the shared troubleshooting ladder: Build, install, OpMode visibility, first team-code file and line, input/decision/output telemetry, then logs. FTC Docs documents common user-code and configuration failures and how to view Robot Controller logs. Preserve the first useful message and nearby context before restarting.

Source M07-F01

Use the same five-part loop for every fault

  1. Observe: run the written bounded case once. Record exact setup, configuration, code version, controls, expectation, symptom, and first relevant message or values before changing anything. Success: the symptom states what happened, not a guessed cause.
  2. Hypothesize: choose one layer: Build, Configuration, Wiring, Input, Code, or Mechanical. Write one possible cause, its predicted evidence, and a result that would reject it. Success: the hypothesis can be wrong.
  3. Instrument: collect only evidence that separates that hypothesis from alternatives. For behavior faults, show the relevant input, decision or state, and commanded output; also record observed output or motion separately. For messages, preserve the exact text, first team-code file and line, and relevant log context. Success: instrumentation does not alter the intended command or physical scope.
  4. Test: run the smallest safe check at the established boundary. Compare actual evidence with the prediction. If supported, make exactly one cause-related change while stopped, switched off, and disconnected, then build and inspect the diff. Success: the record names that one change; rejected hypotheses remain evidence, not failures to hide.
  5. Conclude: repeat the original test with the same setup and boundary. Name a cause only when the before evidence, one change, and actual retest support it. Otherwise leave the fault open and write a new hypothesis before another check. Success: another pair can reproduce the complete trail.

Integrate with your partner

Three pairs: begin at Interface Audit, Telemetry Trace, and Test/Fault Record; rotate every 20 minutes, then reconcile one candidate. Two pairs: begin at Interface Audit and Telemetry Trace, swap stations after 20 minutes, then jointly complete Test/Fault Record. Within every pair, the code driver controls the keyboard and makes only the agreed change; the code navigator reads the requirement, traces both paths, checks each edit against the evidence and safety boundary, and records questions and results. Swap code driver and code navigator after the first reviewed path or after 15 minutes, whichever comes first, so every student serves in both roles at least once. Pair copies keep all hardware writes disabled until the shared diff passes review.

1. Interface audit

  1. Record both candidate identities and list each enabled action and exact output.
  2. Compare lifecycle, initialization, loop call sites, fields, methods, constants, inputs, and output writes.
  3. Mark duplicate names, gamepad conflicts, stale state, missing defaults, and unmatched vendor assumptions.
  4. Draft the smallest integration diff and identify its rollback copy.

Success looks like: every shared resource has one owner and every output retains its tested release and Stop path.

2. Telemetry trace

  1. Choose one drive input and one mechanism input that can be requested together.
  2. Predict each input value, decision or state, final command, and safe result on release.
  3. Run fixed neutral, drive-only, mechanism-only, simultaneous, release, recovery, and simulated Stop cases without hardware writes.
  4. Record mismatches as symptoms. Do not edit while gathering the first trace.

Success looks like: actual telemetry matches each written trace or supplies an exact fault symptom.

3. Test and fault record

  1. Write the Supported test setup, case order, expected behavior, safe output, abort signs, roles, and evidence.
  2. Receive one mentor-prepared, known-safe simulated software or configuration fault in a disposable copy and follow its mentor-set test boundary. Students must never prepare, seed, or create the simulated fault; outputs remain disabled or physically bounded exactly as the mentor key requires.
  3. Complete symptom, layer, hypothesis, prediction, input, decision/state, command, observed result, and rejection fields before editing.
  4. Plan one correction, the identical retest, restoration, and handoff if the fault remains open.

Success looks like: another pair can run the test without selecting a value, widening scope, or guessing what evidence to keep.

Test the integrated controls together

  1. Review the candidate: build, inspect the complete diff, and compare it with both handoffs. Confirm the exact configuration, matching lifecycle, approved controls, limits, enabled actions, safe releases, recovery, output ownership, and telemetry. Success: no unrelated, pending, or unmatched behavior is executable.
  2. Prepare the Supported test: with Hub off and battery disconnected, secure the robot in the game arena, clear every wheel and mechanism, remove load unless its prior test requires it, mark the exclusion area, and assign control and Stop ownership. Success: a second student signs setup, abort signs, and immediate Stop access.
  3. Power and prove neutral: connect the accepted battery while the Hub is off, switch on, confirm status and connection, assign gamepads, select the exact OpMode, call robot live, receive clear, then INIT and Start with all inputs released. Success: input, decision/state, and output telemetry show neutral defaults; every output is zero or its verified safe hold.
  4. Run each path alone: run one bounded drivetrain case and release, then one enabled mechanism case and release. Return to neutral between them. Success: each path matches its upstream evidence and the inactive path remains at its safe output.
  5. Run simultaneous input: apply the written drivetrain and mechanism requests together, including any approved cross-system conflict or interlock case. Do not add load or travel. Success: both input traces, decisions/states, commands, and observed behaviors match predictions without a hidden conflict.
  6. Prove release and reverse or recovery: release one request while holding the other, then release both. Run only the approved reverse or recovery case and return to neutral. Success: no stale drive or mechanism command survives release, and recovery does not bypass its limits or conflict rule.
  7. Prove Stop: during the written bounded simultaneous case, the independent Stop owner presses Stop. Verify no motion, say stopped, switch off the Hub, and disconnect the battery. Success: actual drivetrain and mechanism Stop behavior matches the upstream verified safe outputs; record observation rather than inferring it from code.
  8. Handle every mismatch: preserve the failed row and enter the evidence loop. Make no edit until symptom, layer, hypothesis, prediction, and needed instrumentation are written. After one justified change, repeat the exact failed case plus neutral, release, and Stop cases affected by that change. Success: the record closes from evidence or stays honestly open.
  9. Decide integrated scope: name the exact candidate, configuration, enabled actions, passed cases, open faults, and highest physical scope. Any unresolved safety fault blocks Meeting 8 powered qualification. Success: code, test record, and handoff describe the same scope.

If the robot, one candidate, or logs are unavailable

Do not report an integrated physical pass, physical direction, coexistence, release, recovery, or Stop result that was not observed.

  1. Record the missing robot, candidate identity, configuration, log access, upstream evidence, or test setup. Assign an owner and next check date.
  2. Use recoverable copies of the latest verified drivetrain and mechanism candidates. Disable every hardware write and every feature whose upstream evidence is missing.
  3. Complete the interface audit, integrate the matching lifecycle, build, inspect the diff, and run fixed neutral, drive-only, mechanism-only, simultaneous, release, recovery, and simulated Stop traces.
  4. For each trace, record input, decision or state, commanded output, and expected safe output. Label the result code-path evidence only - not robot tested.
  5. If live logs are unavailable, use a saved exact Build message, Robot Controller log excerpt, configuration capture, or telemetry trace. Predict what the next artifact should show before revealing it.
  6. Prepare the complete Supported test and fault records for later use, including physical prerequisites, exact cases, abort signs, owner, and date. Meeting 8 remains physically blocked.

Success looks like: the integrated code path and diagnosis reasoning are reviewable within their stated scope, while every unperformed physical conclusion remains visibly blocked.

Mentor preparation

  • Audit Meeting 5's tested drivetrain candidate and Meeting 6's mechanism handoff. Prepare exact recoverable copies and one clean integration copy; do not repair missing upstream evidence during setup.
  • Confirm the exact installed robot, matching vendor path and lifecycle, active configuration, enabled actions, limits, holds, safe releases, conflict/recovery rules, and highest tested physical scope.
  • Prepare pair copies with all hardware writes disabled, a complete interface-audit prompt, telemetry cases, Supported test fixture, exclusion marking, accepted battery, cards, and immediate Stop access.
  • Seed only known-safe faults in disposable copies: a harmless compiler typo; an inactive exact-name mismatch that stops at INIT with outputs disabled; a wrong gamepad field with outputs disabled; a stale-command logic branch exercised telemetry-only; or a bounded wrong decision whose hardware writes remain disabled. Record the seed, expected evidence, restoration, and maximum test boundary in a mentor key.
  • Do not seed live wiring, loose or partial connectors, reversed polarity, weakened structure, removed restraints, blocked mechanisms, hard-stop contact, stalls, unsafe directions, widened values, or any fault requiring students to approach a live robot.
  • Rehearse Android Studio Build output, Driver Station log viewing, Robot Controller logs, and Logcat access. Prepare saved exact captures in case the live path is unavailable.
Edit gate: allow no source, configuration, wiring, or physical change until the pair records trial identity, exact symptom and reproduction, one layer, one rejectable hypothesis, predicted evidence, instrumentation, and safe test. Allow one cause-related change, then require the original test and every affected neutral/release/recovery/Stop case.
