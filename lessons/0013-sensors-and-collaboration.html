What you will make the robot do

The Driver Station will show labeled raw readings from one exact installed sensor under named realistic conditions. The team will either stop with trustworthy telemetry, which is a complete success, or use the evidence to propose one bounded behavior with a safe response to invalid readings. No threshold or sensor-controlled motion is added before the raw table is complete.

Words you need today

Sensor
A device that turns a physical condition, such as contact, color, or distance, into information the program can read.
Raw reading
The value or state reported directly by the sensor API before the team compares or converts it for a decision.
Unit
The named measurement scale attached to a number, such as the exact distance unit selected in code.
Field of view
The space a non-contact sensor must see without blockage to detect its target.
Contact path
The physical route a target follows to press a contact sensor without side-loading or damaging it.
Invalid reading
A value the exact sensor documentation or API says is unavailable, saturated, out of range, or otherwise not usable.
Threshold
A boundary chosen from collected evidence that separates one program decision from another.
Bounded behavior
A robot action limited by documented safe output, extent or position, an escape condition, driver override, and Stop.

Before you touch the robot

  • Name the Driver Station operator and Stop owner, condition/reset lead, sensor observer, programmer, and recorder.
  • Press Stop, switch off the Hub, and disconnect the battery before mounting, routing, tightening, or touching a sensor or wire.
  • Read the exact product label or model. Match its current manufacturer document, connector, port, active configuration type/name, and SDK sample before giving wiring or code advice.
  • Protect the cable from pull, pinch, sharp edges, wheels, mechanisms, and field contact while preserving the exact field of view or contact path.
  • Keep the Meeting 12 responsive TeleOp and tested autonomous/fallback unchanged until a small sensor candidate passes review.
A sensor does not make motion safe. Press Stop for unexpected motion or output, collision approach, moving cable, loose mount, blocked mechanism, lost communication, abnormal sound, heat, or odor. Verify all motion has stopped, say stopped, switch off, and disconnect before entry or adjustment.

Follow along: read first, decide later

  1. Name a robot question: write one useful event question the installed sensor could answer without naming a threshold. This prevents adding a sensor only because one is available. Success: the question describes an observable condition and useful decision.
  2. Prove exact identity: copy the manufacturer and model from the part, then match the connector, port, configuration type/name, current manufacturer page, and exact SDK sample header. Success: every identity points to the same device; any mismatch blocks work.
  3. Trace one reading: point from the physical condition to the sensor, API call, raw telemetry label, unit or discrete state, and documented invalid indication. This separates observation from decision. Success: no comparison or actuator command appears in the trace.
  4. Name realistic conditions: choose actual targets and non-targets, useful range or contact states, approach, alignment, robot posture, surface, ambient condition, vibration, something blocking the sensor's view (occlusion), or dirt only where relevant to this exact device. Success: each row can be recreated.
  5. Collect before comparing: reserve repeated raw rows for every named condition. This reveals overlap and invalid values before a threshold is invented. Success: the team agrees not to add a threshold until all rows are filled.

Choose the source by exact installed sensor

REV path

If the installed part is the exact named REV touch, color, or distance sensor, use that matching REV tutorial for its read-display sequence and current exact-product documentation for wiring, mounting, range, and limitations. Implement Java from the exact pinned SDK v12.0 sample. Do not use one REV sensor tutorial for a different REV model.

goBILDA or other manufacturer path

Use goBILDA sensor documentation only when the label identifies that exact goBILDA sensor and exact documentation exists. The goBILDA StarterBot guide and code ZIP contain no general sensor lesson. Otherwise use current documentation from the sensor's actual manufacturer and the official SDK sample that matches its real interface; do not invent a goBILDA path.

Try it with your partner

Three pairs: one pair per station, rotating every 20 minutes. Two pairs: begin at Mount and Raw Code, swap after 20 minutes, then complete Conditions together. Assign condition/reset, telemetry reading, untouched-value recording, and identity/validity auditing; swap halfway. No powered work occurs during rotations.

1. Protect the exact sensor

  1. With power disconnected, verify product label/model, connector, port, configuration, and manufacturer mounting guidance.
  2. Secure the sensor without crushing its housing, distorting a switch, covering the sensor opening (aperture), or placing protection in its sensing path.
  3. Add a small supported length of extra cable that permits normal movement and service (service slack), plus strain relief on the cable rather than the connector.
  4. Trace the field of view or contact path through every relevant mechanism posture and add protection that does not block it.

Success looks like: the mount stays fixed and protected while its documented sensing path remains clear.

2. Display raw telemetry

  1. Read the exact matching sample header and match every required device, name/type, connection, unit, and warning.
  2. Copy the sample into TeamCode, rename it, retain @Disabled, and change only the verified case-sensitive hardware name.
  3. Keep initialization and concise labeled raw telemetry, including the documented invalid or unavailable indication.
  4. Build and inspect the diff. Reject every new threshold, borrowed conversion, sample value, or sensor-commanded output.

Success looks like: another pair can trace exact part to configuration to API field to displayed raw unit/state.

3. Freeze realistic conditions

  1. Restate the robot question without a threshold and name relevant target and non-target cases.
  2. Write repeatable setups across the useful operating range and realistic variations for this device.
  3. Freeze mount, version, configuration, units, target identity, reset, battery acceptance, and observer position.
  4. Reserve at least three untouched readings per condition and define how documented invalid readings will be marked.

Success looks like: the blank table covers realistic use and a safe-edge/no-target condition without predicting a numeric answer.

Test it safely: raw readings first

  1. Pass the identity and mount gate: with power off, inspect exact part, cable, protection, sensing path, active configuration, and matching source. Success: all identity fields agree and the mount has no unresolved safety blocker.
  2. Enable only the reviewed raw candidate: while it is still disabled, perform a final diff review confirming that it contains only the exact sensor mapping, initialization, and labeled raw telemetry. It must contain no actuator mapping or command, comparison, threshold, borrowed value, or sensor-controlled output. Remove only @Disabled, then rebuild. Success: the final build passes and the final diff shows only the reviewed enablement change.
  3. Power up safely: with the Hub off connect the accepted battery; switch on; confirm Hub status and Driver Station connection; deploy the rebuilt telemetry-only candidate; verify its renamed OpMode appears on the Driver Station; select that exact name; press INIT; verify identity, safe outputs, labels, units/states, and documented invalid handling. Success: the renamed OpMode appears and no actuator responds to the sensor.
  4. Collect each frozen condition: call robot live only if needed, use stationary or lowest-risk operation first, recreate the named setup, and record each raw reading exactly. Keep inconvenient, fluctuating, invalid, saturated, and overlapping values. Success: every cell reflects observation rather than a cleaned-up expectation.
  5. Return to safe contact: after each set press Stop, verify safe outputs and no motion, say stopped, switch off, and disconnect before moving the sensor, target, robot, or mechanism where contact is required. Success: any moved mount starts a newly identified set.
  6. Review only after collection: compare full ranges, overlap, and invalid rows. Do not average away a safety-relevant outlier. Success: the team selects telemetry only, remount/recollect, reject, or one evidence-supported bounded behavior.

If the sensor, robot, or exact source is unavailable

  1. Record the missing exact model, document, matching sample, robot question, or robot access. Do not choose a similar-looking device.
  2. Use captured readings only when labeled with exact device, units, setup, robot state, and source. Mark them captured practice - not current BIOBUZZ robot evidence.
  3. Practice range/overlap and invalid-reading analysis on the captured data. Do not use it to approve the current mount or a threshold for another device.
  4. Use symbolic cards for raw input, decision, safe invalid default, bounded output, override, and Stop. Do not compile invented sensor classes or values.
  5. Use remaining robot time on a documented TeleOp/autonomous reliability blocker, mechanism work, driver practice, or portfolio work. Assign owners and dates for missing identity, mounting, raw collection, and physical testing.

Mentor preparation

  • Audit Meeting 12's responsive TeleOp, autonomous/fallback identity, Stop proof, physical blockers, and useful sensor question.
  • Inventory installed sensors from labels, not appearance. Gather current exact-product documentation, connector/port requirements, active configuration, and matching pinned SDK sample.
  • Prepare realistic condition cards and safe mounting materials without supplying a threshold, conversion, sample constant, timer, or other unverified value.
  • Prepare a disabled TeamCode copy, raw-only test card, shared fault log, and peer explanation roles.
  • Block power and automation if identity, electrical requirements, mount, sensing path, safe output, or useful question is unresolved.
Order gate: exact identity, protected mount, raw display, repeated realistic observations, and usefulness decision come before any threshold. A clean telemetry-only result is complete and preferable to weak automation.
