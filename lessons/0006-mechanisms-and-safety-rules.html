What you will make the robot do

The matching team TeleOp will control every installed action classified required on the approved Meeting 4 map and no optional, unavailable, or unapproved action. Each enabled action will use its approved input pattern, reject its recorded conflict, provide required reverse or recovery, report useful telemetry, and return every touched output to explicit zero or its verified safe hold when the request is absent and when Stop occurs.

A source value is only a candidate for the exact named vendor assembly. A physical power, position, velocity threshold, or limit becomes a retained team value only after its exact source and installed-robot test are recorded. An unperformed measurement remains pending and its output remains disabled.

Words you need today

Proportional input
An input whose amount changes the requested output, such as trigger travel controlling intake power. Neutral must calculate explicit zero.
Held input
An action requested only while a button or thresholded trigger remains active. Releasing it must immediately select the documented safe release.
One-press input
An action requested once on the edge from not pressed to pressed. It is appropriate only when the approved action requires a retained state; holding the button must not repeatedly create new state changes.
Mutual exclusion
A decision that prevents conflicting requests from commanding hardware together. The action map says which request wins or whether both are blocked.
Safe release
The explicit zero output or verified safe hold commanded when an action request is absent. Safe release is recorded for each output, not assumed from a missing code branch.
Reverse or recovery
The approved operator action for safely undoing motion, clearing a recoverable jam, or returning to a known state. It is not permission to overpower a bind or hard stop.
Safe hold
A measured retained position that is safe for the exact positional mechanism. It has a named command and evidence; it is not an unknown servo endpoint.
Enabled-feature scope
The set of required, installed actions whose source, controls, values, conflict rules, and tests are complete. Everything else stays disabled.

Before you touch the robot

  • Use a supported test in the game arena: secure the frame on stable support and keep every wheel clear of the support, floor, people, wires, and loose objects.
  • Name the routine Driver Station operator and a separate Stop owner with immediate Stop access and authority to press it without permission.
  • Press Stop, verify no motion, switch off the Hub, and disconnect the battery before touching, loading, measuring, clearing, or changing a mechanism.
  • Secure the robot, battery, Hub, wires, attached pieces, mechanism, and test artifact. Mark the exclusion area and keep everyone outside it while live.
  • Match the installed robot and revision to REV, goBILDA, or unmatched. Use the current Competition Manual for legal actuator/control-system choices; vendor code does not establish legality.
  • Write the prediction, one bounded command, safe release, Stop condition, and evidence before power. Change one test variable at a time.
Stop first. Unexpected movement, loose hardware, unsafe vibration, collision, pinch risk, binding, stall, unusual sound, heat, odor, implausible telemetry, loss of control, or inability to command zero/safe hold means press Stop. Verify no motion, say stopped, switch off the Hub, and disconnect the battery before entry or contact. Never power through a jam.

Use the input pattern the action requires

These traces use names, not reusable values. The matching branch below supplies only names whose declarations have been populated from its signed source-and-measurement record.

Proportional

Calculate a fresh command from the approved analog inputs every loop. Apply the recorded mutual-exclusion rule, then write the output once. Fully released inputs must calculate explicit zero.

Trace: input amounts → conflict decision → bounded command → output and telemetry.

Held

Start from explicit zero/safe hold each loop. Select forward only while its request is held, or the approved reverse/recovery only while that request is held. On both or neither, apply the action map's recorded safe result.

Trace: held booleans → mutual exclusion → named command or safe release → output.

One-press

Detect the false-to-true edge and select only a measured approved retained position. With no new edge, explicitly command the currently approved safe hold. At Stop, command the separately verified Stop hold.

Trace: current/prior button → edge → approved retained state → verified safe hold.

// Shared decision shape; declarations come from the selected vendor record.
double command = safeRelease;
if (forwardRequested && !recoveryRequested && conflictClear) {
    command = approvedForward;
} else if (recoveryRequested && !forwardRequested && recoveryClear) {
    command = approvedRecovery;
}

telemetry.addData("Request", requestName);
telemetry.addData("Conflict clear", conflictClear);
telemetry.addData("Command", command);
// The selected branch writes command to its exact mapped output once.

Why this matters: setting a safe command before decisions prevents a released, conflicting, or rejected request from inheriting the previous loop's moving output.

REV path: exact 2026-2027 REV Starter Bot only

The verified REV material names intake forward/reverse, pollen-poker positions, manual flywheel forward/reverse recovery, velocity-gated feed, and manual feeder recovery. Implement only rows that Meeting 4 marked required and the installed robot actually has. Copy candidate values only from the current exact REV page, record its access date, and retain them only after M06 physical evidence.

// Values below are declarations in the team file, populated only from the
// signed REV source + M06 record. No number comes from this lesson.
double revIntakeCommand = 0.0;
if (revIntakeRequested && !revIntakeRecoveryRequested) {
    revIntakeCommand = REV_INTAKE_FORWARD;
} else if (revIntakeRecoveryRequested && !revIntakeRequested) {
    revIntakeCommand = REV_INTAKE_RECOVERY;
}
revIntake.setPower(revIntakeCommand); // one write; release/conflict is zero

// This declaration exists only after the exact hold passes M06 measurement.
double revPokerHold = REV_POKER_SAFE_HOLD;
if (revPokerActionPressed && !revPokerActionWasPressed) {
    revPokerHold = REV_POKER_ACTION_HOLD;
} else if (revPokerRecoveryPressed && !revPokerRecoveryWasPressed) {
    revPokerHold = REV_POKER_SAFE_HOLD;
}
revPollenPoker.setPosition(revPokerHold); // explicit verified retained hold

// In a finally/shutdown path reached after the active loop:
revIntake.setPower(0.0);
revFlywheel.setVelocity(0.0);
revFeeder.setPower(0.0);
revPollenPoker.setPosition(REV_POKER_STOP_HOLD);

Initialization: REV_POKER_SAFE_HOLD is not a lesson value. The mentor may add that declaration only after the exact position is copied from the matching REV source, tested as the installed mechanism's safe hold under M06-M01, and signed. Until then, the pollen-poker feature stays disabled and no position is written. Mutual exclusion: simultaneous forward/recovery requests command zero. The approved map may name a different conservative winner only if that decision and its test are recorded. Safe release: intake, flywheel, and CR-servo feeder use explicit zero; the positional pollen poker uses only its measured current hold and separately verified Stop hold. A flywheel/feed implementation must also command both outputs explicitly when the velocity gate is false.

Linear shutdown: place the active REV loop inside try and the four brief shutdown commands shown above inside finally. When opModeIsActive() becomes false, exit the loop immediately; do not continue mechanism work after Stop.

goBILDA path: exact 2026-2027 goBILDA StarterBot only

The verified goBILDA artifact names one intake motor, left/right corner-intake CR servos, launcher motor, and windmill CR servo. It demonstrates proportional right-trigger minus left-trigger intake and a held launcher request with velocity-gated windmill feed. It does not supply a positional-servo one-press mechanism or a launcher reverse control; do not invent either. Implement recovery only where the approved map and exact installed mechanism provide measured evidence.

// Bounds and thresholds are declarations in the team file, populated only
// from the signed goBILDA artifact + M06 record.
double gobildaIntakeCommand = gamepad1.right_trigger - gamepad1.left_trigger;
gobildaIntakeCommand = Range.clip(gobildaIntakeCommand,
        GOBILDA_INTAKE_REVERSE_LIMIT, GOBILDA_INTAKE_FORWARD_LIMIT);

double gobildaLauncherCommand = 0.0;
double gobildaWindmillCommand = 0.0;
if (gobildaLaunchRequested) {
    gobildaLauncherCommand = GOBILDA_LAUNCHER_TARGET;
    if (gobildaMeasuredVelocity >= GOBILDA_FEED_THRESHOLD) {
        gobildaWindmillCommand = GOBILDA_WINDMILL_FEED;
    }
}

gobildaIntake.setPower(gobildaIntakeCommand);
gobildaLeftCornerIntake.setPower(gobildaIntakeCommand);
gobildaRightCornerIntake.setPower(gobildaIntakeCommand);
gobildaLauncher.setVelocity(gobildaLauncherCommand);
gobildaWindmill.setPower(gobildaWindmillCommand);

@Override public void stop() {
    gobildaIntake.setPower(0.0);
    gobildaLeftCornerIntake.setPower(0.0);
    gobildaRightCornerIntake.setPower(0.0);
    gobildaLauncher.setVelocity(0.0);
    gobildaWindmill.setPower(0.0);
}

Mutual exclusion: trigger subtraction makes equal opposing intake requests produce zero; test that result and any team deadband or limit rather than assuming it. Safe release: released triggers calculate zero, released launcher request commands zero velocity and zero windmill power, and stop() explicitly zeros every touched mechanism output. The iterative SDK calls stop() once when the OpMode stops, but hardware-control ability is limited then, so no-request zeros remain mandatory in every loop. The verified artifact's empty stop() is not the team shutdown implementation.

Build with your partner

Three pairs: begin at Contract, Control Logic, and Test/Evidence, then rotate every 15 minutes. Two pairs: begin at Contract and Control Logic, swap after 20 minutes, then reconcile one test/evidence record together. Use telemetry-only pair copies; only the reviewed matching implementation reaches the shared candidate.

1. Contract and values

  1. Cross out optional, unavailable, unmatched-vendor, and unapproved actions.
  2. For each required output, record input pattern, conflict, release, reverse/recovery, and telemetry.
  3. Trace every power, position, threshold, and limit to the matching source plus completed or pending M06 trial.
  4. Mark incomplete actions disabled; do not fill unknown declarations with estimates.

Success looks like: executable scope contains only complete required rows and every retained value has two-part provenance.

2. Control logic

  1. Initialize each command to explicit zero or verified safe hold every loop.
  2. Apply the proportional, held, or one-press pattern named by its approved row.
  3. Make conflicting requests select the documented safe command; add required reverse/recovery without bypassing limits.
  4. Write each output once and display input, decision/state, measured condition, and final command.

Success looks like: neutral, action, conflict, release, and recovery telemetry match predictions without hardware calls in the pair copy.

3. Test and evidence

  1. Write one bounded supported-test card per mechanism, beginning without a game artifact or mechanism load.
  2. Name setup, exact configuration, units, method, trial ID, command, observer, Stop owner, abort signs, and pass criteria.
  3. Include initialization, no request, each request, simultaneous conflict, release, reverse/recovery, and Stop.
  4. Record student, checker, date, actual result, and highest passed scope. A failed case disables that action.

Success looks like: another pair can run the card without choosing a value or interpreting a missing branch.

Test one bounded mechanism at a time

  1. Review before deployment: compare the selected matching branch with the approved map, provenance table, telemetry-only cases, build result, and diff. Confirm unrelated and pending features are disabled. Success: every hardware call and possible command points to a signed row.
  2. Prepare the supported test: with the Hub off and battery disconnected, secure all hardware and the unloaded mechanism, verify configuration and exclusion area, and position the operator and Stop owner. Success: a second student signs setup and immediate Stop access.
  3. Prove initialization and no request: connect the battery while the Hub is off, switch on, confirm connection, call robot live, receive clear, then INIT and Start with controls neutral. Success: telemetry and every touched output show explicit zero or the verified safe hold.
  4. Run bounded cases: command one approved action, release it, command approved reverse/recovery, and test the recorded conflict. Return controls to neutral between cases. Success: input, decision/state, measured condition, command, and observed behavior match each written prediction without an abort sign.
  5. Prove Stop: while the mechanism is in a bounded active case, the Stop owner presses Stop. Verify no motion, say stopped, switch off the Hub, and disconnect the battery. Success: each motor/CR servo reaches zero and each positional output reaches its verified Stop hold; record actual behavior rather than inferring it from code.
  6. Decide scope: enable only complete passing actions. A source-only, telemetry-only, failed, or pending case stays disabled for integration. Any part, linkage, wiring, code value, or source change invalidates affected M06 evidence and requires retest. Success: the candidate and record name the same enabled-feature scope.

Measure it M06-M01

If the robot, action map, or measurement is unavailable

Do not choose a vendor path by appearance, invent a value, map unavailable hardware, or report a physical pass.

  1. Mark the missing identity, approval, source, configuration, part, setup, or measurement and assign an owner and next check.
  2. Keep every affected feature disabled. Replace hardware writes with telemetry showing input, conflict decision/state, pending provenance, and explicit zero/safe-hold intent.
  3. Run neutral, request, simultaneous conflict, release, reverse/recovery, and simulated Stop cases. Label the result telemetry only.
  4. Use an unpowered diagram to mark travel, collisions, pinch areas, wire strain, loading, release, and recovery. Do not convert diagram estimates into code values.
  5. Schedule the supported physical trials in order. Carry the exact prerequisites, cards, disabled features, owner, and date into Meeting 7.

Success looks like: complete logic evidence within its stated scope, no active unknown output, and an honest blocker record for every unperformed physical claim.
