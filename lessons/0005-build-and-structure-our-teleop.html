What you will make the robot do

The approved gamepad controls will send a forward request and a turn request to drive(double forward, double turn). The method will calculate bounded left and right outputs, send them to the verified drivetrain motors, report concise telemetry, and command zero when no motion is requested or the OpMode stops.

You will preserve the installed robot's verified names, types, and directions. The REV path stays linear. The goBILDA path stays iterative. Both paths express the same team intent without copying hardware assumptions between robots.

Words you need today

Method
A named group of Java instructions. The team-owned drive method has one job: turn a motion request into drivetrain output.
Method definition
The method heading and body that say what Java does when the method runs. Today its heading is drive(double forward, double turn).
Parameter
A name in a method definition that receives a value. forward and turn receive the two requested motions.
Call site
The place that asks a method to run, such as drive(forwardRequest, turnRequest);.
Steering math
The team-selected rule that combines forward and turn requests into left and right outputs. For the approved two-side arcade design, left adds turn and right subtracts turn.
Output limiting
Keeping final motor commands inside the API range and the team's verified drive limit. The team must record and approve a limit from 0.0 through 1.0 before scaling; the bounds come from the motor-command API, but the chosen value comes from team evidence.
Normalization
Dividing all related outputs by the same amount when one is too large. This preserves their proportion while bringing the largest magnitude to the limit.
Clipping
Restricting each output separately to a lower and upper bound. Clipping can change the proportion between outputs.
Safe default zero
The explicit drivetrain command used before motion is allowed, whenever the request is neutral, and when the OpMode stops.
Lifecycle
The ordered methods an OpMode uses for setup, Start, repeated work, and Stop. This lesson keeps each matching vendor program's lifecycle.
Supported test
A powered test in the game arena with the robot frame secure on stable support and every wheel clear of the support, floor, people, wires, and loose objects.
Travel test
A powered test in the game arena that begins at a marked start, follows a marked route to a marked stop, and keeps everyone outside the exclusion area.

Verify motion has ended, say stopped, switch off the Hub, and disconnect the battery before anyone enters the exclusion area or touches the robot.

  1. Start from approved records: place Meeting 2's motor map beside Meeting 4's action/control map. This prevents a vendor example from silently replacing team evidence. Success: every highlighted code fact points to one approved record or is marked blocked with an owner and next check.
  2. Write the call site first: read the approved gamepad fields into forwardRequest and turnRequest, then call drive(forwardRequest, turnRequest);. This makes the program state the driver's intent before motor detail. Success: each argument can be traced to one approved control and its intended sign.
  3. Write the method definition: add drive(double forward, double turn) outside the lifecycle method but inside the OpMode class. This gives one name to the drivetrain job. Success: students can point to the method name, two parameters, opening and closing braces, and call site.
  4. Calculate left and right: for the approved two-side arcade design, calculate left = forward + turn and right = forward - turn. This converts robot motion intent into side intent. Success: neutral predicts zero/zero, forward predicts matching signs, and a turn predicts different side signs or magnitudes according to the written test.
  5. Verify the team drive limit: copy the value and decision-record ID only from the signed team record, confirm 0.0 <= teamDriveLimit <= 1.0, and then set the verification flag. The API bounds establish what the command accepts; they do not supply a universal robot value. Success: code remains fail-closed at zero until the exact value, record ID, approvers, and date are checked.
  6. Apply the recorded limiting policy: choose normalization or clipping deliberately and record why. If normalizing, divide both outputs by the same denominator before applying the verified team drive limit. If clipping, apply the verified limit and record the control-feel tradeoff. After scaling, use Range.clip on every final output as an API-range guard. Success: fixed-input calculations remain within the API range and verified team limit, and the record identifies the selected policy and approvers.
  7. Send output once: place only the final verified left and right motor calls in drive. This keeps motor output behind one team-owned interface. Success: no other active code path writes to those drive motors, except an intentionally documented diagnostic that remains disabled during this lesson.
  8. Add concise telemetry: display forward request, turn request, final left output, and final right output. This lets students compare intent, math, and command without hiding useful values in prose. Success: the four labels fit on the Driver Station and agree with the paper cases.
  9. Make zero explicit: call drive(0.0, 0.0) before motion is allowed and when the lifecycle ends. Neutral input must also calculate zero/zero. This makes the safe default reviewable in code and testable on the robot. Success: the diff shows every required zero call and fixed-input telemetry shows zero/zero for neutral.
  10. Build and inspect: build TeamCode and compare the diff with the selected matching baseline. This catches Java errors and crossed vendor assumptions before robot power. Success: the build passes and reviewers find only approved controls, the team method, selected math/limiting, telemetry, and explicit zero behavior.

The shared method intent

This example shows normalization for a two-side arcade drivetrain. leftDriveMotor and rightDriveMotor are placeholders for verified team fields. teamDriveLimit has no published default: copy it from the signed team decision, copy that record's ID, confirm the API bounds, and set teamDriveLimitVerified only after both entries are checked. The method otherwise commands zero. A team that approves clipping writes and tests that policy instead, but still verifies the limit before scaling and applies final Range.clip.

import com.qualcomm.robotcore.util.Range;

// Fill these from the signed team decision before enabling drive output.
private double teamDriveLimit;
private String teamDriveLimitDecisionId;
private boolean teamDriveLimitVerified = false;

private void drive(double forward, double turn) {
    double left = 0.0;
    double right = 0.0;

    boolean usableDriveLimit = teamDriveLimitVerified
            && teamDriveLimitDecisionId != null
            && !teamDriveLimitDecisionId.trim().isEmpty()
            && 0.0 <= teamDriveLimit && teamDriveLimit <= 1.0;
    if (usableDriveLimit) {
        left = forward + turn;
        right = forward - turn;

        double denominator = Math.max(1.0,
                Math.max(Math.abs(left), Math.abs(right)));
        left = Range.clip((left / denominator) * teamDriveLimit, -1.0, 1.0);
        right = Range.clip((right / denominator) * teamDriveLimit, -1.0, 1.0);
    } else {
        telemetry.addData("Drive blocked", "Verify team drive-limit record");
    }

    leftDriveMotor.setPower(left);
    rightDriveMotor.setPower(right);

    telemetry.addData("Drive limit record", teamDriveLimitDecisionId);
    telemetry.addData("Drive request", "forward %.2f, turn %.2f", forward, turn);
    telemetry.addData("Drive output", "left %.2f, right %.2f", left, right);
}

Test it safely: Supported test before Travel test

A. Supported test

  1. Write predictions: record the exact forward/turn input, raw left/right calculation, final limited output, and every expected wheel direction for neutral, forward, reverse, left turn, right turn, and the selected combined case. This makes signs and limits testable before motion. Success: a second student checks the arithmetic and named viewing position.
  2. Prepare the setup: in the game arena, keep the Hub off and battery disconnected while securing the frame on stable support, every clear wheel, battery, Hub, wires, attached pieces, and mechanisms. Mark the exclusion area and name the routine operator, Stop owner, observer, and recorder. Success: a second student signs the setup and immediate Stop access.
  3. Verify identity: compare the robot revision, active configuration, motor map, matching lifecycle source, build, selected OpMode, controls, limiting policy, team drive limit, signed decision-record ID, approvers, and date with the test record. Confirm the recorded limit satisfies 0.0 <= teamDriveLimit <= 1.0 before scaling and that final outputs use Range.clip. This prevents testing the wrong program, value, or assumptions. Success: every identity and provenance field agrees or drive output remains zero and powered work stays blocked.
  4. Power and clear: connect the accepted battery while the Hub is off, switch on, confirm Hub status and Driver Station connection, assign the gamepad, select the intended OpMode, release all controls, then call robot live and receive clear before INIT. Success: everyone is outside the exclusion area and the Stop owner confirms immediate access.
  5. Check safe default zero: press INIT and observe all wheels and telemetry before Start. Start with all controls neutral, then release controls after every case. This proves the explicit zero path before and between motion requests. Success: telemetry reports zero/zero and every wheel remains or returns motionless.
  6. Run one case at a time: briefly apply only the recorded input for forward, reverse, left turn, right turn, and the selected combined case. Compare telemetry and every wheel with the prediction, returning to neutral after each case. Success: each row records commanded values, observed directions, zero return, and any discrepancy without silently changing the setup.
  7. Prove Stop: during a bounded final case, press Stop; verify all wheels stop, say stopped, switch off the Hub, verify power is off, and disconnect the battery before entry. Success: the record names the observed Stop response and no output remains.
  8. Decide the gate: authorize Travel test only if every required sign, limiting, telemetry, neutral-zero, Stop, stability, and hardware condition passes. If any case fails, preserve the row, make one evidence-supported correction while disconnected, then repeat every affected Supported test case. Success: the signed decision says pass or blocked and identifies the exact trial.

B. Travel test

  1. Prepare the route: only after the Supported test gate passes, keep the Hub off and battery disconnected while moving the robot to the marked start in the game arena. Mark the route, stop, exclusion area, operator position, and Stop-owner position. Success: the route uses the approved controls and has measurable pass criteria written before motion.
  2. Power and clear: secure the battery and attached pieces, connect while the Hub is off, switch on, confirm Hub status and Driver Station connection, assign the gamepad, select the intended OpMode, release controls, call robot live, and receive clear before INIT. Success: every person remains outside the exclusion area with Stop immediately available.
  3. Run the marked route: from the marked start, use the approved bounded controls to travel forward, make the planned turn, and command zero at the marked stop. This checks behavior under load only after supported direction proof. Success: observers record start, path, turn, stop location, drift or correction, final telemetry, and whether zero ended motion.
  4. Stop and make safe: press Stop at the planned boundary or immediately for any stop condition. Verify motion ends, say stopped, switch off the Hub, verify power is off, and disconnect before anyone enters or touches the robot. Success: Stop response and final robot position are recorded before the setup changes.
  5. Handle a mismatch: preserve the failed trial, change one evidence-supported item while disconnected, and return to all affected Supported test cases before another Travel test. This keeps cause and effect visible. Success: the new trial has a new ID and does not overwrite the original observation.
