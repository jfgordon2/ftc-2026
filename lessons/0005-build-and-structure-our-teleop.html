Tune the Shooter and Build an Auto Path

First check that the robot drives and turns the amounts it is told. Then find the launcher speed that hits the target, and make the robot drive, aim at an AprilTag, and park by itself.

Today’s goal

Leave with checked drive and turn numbers, a launcher speed table we measured ourselves, and one autonomous path that ends inside a taped parking box.

We do not have a field or the new robot yet, so we build a practice field from tape: a rectangle on the wall for the hive opening and lines on the floor for the start and the parking zone. We use one of last season’s practice robots. We check the robot’s own numbers first, because everything after depends on them: if the robot thinks 24 inches is 22, every shooting mark and every route will be off too. The numbers we find today belong to that robot. The steps, the worksheets, the tape layout and the code are what we reuse on the BIOBUZZ robot.

Start here

  1. Check the robot’s numbers. Is the Hub direction set right? Does it drive 24 inches when asked, turn 90 degrees, and spin the launcher up to speed? Robot checks.
  2. Build the practice field. The rest of the team tapes the wall target and the floor lines at the same time. Measurements.
  3. Tune the shooter. Shoot five balls, count hits, change the speed one step, repeat. Shooter steps.
  4. Build the auto path. Type a few numbers into one route, run it, measure where the robot ends. Auto steps.
  5. Save. Put the numbers that worked into the code and save it. Save your work.

One robot runs at a time. While one pair works at the robot, the other students tape the route, graph the shooting results, or read the code for the next step. Swap jobs after every five shots or every test run.

Before power

  • Everyone stands behind the robot when the launcher can spin. Nobody stands between the robot and the wall.
  • One student drives. A different student keeps a hand near Stop on the Driver Station and may press it at any time without asking.
  • Press Stop and wait for the wheel to stop before you load balls, pick up balls, measure, or touch the robot.
  • Clear a jam only with the robot switched off.
Stop first: if the robot goes the wrong way, something is loose, a ball jams, or the numbers on the screen look wrong, press Stop. Then work out why.

Steps and worksheets

Words you need

Ticks per inch: how many encoder counts a drive wheel makes while the robot rolls one inch. The code uses it to turn “drive 24 inches” into a number of ticks. Ticks per second: how fast the launcher wheel spins, counted by its encoder. Our code and goBILDA’s code both ask for launcher speed this way. Camera range: the distance the camera reports to the AprilTags, in inches. Interpolate: pick a value between two measured points. Route: the list of steps for one autonomous path: drives, turns, and aim-and-shoot. IMU: the sensor in the Control Hub that tells which way the robot faces.

Check the robot’s numbers

The code starts with numbers copied from the robot maker’s example code: how many encoder ticks make an inch, and how fast the launcher should spin. They are close, not exact, and every robot is a little different. Check them first. Everything else today, the shooting marks and the route, assumes the robot drives the distance it is told.

One pair works at the robot. Everyone else builds the practice field at the same time. Take the balls out. No camera is needed yet.

1. Battery

  1. Run any program and press INIT only. Read the Battery line and write the voltage at the top of the worksheet.
  2. If it says SWAP or CHARGE, change the battery now. A tired battery makes the robot drive and shoot differently, so every number after this would be off.

2. Which way the Hub faces

The Control Hub has a heading sensor (the IMU) inside it. The code has to be told how the Hub is mounted, or it measures turning around the wrong axis, and the robot cannot drive straight or turn by itself. Programs that drive by themselves stay still until this check is done.

Program: Tune Drive. Press INIT only; never Start for this check. In INIT the motors are off, so you can move the robot with your hands. “Turn the robot by hand” means: leave it on the floor and twist it round with your hands, like turning a box on a table.

  1. Look at the Control Hub on the robot. Which way does the REV logo face: up, down, forward, back, left or right? Which way do the USB ports point? “Forward” means toward the front of the robot: the way it moves when the left stick is pushed forward.
  2. Open Heading.java. Compare your answers with LOGO and USB near the top. The INIT screen also shows them on the Hub logo / USB / confirmed line. If they do not match the robot, change them and build again.
  3. Turn test: watch the Heading sensor (IMU) number on the screen. Turn the robot by hand about a quarter turn to the right (clockwise, seen from above). The number should go up by about 90. Turn it back: it should come back down.
  4. Tilt test: lift the front of the robot about 4 inches and put it down. Then lift one side about 4 inches and put it down. Each time the heading should change by only a few degrees.
  5. If the number goes down when you turn right, barely moves when you turn, or jumps when you tilt, the logo or USB setting is wrong. Look at the Hub again, fix the setting, build, and repeat both tests.
  6. When both tests pass, show the mentor. The mentor sets MOUNTING_CONFIRMED = true and builds. The robot can now drive by itself.

3. Distance: ticks per inch

Program: Tune Drive.

  1. Put a pencil mark or a piece of tape on the side of the robot, and line it up with a tape mark on the floor. Leave at least 4 feet of clear floor ahead.
  2. Press INIT, then D-pad UP to choose 24 inches forward. Press Start. Everyone stays clear.
  3. When it stops, write the left and right tick numbers and the seconds from the screen. Press Stop. Measure how far the mark on the robot really moved, to the nearest quarter inch.
  4. Do it again from the same mark. Then once more with D-pad DOWN for 24 inches backward.
  5. For each run, work out ticks per inch = average of left and right ticks ÷ real inches. Average the three answers.
  6. The code starts with 45.28 for a goBILDA robot and 44.56 for the REV robot. If your average differs by more than 1, change it: open robot/Drive.java and find the three TICKS_PER_INCH_… lines near the top, one per robot. Change only the line for your robot. For last season’s goBILDA robot, that is: 
    public static final double TICKS_PER_INCH_PRACTICE_GOBILDA = 45.28;   // replace 45.28 with your number
    Build, and run 24 inches forward once more. It should now land within half an inch.

Worked example: the robot drives, the screen says 1088 and 1092 ticks, and the tape shows 23.5 inches. Average ticks = 1090. 1090 ÷ 23.5 = 46.4 ticks per inch. That is more than 1 away from 45.28, so we replace 45.28 with 46.4 on our robot’s line.

If the left and right ticks differ by more than about 20, or the robot curves, look for a dragging wheel or a loose hub before you change any numbers.

4. Turns

  1. Tape a square corner on the floor. Line one side of the robot up with one side of the corner.
  2. Press D-pad RIGHT for a 90-degree right turn and Start. Is the robot now lined up with the other side of the corner? Write how many degrees off it looks.
  3. Do the same with D-pad LEFT.

Turns use the Hub’s heading sensor, not the wheel ticks, so changing ticks per inch does not change them. If the robot turns the wrong way or keeps spinning, go back to step 2. More than about 3 degrees off, or a robot that wobbles back and forth at the end, is a note for the mentor; there is no number for you to change today.

5. Launcher speed

Program: Tune Shooter. Still no balls.

  1. Press INIT, then Start. Hold the right bumper. The screen shows the speed asked for and the speed measured, in ticks per second.
  2. Count how many seconds until it says At speed: true. Two seconds or less is normal. Write the measured speed once it settles.
  3. Let go. Press D-pad UP eight times (200 more) and try again. This tells you the launcher has room to spare above its normal speed.

If the measured speed never reaches the speed asked for, check the battery first. If it still cannot, tell the mentor: the normal speed in StarterRobot.java may be too high for this launcher.

Tune the shooter

Program: Tune Shooter (TuneShooter.java). Read its loop() before you drive it. It has five numbered parts.

The three readings should be within about 1 inch of each other. If they jump around, tighten the camera mount and check the lighting.
  2. Check one tap. Load one ball, hold the right bumper, and tap Y once when the screen says At speed: true. One ball should leave. If none or two leave, ask the mentor to change FEED_PULSE_SECONDS in ShooterCalibration.java.

  9. Move to the 26-inch mark, then the 18-inch mark, and find the circled row for each.

Put the table in the code

Open ShooterCalibration.java. Type the circled rows into the two lists, closest range first. Each range lines up with the speed below it.

// Made-up numbers to show the shape. Use your own circled rows.
public static final double[] RANGE_INCHES           = {38, 46, 54};
public static final double[] SPEED_TICKS_PER_SECOND = {1100, 1175, 1250};

Between two rows the code interpolates. With the made-up rows above, a range of 42 inches is halfway between 38 and 46, so the speed is halfway between 1100 and 1175: about 1138. Outside the rows the robot refuses to shoot. It never guesses.

No camera? Set USE_CAMERA = false, aim by hand, and fill in the mark column only. The auto path below needs the camera.

Build the auto path

Program: Autonomous Route. A route is a list of steps in Routes.java. The robot does them from top to bottom. There are three kinds of step:

StepWhat the robot does
drive(inches)Drives that far. A negative number drives backward.
turn(degrees)Turns that much. Positive is right, negative is left.
aimAndShoot()Turns to face the tags, shoots if shooting is switched on, then turns back to the way it was facing.

The robot does not fix its distance from the wall. It shoots from wherever the drive before aimAndShoot() stops, using the speed your table gives for the camera range there.

Plan it on the floor

  1. Start position: back bumper on the start line, on the center line, facing the wall.
  2. Pick the shooting mark that worked best. Measure from the start position to that mark. That is your first drive, in inches.
  3. Put the robot on that mark and read the camera range from Tune Shooter. Check your speed table has a row closer and a row farther than that range.
  4. From that mark, decide the park turn (right is positive, left is negative) and measure the park drive into the box.

Type it in

In Routes.java change only the list that matches the printed target and Start A:

public static final Step[] RED_AUDIENCE_A = {
        drive(8),
        aimAndShoot(),
        turn(-90),
        drive(30),
};

The numbers 8, -90 and 30 are examples. Use yours. You can add or remove lines; keep the comma at the end of each one.

Run it empty

  1. No balls in the robot. Place it on the start position.
  2. INIT. D-pad LEFT then DOWN chooses RED AUDIENCE. Press A for Start A. Shooting should say DRY RUN. Check the route on the screen matches your list.
  3. Press Start and watch. The screen shows which step is running and a note about what happened last.
  4. When it stops, press Stop. Is the robot at least partly inside the box? How many seconds did it take?
  5. Change one number, build, and run again. Three runs in a row that end in the box means the path is done.

If it stops early

The screen saysTry this
Not moving: Hub direction is not confirmedAsk the mentor: the Hub direction check in Heading.java is not finished.
Not moving: MOTION_ENABLED is falseAsk the mentor: the drive-direction check is not finished.
Shot skipped: tags not lined up in timeThe camera could not see the tags, or could not centre them in 3 seconds. Check the tilt, the lighting, and that you chose the printed target. The route still carries on.
Shot skipped: speed table has no rows around … inchesThe first drive stopped outside the ranges you measured. Change the first drive, or measure another row.
Drive/turn timeoutA wheel did not reach its distance in 4 seconds. Look for something blocking a wheel, or split a long drive into two lines.

Extra: shoot during auto

Only after three good empty runs, and only with a filled-in speed table that covers the camera range at your stop. The mentor sets FEED_ENABLED to true in StarterRobot.java. In INIT, press X so Shooting says ON. Load the balls and stand behind the robot.

What this is worth in a match: moving off the field wall in AUTO is LEAVE, 3 points. Ending AUTO at least partly inside the LOADING ZONE is PARK, 5 points. Tipping the hive is 20. AUTO lasts 30 seconds; our program stops itself at 28.

Save your work

  • Your ticks per inch is typed into your robot’s TICKS_PER_INCH_… line in robot/Drive.java if it changed.
  • The circled shooting rows are typed into ShooterCalibration.java.
  • Your route numbers are in the code, and the code builds.
  • Commit with a short message, for example “Meeting 5 ticks per inch, shooter table and route”.
  • Take one photo of the wall and one of the floor with the distances showing, so we can rebuild the practice field in ten minutes.
  • Keep the worksheets in the team binder.

Before you leave, each student explains one thing to a partner: why we check ticks per inch before anything else, why we change only one number at a time, how the table picks a speed between two rows, or what makes the auto stop early.

Mentor preparation

Allow about 30 minutes before the meeting. The Meeting 5 setup guide has the reasons behind each measurement and what to recheck on a real field.

  1. Print the Meeting 5 packet at Actual Size / 100%: the worksheets and the two RED AUDIENCE tag sheets.
  2. Bring painter’s tape, a tape measure, a square corner or large protractor, cardboard for the wall, last season’s balls, and charged batteries.
  3. Robot choice: set ROBOT in StarterRobot.java to the robot on the table. PRACTICE_GOBILDA needs left_drive, right_drive, launcher, left_feeder, right_feeder in the Driver Station configuration. PRACTICE_REV needs leftDrive, rightDrive, flywheel, coreHex, servo. Both also need imu and Webcam 1.
  4. Hub direction: students check this themselves at the start of the robot checks. Look at the Hub beforehand so you know the right LOGO and USB answer, and leave MOUNTING_CONFIRMED = false. Set it to true and build only after students show you both the turn test and the tilt test passing.
  5. Drive direction: with the wheels off the floor, run Tune Shooter and push the left stick forward. Both sides should roll forward, slowly. Then set MOTION_ENABLED = true in StarterRobot.java.
  6. Launcher check: students repeat this in the robot checks; do it once beforehand so you know the launcher works. With no balls, run Tune Shooter, hold the right bumper, and confirm the measured speed climbs to the requested speed. Decide whether the 1800 ticks-per-second cap in ShooterCalibration.java suits your space. The REV robot’s normal speed is 1300, so it starts closer to the cap.

Leave the launcher’s PIDF numbers alone today. Meeting 13 covers them. Check the current FIRST manual and team updates before each meeting; this lesson was checked against Team Update 03.
