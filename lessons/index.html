BIOBUZZ / Eight-week robot programming workshop

Make the robot move, respond, and recover.

After eight weeks, you will be able to drive the competition robot, make it complete a simple route on its own, test changes safely, explain what its code does, and restore a working version when something goes wrong.

Words to know before you start

Java and Blocks
Java is the text-based primary path. Blocks is a visual bridge to Java ideas and the documented event-code fallback only if the Meeting 2 readiness check does not pass.
TeamCode and Android Studio
TeamCode is the folder for the team's robot programs. Android Studio is the app used to read Java code, check it for errors, and turn it into the robot-control app.
Git and commit
Git records code history. A commit is one saved set of understood changes in that history.
TeleOp and autonomous
Students use gamepads during TeleOp. During autonomous, the robot follows programmed instructions without gamepad driving.
OpMode and INIT
An OpMode is a robot program for one activity. INIT prepares the selected OpMode before students press Start.
Driver Station and Control Hub
Students choose and control an OpMode from the Driver Station. The Control Hub is the computer on the robot that runs it.
Telemetry
Messages and values that robot code sends to the Driver Station so students can see what is happening.

Course purpose

By the first event, every student can safely understand, change, test, explain, and recover the competition robot's basic code.

The team will produce reliable TeleOp, a simple repeatable autonomous routine, one independently demonstrated workflow per student, and a practiced backup for every critical role. Programming instruction stays attached to normal building, testing, driving, strategy, and documentation work.

How to use the course

  1. Before each meeting, the mentor confirms that the code and equipment are ready and provides instructions for the exact installed hardware.
  2. Students work in pairs. The driver controls the keyboard, gamepad, or robot. The navigator reads the next step aloud, checks it, and records what happens. Partners swap these jobs during the meeting and rotate each week.
  3. Robot access begins with a prediction and a written test. Use parallel robot, code, and team stations so one robot never leaves most students waiting.
  4. Each meeting follows observe, predict, change, test safely, explain, and, once Git is introduced, commit the tested change.
  5. When the robot or mechanism is unavailable, use the lesson's alternate activity to practice the same programming idea without claiming that hardware passed a test.
  6. End by demonstrating the result, saving the work and individual skill record, and writing what the next meeting needs.
Stop the robot before touching it. Identify the Driver Station operator and emergency-stop owner before powered tests. Use the spoken states robot live, clear, and stopped.

Java/Blocks decision gate

Java remains the primary course and competition path. Blocks diagrams may be used briefly to make program flow visible before students return to Java. At the end of Meeting 2, each pair tries a new but similar motor task. Continue the Java competition path when most pairs can find the relevant line, change it, check it for errors, and explain it with light prompting. Only if that readiness check does not pass, document Blocks as the event-code fallback while students continue optional Java practice away from competition-critical code. This choice measures whether the current tool and teaching path are clear and safe, not whether students pass or fail. Record the fallback decision and the observed evidence for the next meeting.
