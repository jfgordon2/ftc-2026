BIOBUZZ / Eight-week robot programming workshop

Trace it. Evaluate it. Rebuild it.

Students identify the exact robot and source path, make team decisions from evidence, measure the assembled system, rebuild TeleOp and Autonomous behavior, and prove an event-ready handoff.

Purpose Evidence labels Java/Blocks gate Arena testing References Four-phase map

Course purpose

By the first event, every student can trace the exact robot code, distinguish sourced facts from team choices and measurements, rebuild required behavior, test it safely, recover a known-good version, and explain the evidence.

Java is the primary path. Every lesson advances one cumulative robot artifact while preserving a tested fallback. Work stays in TeamCode; official files under FtcRobotController are not team editing targets.

Read every consequential claim by owner

Source F is a documented fact within the named source and scope. Team choice D is a BIOBUZZ decision with a recorded rationale. Measure it M is a result that only the identified robot and procedure can establish. An unperformed M claim remains pending delivery evidence; documentation never turns it into a passed robot result.

Meeting 2 Java/Blocks decision gate

Java remains the primary course and competition path. At the end of Meeting 2, each pair receives a fresh but similar motor task and must locate the relevant line, make the change, build it, and explain the expected result with light prompting. Continue Java as the competition path if most pairs can do this safely. Otherwise activate the mentor-prepared Blocks first-event project for the exact installed robot while Java continues only away from competition-critical code.

The Blocks fallback is not a second curriculum. It uses the same action map, hardware record, test cards, measurements, safety gates, qualification routine, Autonomous route, reliability checks, and handoff. It never authorizes an unperformed robot test or a feature that Blocks cannot expose safely.

Powered work happens only in the game arena

Supported test: the robot or frame is secured on stable support, with every wheel clear of the support, floor, people, wires, and loose objects.

Travel test: the robot is on the game arena at a marked start, following a marked route to a marked stop, with a marked and cleared exclusion area.

Shared controls: for every powered test, name the Driver Station operator and a different Stop owner, keep everyone outside the exclusion area while the robot is live, define explicit safe output and stopping conditions, and record evidence. Use stations or workstreams for team rotations.
