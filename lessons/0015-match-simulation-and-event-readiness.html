Rehearse the current event flow, rotate every responsibility, recover from recorded evidence, and protect the exact robot version that repeatedly passes.

What you will make the team able to do

Complete three consecutive uncoached, event-like autonomous-to-driver-controlled passes using timing and procedure checked from current FIRST sources on delivery day. Rotate event, build, code, and test responsibilities; safely recover every failure; then identify one exact deployed and tested commit as the event candidate and name a known-good rollback. Any failed qualifying attempt or intervention listed in the test section resets the count to zero; earlier attempts remain useful nonqualifying evidence.

Words you need today

Match simulation
A complete practice run that follows the currently verified event phases, transitions, setup, Stop, and reset procedure.
Field reset
Returning the practice area and game pieces to the verified starting condition only after the robot is stopped and safe to approach.
Observer
A student who does not coach during the run and records what actually happened against the current cue card.
Pit
The event work area and process for inspection, diagnosis, repair, code recovery, and readiness between runs.
Triage
Sorting an issue by urgency and choosing the next safe action after the run.
Must-fix defect
A safety or event-blocking problem that must be corrected and fully retested before release.
Event candidate
The exact commit and robot configuration deployed for the complete passing simulations and proposed for the event.
Freeze
We stop adding features and identify the exact tested version. Files are still technically editable, but any later correction needs a new commit and the required tests again.
Rollback
Returning to a named earlier known-good commit and configuration when the candidate is unsafe, unavailable, mismatched, or broken.

Before you touch the robot

  • Copy the exact candidate commit, configuration, autonomous and fallback, TeleOp, battery, controllers, and Meeting 14 blockers before changing or running anything.
  • Record the current Competition Manual title, season, revision/date, URL, and check time. Copy current phases, timing, transitions, field interaction, drive-team limits, and local event instructions; do not use remembered constants.
  • Name the Driver Station operator and a separate Stop caller. Name a primary and backup for every active role.
  • Before contact or reset, press Stop, verify zero commanded motion, say stopped, switch off the Hub, disconnect/isolate the battery, and release or support stored energy.
  • Before motion, keep the Hub off while connecting the accepted battery; switch on; confirm Hub and Driver Station connection; select the exact candidate/configuration; press INIT; and verify identity and safe outputs before robot live and clear.
Press Stop for unexpected motion, unsafe field entry, loose hardware, cable movement, binding, communication loss, repeated reset, abnormal sound, heat, swelling, smoke, or odor. Verify zero motion, say stopped, switch off, and disconnect before anyone enters or touches the robot. Never combine field entry or robot contact with Driver Station control or Stop ownership.

Follow along: trace one complete event flow

  1. Verify the cue card: copy current official phases, timing, transition/start cues, field and human-player actions, and Stop/reset procedure. This prevents stale instructions. Success: the card names its current source and check time.
  2. Identify the robot: read the full commit, configuration, autonomous/fallback, TeleOp, battery, and controllers aloud. This prevents a good run from being credited to unknown code. Success: every run record can repeat the same identity.
  3. Walk the safe transition: rehearse Hub-off battery connection, Hub-on status, Driver Station connection, candidate selection, INIT safe outputs, live/clear, current event cues, Stop, zero motion, stopped, Hub off, battery disconnection, and only then field reset/contact. Success: each caller knows the next state and who controls it.
  4. Practice silent observation: the observer records cues, behavior, failures, and Stop without coaching. This preserves honest evidence. Success: the team can describe the run after it ends without changing it during the run.
  5. Make the release decision: triage each issue as must-fix, nonblocking defect, request, or current-rule question. This protects reliability from late features. Success: every item has a reason, owner, and required retest or defer decision.

Try all four roles with your partner

Three pairs: start in three lanes with one lane empty; every 15 minutes all pairs and the empty place move one lane. Two pairs: start in opposite lanes with two empty; move one lane each block. Every pair completes event, build, code/pit, and test/observer work. Swap the student acting and recording halfway through each lane.

1. Event and field

  1. Use the current cue card to mark setup, queue, field reset, human-player actions, phase cues, Stop, and exit.
  2. Map available field elements and label every substitute or absent interaction.
  3. Name the primary and backup; rehearse the clear-field and stopped calls.

Record: current-source cue card, reset map, unavailable limits, and primary/backup proof.

2. Build and inspection

  1. With power off and battery disconnected, inspect structure, fasteners/witness marks, wheels, mechanisms, guards, battery retention, wiring, connectors, starting posture, and clearance.
  2. Use FIRST for current inspection/legal equipment and exact manufacturer documents only for the installed part's inspection or service.
  3. Record accepted condition, must-fix item, exact spare, and required retest.

Record: signed inspection, today's Self-Inspect/current checklist, exact part/source, and gap owner.

3. Code and pit

  1. Verify full candidate and rollback hashes, clean state, configuration backup, build/deploy path, OpModes, and who may authorize a change.
  2. Locate the Meeting 14 recovery guide and practice finding one symptom, first evidence, safe action, and restore proof.
  3. List only exact tested spares, cables, tools, and recovery files.

Record: candidate/rollback card, restore path, recovery record, and packing gaps.

4. Test and observer

  1. Write one run row with prediction, setup identity, roles, current cues, expected behavior, Stop condition, and pass rule.
  2. Observe without prompting; record actual behavior, messages, field state, and failure time.
  3. State whether a complete rerun is required and why.

Record: runnable test card, objective observer notes, disposition, and named retest.

Staff every live run

Record a name and a different named backup for each responsibility before every run. The Driver Station operator/drive-team student controls the robot. The immediate Stop owner/caller does not operate the Driver Station and keeps uninterrupted access to Stop. The field-reset student enters only after stopped, Hub off, and battery disconnection. The pit responder preserves evidence and leads between-run recovery. The observer/logger watches without coaching and records the complete flow.

  • Four students / two pairs: Student A is Driver Station operator/drive team; Student B is the separate immediate Stop owner/caller; Student C observes/logs during the run and performs field reset only after safe shutdown; Student D is pit responder. On the next run, rotate A -> pit, B -> Driver Station, C -> Stop, and D -> observer/field reset; continue the same rotation. Name backups from students who already rehearsed that responsibility during the four practice lanes. Never combine Driver Station operation with Stop ownership.
  • Six students / three pairs: assign one student each to Driver Station operator/driver, second drive-team role if permitted by current rules, immediate Stop owner/caller, field reset, pit responder, and observer/logger. Rotate every student one position after each run, except use only role combinations permitted by the current manual and local event procedure. If the second drive-team role is not applicable, that student shadows one named backup without touching controls.

Test it safely: three consecutive complete passes

No coaching during a run. Mentors and inactive students may call Stop for safety but may not prompt setup, controls, strategy, code, or recovery. A coached run is practice, not one of the three passing simulations.
  1. Predict and inspect: name the expected autonomous, transition, driver-controlled behavior, fallback, and Stop result. Complete current inspection and identity checks. Success: all fields and role backups are named before power-up.
  2. Power and run: use the full safe power-up sequence, then follow the current official timing and procedure from queue/setup through autonomous, transition, driver control, Stop, zero motion, power-off/disconnection, reset, and pit return. Success: the observer records the whole flow without coaching.
  3. Triage after stopped: preserve symptom, time, hash, configuration, battery, input, field state, messages, telemetry, and logs. Test one explanation. Only a must-fix defect may justify the smallest controlled correction today.
  4. Reset the qualifying count: return to zero after any failed, coached, or otherwise nonqualifying attempt; redeploy; rebuild; repair; setup or procedure intervention outside the written normal reset; candidate or configuration change; or identity mismatch. Repeat inspection and the entire affected event flow before starting a new set. Keep every earlier attempt, but mark it nonqualifying rather than counting passes from before and after the interruption together.
  5. Freeze or block: freeze only after three new complete, consecutive, uncoached passes on the same exact deployed commit/configuration with no reset trigger between them and no unresolved must-fix defect. Otherwise restore the verified rollback when appropriate or leave release blocked.

Keep failed, coached, interrupted, and earlier passing attempts. Add rows or use another copy as needed. Only three new passes numbered 1, 2, and 3 with no reset trigger between them form the qualifying set.

If the field, robot, network, or current source is unavailable

  1. Partial field: mark available boundaries and rehearse queue, setup, cues, controls, Stop, handoff, and reset. Record absent interactions; do not claim scoring, collision, clearance, or official-field proof.
  2. No safe motion or robot: use the actual candidate, configuration, controllers, prior logs/video with source, and tabletop cards. Build and rehearse roles, but do not count physical passes or freeze newly unproven behavior.
  3. No current source: do not state remembered timing or procedure. Mark the latest recorded official document currency unverified, practice untimed flow, and assign a live recheck before freeze or event use.
  4. Not enough time/equipment: preserve the last proven version and record the blocked run, owner, and date for three complete physical simulations.

Mentor preparation

  • Audit Meeting 14's exact identity, recovery guide, inspection evidence, unresolved risks, and student demonstrations.
  • At delivery, open live FIRST Team Resources and the current Competition Manual/event resources. Record title, season, revision/date, URL, and time; extract current timing/procedure instead of supplying remembered values.
  • Compare the Driver Station Practice Timer with current procedure. If it differs, use a neutral timekeeper and written current-source cue card.
  • Prepare the safest realistic field, reset map, protected observer locations, battery flow, printed shared records, and explicit substitutes for unavailable elements.
  • Do not authorize a freeze unless three new consecutive complete uncoached passes with no reset trigger between them, exact deployed identity, inspection, Stop proof, no unresolved must-fix defect, and rollback are all recorded.
