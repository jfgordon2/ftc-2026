Start here

A control map connects a robot action to a button or stick. “Required” is our plan; “ready” means we have built and tested it.

  1. Use the current game manual to list legal collection and scoring actions. Read the specific rules linked below.
  2. Mark launching required. Mark an unfinished intake, feeder, or launcher “required — not ready” and give its build task an owner.
  3. Sketch the pollen path from the floor through intake and feeder to launcher. Compare what the practice robots already teach us.
  4. For each required action, choose hold, press-once, or variable input. Decide what release, reverse, conflicting buttons, and Stop should do.
  5. Act out the controls with one and then two gamepads. Record the simpler workable arrangement and review it together.

Robot for today: Choose REV practice, goBILDA practice, or the ready BIOBUZZ build. Keep separate records for each. See the practice and build plan.

Build task: Make a chassis and mechanism sketch. Choose parts, mounting locations, tool needs, and one next build task per pair.

Keep a short result: robot + code version; what we changed; expected result; observed result. Use the detailed worksheet when the test calls for measurements.

Read the safety checklist before power. Open the detailed steps for code, test cases, and worksheets; the mentor helps choose the section needed next.

Before you touch the robot

  • Do not deploy, run, or change robot code today. Park the gamepads while the team is designing controls.
  • Press Stop, switch off the Hub, and disconnect the battery before inspecting installed mechanisms.
  • Move a mechanism by hand only when its exact documentation and the mentor say that manual movement is safe. Otherwise inspect without moving it.
  • Record unknown mechanism identity, travel, safe state, or capability as pending. Do not turn a vendor example into evidence about a different robot.
  • Reject any proposed action that lacks a safe release and Stop behavior. Do not invent a power, position, timing, dimension, limit, or button assignment to fill a blank.
Stop the inspection for loose hardware, stored energy, unsupported parts, pinches, sharp edges, damaged wiring, or unexpected motion. Make the robot safe before continuing. No physical result is passed in this lesson.

Detailed steps, code, and worksheets

What you will decide

The team will approve one complete list of TELEOP actions. Every action will be classified required, optional, or unavailable, then receive a control design or an explicit reason that no control will be implemented.

This meeting produces a design contract, not robot code. Meetings 5-8 may implement and qualify only what this record approves. The matching vendor program is evidence about available mechanisms and existing controls; it does not decide the team's strategy or button map.

Team choice M04-D01 The team classifies actions and chooses one or two gamepads from workload, conflicts, safe release, recovery, feedback, and diagnosis evidence rather than convention.

Words you need today

Game action
Something the robot may need to do during the game, stated without naming a button or code solution.
Required
An action the team commits to implement and qualify for its current event plan.
Optional
An action that may add value but may not displace required, safe, reliable work.
Unavailable
An action the installed robot cannot currently perform or the team deliberately excludes. It receives no enabled control.
Proportional
An input whose amount can request different amounts of action. This describes behavior, not a particular stick, trigger, or output value.
Held
An action requested only while an input remains held.
One-press
One press requests one bounded action or state change; continuing to hold must not repeatedly create unintended requests.
Safe release
The exact safe output or verified safe hold expected when an operator stops requesting an action.
Conflict
Two requests that cannot be performed safely or reliably at the same time.
Control map
The approved connection from operator and input to action, behavior, feedback, safe release, recovery, and telemetry.
Reclassification
The formal Meeting 8 process for changing an approved required action to optional or unavailable when evidence shows it cannot be made safe.

Worked example: collect pollen

This is a paper design example, not our approved control map or a claim that hardware has passed. It follows the collection row in the game-action inventory. Recheck that row’s current rules before approving our version.

From a game action to a proposed control
DecisionExample answer
Action and reasonCollect allowed pollen from the floor so it can reach our required launcher. Use the collection row’s sections 10.1 and 10.5.3 and rules G407–G409 for the rule check; this example does not approve every possible collection situation.
Hardware and readinessAssume a motor-driven intake is planned but not yet installed. Classification: required. Readiness: not built; output disabled. Builder’s next task: complete the intake using the separate build instructions.
Operator and behaviorThe mechanism operator requests intake while the driver steers. Choose held input: collect only while the operator holds a button.
Proposed assignmentGamepad 2 right bumper requests collect; left bumper requests reverse. These are example team choices, not vendor defaults or required assignments.
Release, recovery, and conflictNeither button: command zero. Right alone: approved collect command. Left alone: approved reverse command. Both: command zero. Reverse is enabled only after the installed mechanism’s reverse test passes; Stop never depends on reverse working.
Feedback and testDisplay STOP, COLLECT, or REVERSE and the commanded output. Test neither, right, left, both, release, and Stop on the installed robot. Record which behavior actually occurred.
Approval and remaining workNot approved for powered use. Rehearse workload, build and inspect the intake, determine its safe settings, and complete physical tests before enabling it. This paper exercise supplies no motor power or completed measurement.
  1. One partner acts as the operator; the other reads each of the six test cases and asks what should happen.
  2. Explain why both buttons select STOP and why releasing the button must write zero.
  3. Use the blank control-design record for one actual team action. Change the example choices wherever our robot or workload needs something different.

Try it with your partner

Assign one pair to each workstream. With two pairs, combine installed capability with workload. Rotate the speaker and recorder halfway through. No pair may fill a control assignment from memory alone.

1. Game evidence

  1. Read each named section and rule in the current manual.
  2. Write what the rule permits, constrains, or forbids without proposing hardware or controls.
  3. Record the current revision, access date, exact section/rule, and any Team Update or Q&A question needing mentor review.
  4. Challenge any action whose rule citation does not support the words in its row.

Success looks like: every season-dependent action has an exact current section or rule and no vendor page is used as game authority.

2. Installed capability

  1. Use Meeting 3's matching source identity and trace; keep the unmatched program reading-only.
  2. With power disconnected, compare every traced mechanism with the installed robot.
  3. Mark each candidate installed, absent, or unknown. Record exact evidence or a named blocker.
  4. List unknown safe release, recovery, travel, and physical-limit evidence for Meeting 6.

Success looks like: the inventory distinguishes vendor-example capability from verified installed capability and invents no hardware value.

3. Operator workload

  1. Act out each required action with paper action cards while another student calls concurrent drive, alignment, scoring, and recovery tasks.
  2. Record who needs the action, what else that person is doing, and which simultaneous requests conflict.
  3. Compare a one-gamepad and two-gamepad rehearsal without assigning actual inputs.
  4. Recommend one or two gamepads from missed tasks, hand conflicts, communication load, and recovery access.

Success looks like: the recommendation cites observed workload and conflicts, not preference or convention.

Review the map before approval

This is a paper and source review, not a powered robot test. Read every action aloud and reject incomplete rows.

  1. Game check: verify each season claim against the named current manual section or rule. Pass: the citation supports the action and constraint; open interpretation questions are blocked, not guessed.
  2. Scope check: compare every installed claim with Meeting 3 and the powered-off robot. Pass: vendor assumptions, installed evidence, and unknowns are distinct.
  3. Classification check: ask what the event plan loses if each required action is removed. Pass: required, optional, and unavailable have specific rationales and approval.
  4. Workload check: act out each required action with concurrent tasks. Pass: the selected operator and gamepad count are plausible and all conflicts have a policy.
  5. Safety and recovery check: point to safe release, Stop expectation, reverse/recovery, feedback, and acceptance evidence. Pass: no required action depends on an invented state or an unexplained blank.
  6. Diagnosis check: trace proposed telemetry from input through decision/state to commanded output or safe state. Pass: Meeting 7 can distinguish a wrong request from a wrong decision or output.
  7. Source-scope check: search the map for every number and control name. Pass: each is an actual team assignment, exact-source fact, or pending measurement; none came from the unmatched vendor path.

Approval gate: every action is present, every required field is complete, all blockers are explicit, the gamepad-count rationale is signed, and the team can explain what Meetings 5-8 must implement and prove. Otherwise mark the map provisional.

If the robot or current source is unavailable

  1. Use the saved Meeting 3 matching trace to inventory candidate capability. Mark installed mechanism availability pending physical inspection; do not claim it is present.
  2. Use a mentor-provided saved copy of the current manual only if its revision and retrieval date are known. If the current manual, Team Update, or needed Q&A cannot be checked, mark affected game claims pending current-source check.
  3. Complete the game-action, classification, workload, conflict, behavior, feedback, telemetry, and one/two-gamepad analysis on paper.
  4. Leave hardware-dependent safe release, recovery, limit, and acceptance evidence pending. Invent no replacement value or result.
  5. Mark the map provisional, not approved for implementation. Name the person and date for source recheck and powered-off robot inspection before Meeting 5 or 6 uses the affected row.

Success looks like: useful strategy and workload work is complete, every unavailable check has an owner, and no unverified physical or season claim is presented as passed.

Then explain one fact that remains pending.

Record each student's evidence

  • Game reasoning passes when the student distinguishes a manual fact from a team strategy choice.
  • Control reasoning passes when the student chooses behavior and safe release before naming an input.
  • Source reasoning passes when the student refuses to transfer an unmatched vendor control or value.
  • Team reasoning passes when the student can defend or revise the one/two-gamepad decision from workload evidence.

How Meeting 8 may reclassify an action

The signed map is an implementation contract, not permission to keep an unsafe feature enabled. If Meeting 8 evidence shows a required feature cannot be made safe, use every step below.

  1. Record the failed criterion, trials, defect evidence, affected action, and why repair/retest did not make it safe.
  2. Propose optional or unavailable; record the strategy cost and rationale. Do not silently delete the row.
  3. Obtain named mentor and team approval with date and new map revision.
  4. Disable the behavior in code, remove it from the event plan, and identify it as excluded on the qualification record.
  5. Repeat the complete qualification routine under the revised scope. A previous run does not qualify a changed scope.
Not waivable: safe initialization, drivetrain control, Stop, and every action still classified required. Repair and retest those capabilities; do not reclassify them merely to claim a pass.
