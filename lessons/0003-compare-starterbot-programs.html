Before you touch the robot

  • Name the routine Driver Station operator, observer, recorder, and a separate Stop owner. The Stop owner keeps immediate access to Stop and may press it without permission.
  • Press Stop, switch off the Control Hub, and disconnect the battery before touching wheels, mechanisms, wiring, supports, or game pieces.
  • Remove game pieces. Inspect and secure the robot, battery, Hub, wires, wheels, drivetrain, intake, launcher or flywheel, feeder or windmill, and pollen poker or corner-intake servos that exist on the matching assembly.
  • Match each practice robot to its own saved last-season program, configuration, motor map, and modifications. Keep the BIOBUZZ vendor examples below reading-only unless the installed robot actually matches that new-season assembly.
  • For the first powered run, place the robot on stable support in the game arena. Prove every drive wheel is clear and every mechanism has unobstructed travel. Mark an exclusion area and keep everyone outside it before INIT.
Supported test before Travel test. The matching program must pass the Supported test cases, neutral-output check, and Stop check before the robot moves to the marked start. Unexpected motion, support movement, interference, loose hardware, wire movement, heat, smoke, odor, unusual sound, implausible telemetry, or lost control means immediate Stop, Hub off, battery disconnected, and no contact until the Stop owner says stopped.

Words you need today

TeleOp
A driver-controlled OpMode that reads controls and commands robot outputs after Start.
Lifecycle
The stages in which an OpMode initializes, waits, runs repeatedly, and stops. A linear OpMode puts that flow in one runOpMode(); an iterative OpMode separates it into methods such as init() and loop().
Method
A named group of instructions. Both programs use subsystem methods so a reader can follow one robot action at a time.
Parameter
An input named by a method. In arcadeDrive(double forward, double rotate), forward and rotate carry requested motion into the method.
Source identity
The exact file or page, revision or access date, and checksum when available that identify the code the team reviewed.
Working tree
The files currently checked out on the laptop, including saved changes that are not yet committed.
Diff
A line-by-line view of what changed from a chosen Git version. Today it must show only one telemetry-label edit in the matching program.
Commit
A Git history record of staged changes. Today students create one only after the matching program's controlled test passes.
Supported test
A powered test with the robot stable on inspected support, drive wheels clear of the floor, mechanism travel clear, and people outside the marked exclusion area.
Travel test
A powered test in the game arena that begins at a marked start, follows a marked route to a marked stop, and keeps everyone outside the exclusion area.

Follow along: trace both programs side by side

First trace the saved programs that belong to our two last-season practice robots. For each, find setup, repeated input reading, drive output, mechanism output, and Stop. Do not assume their lifecycles or button assignments match the examples below. The 2026-2027 examples are a separate design comparison for our BIOBUZZ build; they are not the programs to install on the practice robots.

REV 2026-2027 Starter Bot TeleOp

  • Lifecycle: the class extends LinearOpMode. One runOpMode() maps hardware, applies setup, waits for Start, and repeatedly calls subsystem methods while the OpMode remains active.
  • Drive: the left-stick arcade drive in arcadeDrive() reads left stick X and reversed left stick Y. It sends y + x left and y - x right, so one left stick supplies forward/reverse and rotation.
  • Intake: intakeControls() uses the right bumper for intake, a right-trigger press for reverse, and zero otherwise.
  • Pollen poker: pollenPoker() uses edge-detected cross and circle presses to request its two positions.
  • Flywheel and feeder: flywheelControls() provides manual forward and reverse flywheel requests, a velocity-gated feeder request, manual feeder forward/reverse, and a neutral branch that stops flywheel and feeder output.

Boundary: these names, directions, controls, mechanisms, and source settings belong only to the exact REV 2026-2027 Starter Bot example.

Source M03-F01

goBILDA 2026-2027 StarterBot TeleOp

  • Lifecycle: the class extends iterative OpMode. init() maps and configures hardware; init_loop() and start() are present; loop() repeatedly updates behavior; and stop() is present.
  • Drive: loop() calls arcadeDrive(-gamepad1.left_stick_y, gamepad1.right_stick_x). This is left-stick forward/reverse and right-stick rotation.
  • Parameterized method: arcadeDrive(double forward, double rotate) sends forward + rotate left and forward - rotate right.
  • Trigger intake: right trigger minus left trigger creates proportional intake power, which is later sent to the intake motor and both corner-intake servos.
  • Launcher, windmill, and intake-assist behavior: launch() uses a held right bumper to request launcher velocity. Above the source's velocity gate it runs the windmill and adds intake assist; otherwise it stops the windmill, and releasing the bumper requests zero launcher velocity.

Boundary: these names, directions, controls, mechanisms, and source settings belong only to the exact goBILDA 2026-2027 StarterBot. The verified ZIP contains this TeleOp and no Autonomous program.

Try it with your partner

Three pairs: rotate every 20 minutes, then use five minutes to reconcile records. Two pairs: spend 15 minutes at Source or Lifecycle, swap for 15 minutes, then spend 35 minutes on Match and Change together (65 minutes total). Swap driver and navigator before any edit.

1. Source and assembly

  1. Record the installed manufacturer, exact assembly revision, visible identifiers, saved configuration, and Meeting 2 motor-map evidence.
  2. For each practice robot, record the saved source file, commit or archive identity, robot season/revision, and matching configuration. Separately record the URL/date or ZIP identity of each BIOBUZZ reading example.
  3. Compare the physical mechanisms and configuration names with the matching source. Record every contradiction as a blocker with an owner and next check.
  4. Mark one source matching run candidate only if all identity evidence agrees. Mark the other reading comparison only - do not install or run.

Success looks like: another student can identify the exact installed assembly, exact reviewed source, and why only one path may run.

2. Lifecycle and controls

  1. Trace the REV LinearOpMode from runOpMode() through wait, active loop, and all four subsystem calls.
  2. Trace the goBILDA iterative OpMode through init(), init_loop(), start(), loop(), and stop().
  3. Draw each drive-input path from physical stick to field, arithmetic, method, and left/right output.
  4. Complete the mechanism/control rows, shared patterns, vendor assumptions, one keep choice, and one reconsider choice.

Success looks like: your trace explains both programs without claiming their controls or hardware are interchangeable.

3. Matching path and bounded change

  1. Open only the matching checked-in program or the activated matching prepared Blocks project. Confirm its file/project identity against the source record.
  2. Before editing, run the team's status view and confirm unrelated changes are identified and left untouched.
  3. Change one team-specific telemetry label that identifies the selected path, such as changing only a caption to TEAM_NAME REV | Flywheel Velocity or TEAM_NAME goBILDA | Motors.
  4. Do not change hardware names, directions, controls, drive arithmetic, mechanism logic, constants, imports, formatting, or the unmatched program.
  5. Build the matching Java program, or save and validate the prepared Blocks project, then inspect the path-limited diff.

Success looks like: the matching artifact builds or validates and the diff changes exactly one telemetry-label line or one equivalent Blocks telemetry-label field.

Test it safely: Supported test before Travel test

A. Matching-program Supported test

  1. Write the cases: on the robot test card, list neutral, matching drive inputs, each matching mechanism request, telemetry-label result, Stop conditions, and the mentor-approved input boundaries. This makes expected motion visible before power. Success: every case names the input, expected output, observer, and abort condition without inventing a source setting.
  2. Recheck identity: compare the exact assembly, active configuration, motor map, matching checked-in file/project, source identity, and one-line diff. Success: two students sign the match and the unmatched path is marked reading comparison only.
  3. Secure and clear: with the battery disconnected, remove game pieces; place the robot on stable support; verify every drive wheel and mechanism can move without contact; secure the Hub, battery, wires, and robot; and clear the exclusion area. Success: the observer signs support, clearance, and mechanism checks.
  4. Prepare controls: position the routine operator and separate Stop owner with immediate Stop access. Connect the battery, switch on the Hub, confirm the expected Robot Controller connection, assign the gamepad, and select only the matching OpMode/project. Success: roles, connection, gamepad, and displayed identity match the card.
  5. Clear before INIT: release every control, have the operator say robot live, have the observer verify the exclusion area and answer clear, then press INIT. INIT executes user code. Success: initialization completes with no unexpected motion or diagnostic.
  6. Verify the change: confirm the team-specific telemetry label appears in the expected lifecycle stage. Success: the exact caption identifies the selected vendor path.
  7. Run one case at a time: press Start, apply only the named input within the recorded boundary, release it, and observe the matching output. Press Stop between cases whenever the card requires repositioning or inspection. Success: each observation matches its prediction, neutral removes the requested output, and no excluded behavior appears.
  8. Prove Stop: during the planned Stop case, the Stop owner presses Stop. Verify outputs and motion end, say stopped, switch off the Hub, and disconnect the battery before contact. Success: the result and any remaining motion are recorded exactly.
  9. Handle any failure: keep the original failed row, make the robot safe, record the symptom, and change only one evidence-supported item. Rebuild and repeat every Supported test case the correction could affect. Success: the before-and-after records remain traceable; the Travel test remains prohibited until all required Supported test cases pass.

B. Optional Travel test

The Travel test is optional. Authorize it only when every required Supported test case passes and the mentor signs the Travel test authorization row. Keep every mechanism control neutral; this is a short drive-only confirmation, not mechanism testing.

  1. Prepare the route: only after the Supported test gate passes, press Stop, verify motion has ended, say stopped, switch off the Hub, and disconnect the battery before moving the robot to the marked start in the game arena. Mark the route, marked stop, exclusion area, operator position, and Stop-owner position. Success: both operator and observer sign the marked start, marked route, marked stop, exclusion area, and role checks.
  2. Prepare the exact tested program: reconnect and switch on, select only the supported matching program, assign the gamepad, release controls, call robot live, receive clear, and press INIT. Success: identity and telemetry match the Supported test and everyone remains outside the exclusion area before Start.
  3. Run the marked route: from the marked start, press Start and apply only the card's bounded forward/reverse or rotation input. Follow the marked route, release controls, verify neutral, and press Stop at the marked stop or immediately for an abort condition. Success: the robot follows the marked route, responds as predicted, and stops at the marked stop while everyone remains outside the exclusion area.
  4. Record and power down: record marked start, marked route, marked stop, response, neutral, Stop, and any symptom; say stopped; switch off the Hub; and disconnect the battery. Success: the Travel test result is tied to the exact Supported test trial and source identity.
  5. Requalify after a correction: any code, configuration, electrical, or mechanical correction cancels Travel test authorization. Return to stable support and repeat every affected Supported test case before another Travel test. Success: a fresh Supported test record authorizes the new Travel test.

Measure it M03-M01

Students: inspect the tested diff and create the commit

Begin only after the matching program's required controlled test is recorded as passing. Keep the robot stopped, Hub off, and battery disconnected while students use Git.

  1. Show the working tree and verify a clean index: a student runs git status --short and git diff --cached --quiet in the robot-code repository. The working tree is the current checked-out files and their uncommitted changes; the index holds changes selected for the next commit. Success: the team identifies every changed path and the quiet command exits successfully, proving the index is clean. If it does not, do not stage or commit until the owner resolves the existing staged work.
  2. Inspect only today's path: a student runs git diff -- path/to/MATCHING_FILE. git diff shows unstaged changes. Success: the output contains exactly the one tested telemetry-label change and no behavior change.
  3. Stage only the tested artifact: a student runs git add -- path/to/MATCHING_FILE. Success: only the exact matching file containing the tested telemetry label is selected.
  4. Inspect the complete index: a student runs git diff --cached --name-only and the unrestricted git diff --cached. If either command shows an unrelated path, run git restore --staged -- path/to/UNRELATED_FILE; this preserves its working-tree change. Repeat both complete-index commands until the name list contains only path/to/MATCHING_FILE and the staged diff contains exactly the one tested telemetry-label change. Success: no unrelated staged change can enter the commit.
  5. Create the record: only after the complete index passes, a student runs git commit -m "Identify matching StarterBot path". git commit records every staged change in repository history, so do not run it unless the previous step passes. Success: Git reports one new commit containing only the matching program's tested telemetry-label change.
  6. Record its identity: a student runs git rev-parse --short HEAD and copies the short hash and message into the controlled-test record. Success: another student can connect the commit to the exact source, diff, and passing trial.

If any required test is failed, blocked, or unperformed, students may inspect git status and git diff for learning, but they do not create the tested commit.
