Today’s goal

Compare launcher speed graphs and tune F, then P, one change at a time.

Start here

F supplies a starting estimate of motor effort. P corrects speed error. Changing both at once hides which change helped.

  1. Read the original PIDF values from the actual controller and save them with its mode and robot configuration.
  2. Graph target and measured velocity for three baseline trials. Describe slow response, overshoot, or repeated swings.
  3. Choose a pass rule before tuning. Compare one small F change at a time using the approved procedure.
  4. Keep or restore F, then compare P changes. Leave I and D unchanged; stop and restore settings if behavior becomes unsafe.
  5. Run three final trials. Keep the new settings only if the evidence supports them; otherwise restore the original values.

Words you need before using them

Target velocity
The launcher speed the program requests, in the exact controller/API unit recorded for this setup.
Measured velocity
The launcher speed reported from encoder feedback at a named time, in the same recorded unit as the target.
Error
Target velocity minus measured velocity. Signed error keeps above/below direction; absolute error keeps only the size of the difference.
Control loop
The controller's repeated compare-and-adjust process: read target and measured velocity, compute error, and adjust output.
PIDF coefficients
Four controller settings named P, I, D, and F. Their units, scaling, and exact behavior depend on the controller implementation and selected run mode.
F: feedforward
An estimate of the baseline output needed for the requested speed before feedback corrects the remaining error.
P: proportional
An immediate correction that changes with the current error: a larger current error requests a larger correction.
I: integral
A correction based on error accumulated over time. Accumulation may continue while correction is limited, which is called windup.
D: derivative
A correction based on how quickly error changes. It may add damping, but measurement noise may make it react rapidly.
Ready state
The recorded true/false result of the Meeting 12 ready condition; it does not mean safe or successful unless every declared criterion also passes.
Overshoot
How far measured velocity crosses beyond the target or ready band after starting or recovering.
Oscillation
Repeated movement above and below the target. One crossing is not sustained oscillation; small irregular changes may be measurement noise.
Recovery
How the launcher returns toward ready velocity after the same controlled launch/load removes energy.
Baseline trial
A trial run with a named starting configuration that later trial results are compared against.
Candidate
One proposed coefficient configuration being tested; it is not accepted merely because it ran.
Acceptance criteria
The pass, fail, and safety rules recorded before candidate results are visible.
Supported test
A powered test only in the game arena: the robot frame is secured on stable support; wheels and launcher hazards are safely clear as applicable; the battery, Hub, wires, attached pieces, mechanisms, and test artifact are secured; a marked exclusion area is clear; a Driver Station operator and independent Stop owner are named; and no one contacts the live robot or setup.
Rollback
The complete original read-back P, I, D, and F tuple, controller, run mode, and code identity kept so the team can restore the starting configuration.

Source M13-F01 The pinned API requires an explicit run mode when reading or writing PIDF coefficients and warns that controller implementations may differ. The letters above are a mental model, not universal coefficient units, equations, values, or guaranteed effects.

Trace only the matching controller and source

  1. Read before writing: identify the exact velocity-control run mode, call getPIDFCoefficients(mode), and record the returned tuple before any setter call. Confirm the read mode is the same mode the launcher uses. Success: rollback includes controller, mode, tuple, code identity, and read time.
  2. Trace the guarded action: point to target, measured velocity, ready rule, active check, timeout, abort, load/feed action, and explicit shutdown for every touched output. Success: a coefficient change cannot bypass Meeting 12 guards.
  3. Trace one coefficient write: verify the same explicit mode and preserve P/I/D/F ordering. Display requested and read-back values after the write where the controller supports reliable read-back. Success: mismatch or unsupported behavior blocks trials.
  4. Keep scope narrow: F changes only during the F phase. After selecting/restoring F and creating a new P-phase baseline, P changes only during the P phase. I and D remain equal to the original matching-source values throughout.
